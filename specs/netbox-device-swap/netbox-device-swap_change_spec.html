Wiom · Change Spec · v0.1 · PM deliverable

CSP Netbox Swap — Diagnosis-Driven Device Replacement

Makes the OS-defined netbox swap reachable end-to-end for CSPs/technicians: complaint intake opens to all connection lifecycle states, CSPs record a device diagnosis on the task, a device-fault diagnosis initiates the swap journey, and every swap leaves a verifiable, reconcilable audit trail. Per author directive, this spec carries exact technical references (API paths, event names, field names, DB columns) inline — a deliberate deviation from the template's default scope fence, requested for tech-team handover.

Author: Jaivin Prajapati  ·  Reviewer: Engineering  ·  Tier: Full

Quick Check

7-line triage. Filled last, after the body.
What is changing?
The built-but-unreachable netbox swap flow becomes a live CSP journey: intake gate on connection state removed, diagnosis capture added, device-fault diagnosis initiates the swap; swap guard G6 removed.
What triggered it?
Product decision: today's swaps run outside the OS (manual/old-app); the OS-governed flow exists in backend but has no diagnosis write-path, so it can never execute. Audit trail of swaps is unverifiable.
Blast radius
Complaint intake & auto-closure (SRS), RESTORE task resolution journey (CSP app + SRS), swap emission guards (SRS), custody swap execution (ACS — no change, confirmation only).
Reversible?
Feature: Yes — disabling the diagnosis→swap journey stops all swaps cleanly. An executed swap: No, by design — there is no un-swap; reversal is a second forward swap.
Money / PII / migration?
N / N / N.
OS impact / sign-off?
SR OS (behaviour change — Varun, Pending) · ESR (contract change — Dhruv, Pending) · Asset Custody OS (confirmation-only — Dhruv, Pending). Not all signed off.

A2. Why This Change WHAT

QuestionAnswer
What's wrong with the current behaviour?When a CSP/technician diagnoses a faulty netbox, there is no in-system way to swap it: the OS-governed swap flow exists in the backend but is unreachable (no diagnosis can be recorded, so its entry guards can never pass), and complaints on non-ACTIVE connections are auto-voided before any resolution can happen. Real swaps therefore happen outside the system, with no verifiable record.
Who experiences it?Customers with internet issues caused by faulty devices (delayed/no resolution); CSPs and technicians (no legitimate swap path); Wiom inventory & finance (swaps cannot be reconciled — devices move without audit trail).
Cost of leaving it as-is?Every swap remains an off-books device movement: unrecoverable devices, unreconcilable inventory, customer downtime, and a complaint system that voids genuine issues based on connection lifecycle state.

A3. Current Behaviour WHAT

Confirmed with author 2026-06-06. Observable behaviour of the slice being changed. Technical references inline per author directive.
Trigger / conditionObservable behaviour today
Customer on a non-ACTIVE connection (paused / deactivating) reports an issueThe complaint is auto-voided: when the system learns the connection deactivated (CL_CONNECTION_DEACTIVATED event), any complaint in INTAKE, CLASSIFIED, or PENDING_VERIFICATION moves to UNRESOLVABLE with reason CONNECTION_INACTIVE. No service ticket survives; no swap is possible.
CSP works a RESTORE task and concludes the device is faultyThere is no way to tell the system. The diagnosis fields exist on the task record (complaint_tasks.diagnosis_outcome, complaint_tasks.diagnosis_fault_type) but no app journey or API writes them — so the swap entry guards (G8 "diagnosis complete", G9 "device fault type") can never pass, and the swap flow is unreachable in practice.
A swap is submitted (POST /tasks/{taskId}/device-swap with old_device_id, new_device_id)SRS validates G6–G11 (incl. G6: connection ACTIVE via CL OS query) and emits DEVICE_SWAP. ACS validates G1–G5, atomically moves the old device DEPLOYED → RETRIEVAL_PENDING and the new device CUSTODIED/IDLE → DEPLOYED, and emits DEVICE_SWAP_COMPLETED. SRS records the swap on the complaint (complaints.device_swap_old_device_id, device_swap_new_device_id, device_swap_initiated_at, device_swap_completed_at, resolution_type = DEVICE_REPLACED) and moves it to PENDING_VERIFICATION. Guard failure → rejection with reason (DEVICE_SWAP_REJECTED), complaint unchanged. No completion within 120 s → ops flag, complaint stays open.
A swap completesNothing informs the old-app stack (inventory service, remote service) — actual internet connectivity does not shift to the new device. Only TAS updates its installation-candidate device reference.
Verification window runs after a swapTelemetry check is always inconclusive in v1; customer confirmation or the customer-verification timeout resolves the complaint. Customer denial re-escalates it. A completed swap is never reversed.
CSP attempts another swap on the same complaint after failed verificationNothing explicitly governs it — guards re-evaluate and a second swap proceeds if they pass. No allow/disallow rule is defined.

A4. Desired Behaviour WHAT

Trigger / conditionDesired observable behaviour
Customer on any connection lifecycle state reports an issueA service ticket is created regardless of connection state. CL_CONNECTION_DEACTIVATED no longer voids complaints in INTAKE / CLASSIFIED / PENDING_VERIFICATION — it is consumed as context only. CONNECTION_INACTIVE remains available as an explicit, executor-chosen closure reason.
CSP works a RESTORE task and concludes the device is faultyThe CSP walks guided diagnosis steps in the app (generic in v1 — educational) and records the result: a diagnosis outcome and one fault type. Recording writes diagnosis_outcome + diagnosis_fault_type onto the active task (proposed endpoint: POST /tasks/{taskId}/diagnosis — engineering may rename).
Recorded fault type is one of the 3 device faults (DEVICE_HARDWARE / DEVICE_SOFTWARE / DEVICE_CONNECTIVITY)The swap journey opens automatically — no resolution-type menu. The CSP picks a replacement netbox from their own inventory and submits. The system records resolution_type = DEVICE_REPLACED on the complaint without the CSP selecting it. Any other fault type → the swap journey never opens; existing resolution paths apply unchanged.
A swap is submittedAs today, minus G6: connection-state is no longer checked before emitting DEVICE_SWAP (the custody binding guards G4/G5 remain the protection — a connection without a matching device binding mechanically fails the swap). Everything else identical: ACS guards, atomic two-device transition, swap recorded on the complaint, PENDING_VERIFICATION, 120 s completion window.
A swap completesConnectivity-shift information flows to the old-app stack (inventory service, remote service, others). [Details pending — PM to supply; placeholder section, see A5-D9.] The old device is expected back at Wiom (RETRIEVAL_PENDING, unchanged custody tail).
Verification fails (customer denies) after a swapThe swap stands — no un-swap exists. The complaint re-escalates per the existing model; SRS already holds the new device as the connection's device; the CSP may re-diagnose and perform another swap. The displaced device proceeds to return-to-Wiom regardless.
Complaint reopens after swap (within reopen window)Same complaint lineage, no fresh SLA clock — and the reopened complaint runs against the new device, because the swap already updated the complaint's device facts when ACS confirmed.
Repeat swap on the same complaintAllowed, unlimited. Guards re-evaluate on every attempt; each executed swap appends to the same complaint's audit trail. Each displaced device enters RETRIEVAL_PENDING.

A7. Rules, Invariants & Edge Cases Affected WHAT

A7.1 Rules & invariants (must always hold)

#Rule / invariantStatement
I1INV — complaint anchoringEvery swap submission carries a complaint_id whose complaint is in ASSIGNED or ESCALATED at the moment of submission. A swap without an open complaint is structurally impossible.
I2INV — swap atomicityFor any swap attempt, either both devices transition (old → RETRIEVAL_PENDING and new → DEPLOYED) or neither does. At no instant are zero or two devices bound to the connection.
I3INV — single bindingA connection has at most one device bound to it at any moment — including during and after any number of repeat swaps.
I4INV — diagnosis gateThe swap journey is reachable only when the active task carries a recorded diagnosis_fault_type in {DEVICE_HARDWARE, DEVICE_SOFTWARE, DEVICE_CONNECTIVITY}. No diagnosis, or a non-device diagnosis, means no swap journey.
I5INV — audit completenessEvery executed swap is recorded on its complaint with old device id, new device id, initiation and completion timestamps — sufficient to reconcile every swap from complaint records alone.
I6INV — no lifecycle auto-closureNo complaint is ever moved to a terminal state by a connection lifecycle event. Terminal transitions require resolution, verification outcome, or explicit executor/ops action.
I7INV — resolution-type consistencyEvery swap executed via the device-fault journey carries resolution_type = DEVICE_REPLACED on the complaint. No swap exists with a different or missing resolution type.
R1RULE — unlimited repeat swapsAny number of swaps may execute against one complaint; each attempt re-runs all remaining guards; no cap parameter exists in v1.
R2RULE — explicit CONNECTION_INACTIVECONNECTION_INACTIVE may appear as an unresolvable reason only from an explicit executor/ops closure, never from automatic event handling.
R3RULE — duplicate-submission safetyWhile a swap is in flight (emitted, completion not yet received), a second submission for the same task is rejected as "swap in progress". A duplicate of an already-processed swap event is ignored (idempotent) — it never produces a second device transition.

B5. Acceptance Criteria — Verification Layer HOW

Backend point of view, derived from the required behaviour (A5/A7), not from existing code. Labelled Given/When/Then blocks across five classes; coverage audited in B5.1.

Business logic

LOGIC_01 (D1 · happy): Ticket on a non-ACTIVE connection
Given a connection in a paused or deactivating lifecycle state
When the customer reports an internet issue
Then a service ticket is created and proceeds to classification
And no connection-state check blocks or voids it
LOGIC_02 (D2 · negative): Deactivation event no longer voids
Given complaints in INTAKE, CLASSIFIED, and PENDING_VERIFICATION for one connection
When a connection-deactivated event arrives for that connection
Then all three complaints remain in their current states
And no UNRESOLVABLE transition occurs and no resolution signal is emitted
LOGIC_03 (D3 · happy): Explicit CONNECTION_INACTIVE closure still works
Given an open complaint whose connection is genuinely gone
When an authorised executor/ops user explicitly closes it as unresolvable with reason CONNECTION_INACTIVE
Then the complaint reaches UNRESOLVABLE with that reason recorded as an explicit action (actor + timestamp)
LOGIC_04 (D4 · happy): Swap proceeds without any connection-state query
Given an open complaint with a device-fault diagnosis and a valid replacement device
When the swap is submitted
Then the swap emits without any connection-state lookup having occurred
And an unavailable connection-state source can never block or fail a swap submission
LOGIC_05 (D5 · happy): Diagnosis recording
Given a CSP on an active RESTORE task of an open complaint
When they record a diagnosis with outcome text and exactly one fault type from the registry
Then both values persist on that task and are retrievable
And the recording actor and time are auditable
LOGIC_06 (D5 · negative): Diagnosis outside an actionable task
Given a task whose complaint is not in ASSIGNED or ESCALATED
When a diagnosis recording is attempted
Then it is rejected and nothing is written
LOGIC_07 (D6 · happy): Device fault opens the swap journey and sets resolution type
Given a recorded fault type of DEVICE_HARDWARE, DEVICE_SOFTWARE, or DEVICE_CONNECTIVITY (each tested)
When the CSP completes the swap journey and submits
Then the complaint carries resolution_type DEVICE_REPLACED set by the system
And at no point did the CSP choose a resolution type
LOGIC_08 (D6 · negative): No diagnosis → no swap
Given an active task with no recorded diagnosis
When a swap submission is attempted directly (bypassing the journey)
Then it is rejected on the diagnosis-complete guard and no swap event is emitted
LOGIC_09 (D7 · happy): Second swap on the same complaint
Given a complaint with one completed swap and a subsequent failed verification
When the CSP re-diagnoses a device fault and submits a second swap with a new replacement
Then the second swap executes through the full guard set
And both swaps are independently visible in the complaint's audit trail
LOGIC_10 (D8 · negative): Failed verification never reverses a swap
Given a completed swap on a complaint in verification
When the customer denies the resolution
Then the complaint re-escalates per the existing model
And both devices remain exactly in their post-swap states (new: serving the connection; old: pending return to Wiom)
LOGIC_11 (D10 · negative): UPGRADE reason unreachable
Given the v1 swap journey
Then every emitted swap carries reason FAULTY_DEVICE
And a request carrying reason UPGRADE is rejected as out of scope

Computation & calculation

COMPUTE_01 (completion window · normal): Completion within the window
Given a swap emitted at time T with a 120-second completion window
When completion arrives at T + 119 s
Then the swap is recorded as completed and no ops flag is raised
COMPUTE_02 (completion window · boundary): Window expiry is exact
Given a swap emitted at time T with no completion received
When the clock reaches exactly T + 120 s
Then the ops flag is raised and the complaint remains open (no auto-resolve)
And a completion arriving at T + 121 s is still processed normally with the ops flag retained as advisory (E5)
COMPUTE_03 (reopen window · normal): Reopen inside the window
Given a complaint resolved after a swap at time R, with the reopen window configured
When the customer reports the same issue (same connection, class, subtype) before the window ends
Then it attaches to the original lineage with no fresh SLA clock
And the reopened complaint references the new device as the connection's device
COMPUTE_04 (reopen window · boundary): Reopen outside the window
Given the same resolved complaint
When the same issue is reported just after the reopen window expires
Then a new, independent complaint is created with a fresh SLA clock
And it too references the new device
COMPUTE_05 (swap count · zero/unbounded): Audit under repeat swaps
Given one complaint that undergoes 0, 1, and N>2 swaps (each tested)
Then the number of reconstructible swap records on the complaint equals exactly the number of completed swaps
And rejected or timed-out attempts are distinguishable from completed swaps

Invariants

INVARIANT_01 (I1): Complaint anchoring
Given any swap event ever emitted, under any path including repeats and races
Then its complaint was in ASSIGNED or ESCALATED at submission time
And no path exists that emits a swap without an open complaint
INVARIANT_02 (I2): Atomicity
Given any swap attempt, including one that fails mid-execution
Then either both device transitions are observable or neither is
And a partial outcome (one device moved, the other not) is never observable, even transiently to a concurrent reader
INVARIANT_03 (I3): Single binding
Given any connection at any moment — before, during, and after any number of swaps
Then at most one device is bound to it
And immediately after each completed swap exactly one device (the newest) is bound
INVARIANT_04 (I4): Diagnosis gate
Given every path into the swap journey, including direct API calls
Then a swap can only initiate when the active task's latest recorded fault type is one of the 3 device types
And no swap exists whose task lacks such a diagnosis at submission time
INVARIANT_05 (I5): Audit completeness
Given every completed swap in the system
Then the complaint record alone yields: old device id, new device id, initiated-at, completed-at, and the governing complaint
And a reconciliation run over complaints finds every device that left or entered DEPLOYED via swap
INVARIANT_06 (I6): No lifecycle auto-closure
Given any sequence of connection lifecycle events against any complaint in any state
Then the complaint never reaches a terminal state from those events alone
And every terminal transition traces to a resolution, a verification outcome, or an explicit human action
INVARIANT_07 (I7): Resolution-type consistency
Given every swap executed via the device-fault journey
Then its complaint carries resolution_type DEVICE_REPLACED
And no completed swap exists with a missing or different resolution type

Use & edge cases

EDGE_01 (E1): Swap on a deactivating connection
Given a connection whose device binding has been cleared by deactivation
When a swap is submitted for it
Then submission passes (no G6) but custody rejects on the binding guards
And the CSP receives the binding-specific rejection and no device changes state
EDGE_02 (E4): Chained swap custody states
Given a complaint with swap #1 completed (device A out, device B in)
When swap #2 completes (device B out, device C in)
Then A and B are both pending return to Wiom, C is serving the connection
And the audit trail orders both swaps unambiguously
EDGE_03 (E6): Non-device diagnosis
Given a recorded fault type outside the 3 device types
Then the swap journey is not offered and a direct swap submission is rejected on the fault-type guard
And existing non-swap resolution paths remain available
EDGE_04 (E7): Invalid replacement device
Given a replacement device that is (a) owned by a different CSP, or (b) in a non-eligible custody state (each tested)
When the swap reaches custody validation
Then it is rejected with the specific guard reason and no state changes
And the CSP can immediately retry with a different device on the same complaint
EDGE_05 (E8): Complaint becomes non-actionable between diagnosis and submission
Given a device-fault diagnosis recorded on a task
When the complaint leaves ASSIGNED/ESCALATED (platform takeover or explicit closure) before the swap is submitted
Then the submission is rejected on the open-complaint guard
And no swap event is emitted
EDGE_06 (E9): Re-recorded diagnosis governs
Given a task first diagnosed DEVICE_HARDWARE, then re-recorded as a non-device fault
When a swap submission is attempted
Then it is rejected — the latest diagnosis governs
And re-recording back to a device fault re-opens the journey
EDGE_07 (E12 / R3): Duplicate submission
Given a swap in flight (emitted, completion not yet received)
When the same task submits again
Then the second submission is rejected as swap-in-progress
And a duplicate delivery of the same swap event to custody produces no second transition (idempotent)
EDGE_08 (E2+E3 chain): Deny-then-reopen sequence
Given a completed swap, then customer denial, then resolution, then a reopen within the window
Then at every step the complaint lineage is single and continuous
And every post-swap interaction references the new device, never the displaced one

Regression

REGRESSION_01 (G-A): Non-swap resolutions unaffected
Given a RESTORE task with no diagnosis recorded, or with a non-device diagnosis
When the CSP submits a generic (non-swap) resolution
Then the flow behaves exactly as before this change — same states, same verification entry, no new mandatory step
REGRESSION_02 (G-B): Custody execution untouched
Given a valid swap reaching custody
Then all five custody guards still evaluate, the two-device transition is atomic, completion is emitted with both devices' state facts, and duplicate events remain idempotent — identical to pre-change behaviour
REGRESSION_03 (G-C): No connection/quality side-effects from a swap
Given a completed swap
Then the connection's lifecycle state is unchanged
And no event reaches connection-lifecycle, compensation, or quality systems from the swap itself
REGRESSION_04 (G-D): Quality signal unchanged
Given a complaint resolved after a swap and a complaint resolved without one
Then both emit the same resolution-signal structure with the same semantics — no new fields, no new events
REGRESSION_05 (G-E): Platform reclassification still evidence-gated
Given a CSP claiming router fault to transfer ownership to the platform
Then the evidence requirement and time bound apply exactly as before
And recording a device-fault diagnosis does not substitute for that evidence
REGRESSION_06 (G-F): Installation binding flow intact
Given a normal new installation (no swap involved)
Then device binding and deployment behave exactly as before the change
REGRESSION_07 (G-G): Verification model unforked
Given a complaint entering verification after a swap
Then it follows the same sequential verification model as any other resolution — no swap-specific verification branch exists
REGRESSION_08 (G-H): Timeout semantics preserved
Given the swap-completion window

REGRESSION_09 (G-I): Explicit unresolvable paths survive
