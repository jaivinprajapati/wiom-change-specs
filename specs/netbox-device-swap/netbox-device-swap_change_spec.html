Wiom · Change Spec · v0.3 · PM deliverable

CSP Netbox Swap — Diagnosis-Driven Device Replacement

Backend specification for the netbox swap flow inside SRS: a swap initiates on an open service ticket with a device-fault diagnosis, executes through ACS only after the old-app services (Remote, Inventory) confirm the connectivity shift, and completes without resolving the ticket — resolution and verification then proceed through the normal flow, verified by the common verification service. Scope is strictly swap-related; SRS fundamentals (ticket-creation gating, complaint lifecycle automatics) are a separate amendment and are not part of this spec. Per author directive, exact technical references (API paths, event names, field names, DB columns) are carried inline — a deliberate deviation from the template's default scope fence.

Author: Jaivin Prajapati  ·  Reviewer: Engineering  ·  Tier: Full

7-line triage. Filled last, after the body.
What is changing?
The built-but-unreachable netbox swap becomes a live backend flow: swap initiation carries the diagnosis fault type + resolution type; ACS executes only after Remote + Inventory services confirm; swap completion no longer resolves the ticket; guard G6 removed.
What triggered it?
Product decision: today's swaps run outside the OS with no verifiable record; the OS-governed flow exists in backend but has no diagnosis input path, so it can never execute — and even if it did, internet would not actually shift to the new device.
Blast radius
Swap initiation & guards (SRS), swap execution sequence (ACS — new pre-execution gate), post-swap ticket state (SRS), old-app boundary (Remote + Inventory services).
Reversible?
Feature: Yes — disabling swap initiation stops all swaps cleanly. An executed swap: No, by design — there is no un-swap; reversal is a second forward swap.

N / N / N.

A2. Why This Change WHAT

QuestionAnswer
What's wrong with the current behaviour?When a CSP/technician diagnoses a faulty netbox, there is no in-system way to swap it: the OS-governed swap flow exists in the backend but is unreachable (no path feeds it a diagnosis, so its entry guards can never pass). And even if it executed, custody records would change while actual internet delivery — driven by the old-app Remote and Inventory services — would not, leaving the customer offline with a "completed" swap.
Who experiences it?Customers with device-fault internet issues (no resolution, or a paper resolution with no internet); CSPs and technicians (no legitimate swap path); Wiom inventory & finance (swaps happen off-books and cannot be reconciled).
Cost of leaving it as-is?Every swap remains an unaudited device movement: unrecoverable devices, unreconcilable inventory, customer downtime, and a custody ledger that can drift from connectivity reality.

A3. Current Behaviour WHAT

Confirmed with author 2026-06-06 (re-scoped to swap-only in v0.2). Observable behaviour of the slice being changed. Technical references inline per author directive.
Trigger / conditionObservable behaviour today
CSP works a RESTORE task and concludes the device is faultyThere is no way to tell the system. The diagnosis fields exist on the task record (complaint_tasks.diagnosis_outcome, complaint_tasks.diagnosis_fault_type) but nothing feeds them — so the swap entry guards (G8 "diagnosis complete", G9 "device fault type") can never pass, and the swap flow is unreachable in practice.
A swap is submitted (POST /tasks/{taskId}/device-swap with old_device_id, new_device_id)SRS validates G6–G11 — including G6, a connection-state query to CL OS — and emits DEVICE_SWAP. ACS validates G1–G5 and immediately executes the atomic custody transition (old device DEPLOYED → RETRIEVAL_PENDING, new device CUSTODIED/IDLE → DEPLOYED), then emits DEVICE_SWAP_COMPLETED. No external system is consulted before execution.
The swap completesNothing informs the old-app stack (Remote service, Inventory service) — actual internet delivery does not shift to the new device. Custody says "swapped"; connectivity says otherwise. On receiving DEVICE_SWAP_COMPLETED, SRS records the swap on the complaint (complaints.device_swap_old_device_id, device_swap_new_device_id, device_swap_initiated_at, device_swap_completed_at, resolution_type = DEVICE_REPLACED) and auto-moves the complaint to PENDING_VERIFICATION — swap completion is treated as the resolution action itself.
Verification window runsVerification is SRS-internal today (telemetry check always inconclusive in v1; customer confirmation or timeout resolves; denial re-escalates). A common verification service — which will verify all service tickets in general, not just swaps — is being built in parallel and is not yet the verifier.
CSP attempts another swap on the same complaintAllowed for the time being — guards re-evaluate and a second swap proceeds if they pass. Nothing additional governs it.
Guard failure / no completionAny guard failure → rejection with reason (DEVICE_SWAP_REJECTED), complaint unchanged. No completion within 120 s (P_SWAP_COMPLETION_TIMEOUT) → ops flag, complaint stays open, late completion still processed.

A4. Desired Behaviour WHAT

Trigger / conditionDesired observable behaviour
CSP initiates a device swap on an open service ticketThe backend receives, in the swap-initiation request itself: the diagnosis fault type, the diagnosis outcome, the resolution type (DEVICE_REPLACED), and the replacement device. How the frontend collects these (journey, screens, ordering) is the frontend's decision — this spec only defines what the backend must receive. The backend persists the diagnosis onto the active task (complaint_tasks.diagnosis_outcome, diagnosis_fault_type) before evaluating guards.
Swap submission is validatedGuards G7–G11 evaluate (open complaint; diagnosis present; fault type ∈ {DEVICE_HARDWARE, DEVICE_SOFTWARE, DEVICE_CONNECTIVITY}; replacement device specified; resolution type = DEVICE_REPLACED). G6 is removed — no connection-state query is made; the custody binding guards (G4/G5 at ACS) are the protection.
ACS receives DEVICE_SWAPACS validates G1–G5 as today. Then — new gate — ACS calls the old-app Remote service and Inventory service and waits for their confirmation of the connectivity shift. Only after both confirm does ACS execute the atomic custody transition and emit DEVICE_SWAP_COMPLETED. If confirmation fails, the swap is nullified: zero state change anywhere, rejection surfaced to SRS/CSP with reason "ACS failed". (Exactly what Remote and Inventory must do is pending — PM to supply.)
The swap completesSRS records the swap on the complaint (same audit fields, now supporting multiple swaps per complaint) and updates the device mapping in SRS itself — from this moment, every further task, step, guard evaluation, or action on this ticket (and on the connection within SRS) considers the new device, never the old one. The ticket is NOT resolved and does NOT enter verification — it remains open in its current state (ASSIGNED/ESCALATED). Swap completion is a step inside the ticket, not its resolution.
After the swap, resolution proceedsThe CSP submits resolution through the normal, unchanged resolution flow. Verification is performed by the common verification service being built in parallel — the layer that verifies all service tickets in general. This spec defers entirely to it; no swap-specific verification exists.
Verification fails (customer denies) after a swapThe swap stands — no un-swap exists. The ticket re-escalates per the common verification model; the CSP may initiate another swap (unlimited, each fully guard-checked); the displaced device proceeds to return-to-Wiom (RETRIEVAL_PENDING tail, unchanged).
Ticket reopens after a swap (within reopen window)Same complaint lineage, no fresh SLA clock — and the reopened ticket runs against the new device, because the swap already updated the complaint's device facts when ACS confirmed.
Swap lifecycle boundariesA swap can only start after a service ticket exists and is actionable, and it ends before resolution begins. swap_reason is always FAULTY_DEVICE in v1; UPGRADE remains a declared placeholder.

A7. Rules, Invariants & Edge Cases Affected WHAT

A7.1 Rules & invariants (must always hold)

#Rule / invariantStatement
I1INV — complaint anchoringEvery swap initiation carries a complaint_id whose complaint is in ASSIGNED or ESCALATED at the moment of initiation. A swap without an open service ticket is structurally impossible.
I2INV — swap atomicityFor any swap attempt, either both devices transition (old → RETRIEVAL_PENDING and new → DEPLOYED) or neither does. At no instant are zero or two devices bound to the connection.
I3INV — single bindingA connection has at most one device bound to it at any moment — including during and after any number of repeat swaps.
I4INV — diagnosis gateNo swap emits unless the initiation request carried a fault type in {DEVICE_HARDWARE, DEVICE_SOFTWARE, DEVICE_CONNECTIVITY} and it was persisted onto the active task before guard evaluation. The latest persisted diagnosis governs.
I5INV — audit completenessEvery executed swap is recorded on its complaint with old device id, new device id, initiation and completion timestamps — every swap in the system is reconcilable from complaint records alone, including multiple swaps on one complaint.
I6INV — connectivity-before-custodyACS executes device custody transitions only after the Remote and Inventory services have confirmed the connectivity shift. A failed or absent confirmation leaves zero state change anywhere — custody never claims a swap that connectivity has not performed.
I7INV — resolution-type consistencyEvery swap initiation carries and every executed swap records resolution_type = DEVICE_REPLACED. No swap exists with a missing or different resolution type.
R1RULE — unlimited repeat swapsAny number of swaps may execute against one complaint; each attempt re-runs the full guard set including the old-app confirmation gate; no cap parameter exists in v1.
R2RULE — swap bounded in ticket lifecycleA swap starts only on an existing, actionable ticket and ends before resolution begins. Swap completion never resolves, closes, or advances the ticket's state.
R3RULE — duplicate-submission safetyWhile a swap is in flight (emitted, completion or rejection not yet received), a second initiation for the same task is rejected as "swap in progress". A duplicate delivery of an already-processed swap event produces no second transition (idempotent).

B5. Acceptance Criteria — Verification Layer HOW

Backend point of view, derived from required behaviour (A5/A7), not from existing code. Labelled Given/When/Then blocks across five classes; coverage audited in B5.1. SRS-fundamentals scenarios are out of scope.

Business logic

LOGIC_01 (D1 · happy): Swap proceeds without any connection-state query
Given an open ticket and a valid swap initiation
When SRS processes it
Then the swap emits without any connection-state lookup having occurred
And an unavailable connection-state source can never block or fail a swap initiation
LOGIC_02 (D2 · happy): Initiation carries and persists the diagnosis
Given a swap initiation carrying fault type DEVICE_HARDWARE, DEVICE_SOFTWARE, or DEVICE_CONNECTIVITY (each tested), an outcome, resolution type DEVICE_REPLACED, and a replacement device
When SRS processes the request
Then the diagnosis is persisted on the active task before any guard is evaluated
And the persisted values are retrievable with recording actor and time
LOGIC_03 (D2 · negative): Missing diagnosis fields reject the initiation
Given a swap initiation missing the fault type, or the resolution type, or the replacement device (each tested)
When SRS processes the request
Then it is rejected with the specific missing-field reason and no swap event is emitted
LOGIC_04 (D3 · happy): Completion leaves the ticket open
Given a ticket in ASSIGNED (and separately in ESCALATED) with a swap in flight
When the swap completes
Then the swap is recorded on the ticket and the ticket remains in exactly the state it was in
And it does not enter PENDING_VERIFICATION, RESOLVED, or any other state
And the SRS device mapping for the ticket now references the new device — every subsequent task, step, or action on the ticket considers the new device, never the old
LOGIC_05 (D3 · happy): Resolution flows normally after a swap
Given a ticket with a completed swap
When the CSP submits resolution through the normal resolution flow
Then the ticket enters verification exactly as any non-swap ticket would
And verification is performed by the common verification service with no swap-specific branch
LOGIC_06 (D4 · happy): Old-app confirmation precedes custody change
Given a swap that has passed ACS guards G1–G5
When the Remote and Inventory services both confirm the connectivity shift
Then and only then ACS executes the atomic transitions and emits completion
And the custody transition timestamps are never earlier than the confirmations
LOGIC_07 (D4 · negative): Failed confirmation nullifies the swap
Given a swap that has passed ACS guards G1–G5
When the Remote or Inventory confirmation fails
Then no custody state changes, no completion event is emitted, and nothing records the swap as executed
And the rejection reaches the CSP with reason "ACS failed", leaving the ticket unchanged and retry possible
LOGIC_08 (D5 · happy): Second swap on the same ticket
Given a ticket with one completed swap and a subsequent verification denial
When the CSP initiates a second swap with a new replacement and a fresh diagnosis
Then the second swap executes through the full guard set including the old-app gate
And both swaps are independently visible and ordered in the ticket's audit trail
LOGIC_09 (D6 · negative): Failed verification never reverses a swap
Given a completed swap on a ticket whose resolution is later denied in verification
Then both devices remain exactly in their post-swap states (new: serving the connection; old: pending return to Wiom)
And no reversal mechanism exists on any path
LOGIC_10 (D7 · negative): UPGRADE and wrong resolution types rejected
Given an initiation carrying swap reason UPGRADE, and separately one carrying a resolution type other than DEVICE_REPLACED
When SRS processes each
Then each is rejected as invalid for v1 and no swap event is emitted

Computation & calculation

COMPUTE_01 (completion window · normal): Completion within the window
Given a swap emitted at time T with a 120-second completion window
When completion (including the old-app round-trip) arrives at T + 119 s
Then the swap is recorded as completed and no ops flag is raised
COMPUTE_02 (completion window · boundary): Window expiry is exact and non-terminal
Given a swap emitted at time T with no completion received
When the clock reaches exactly T + 120 s
Then the ops flag is raised, the ticket remains open, and nothing auto-resolves
And a completion arriving at T + 121 s is still processed normally with the ops flag retained as advisory (E6)
COMPUTE_03 (reopen window · normal): Reopen inside the window references the new device
Given a ticket resolved after a swap at time R, with the reopen window configured
When the customer reports the same issue (same connection, class, subtype) before the window ends
Then it attaches to the original lineage with no fresh SLA clock
And the reopened ticket references the new device as the connection's device
COMPUTE_04 (reopen window · boundary): Reopen outside the window is independent
Given the same resolved ticket
When the same issue is reported just after the reopen window expires
Then a new, independent ticket is created with a fresh SLA clock — and it too references the new device
COMPUTE_05 (swap count · zero/unbounded): Audit under repeat swaps
Given one ticket that undergoes 0, 1, and N>2 swaps (each tested)
Then the number of reconstructible swap records on the ticket equals exactly the number of completed swaps
And rejected, nullified, and timed-out attempts are distinguishable from completed swaps

Invariants

INVARIANT_01 (I1): Complaint anchoring
Given any swap event ever emitted, under any path including repeats and races
Then its ticket was in ASSIGNED or ESCALATED at initiation time
And no path exists that emits a swap without an open service ticket
INVARIANT_02 (I2): Atomicity
Given any swap attempt, including one that fails mid-execution
Then either both device transitions are observable or neither is
And a partial outcome is never observable, even transiently to a concurrent reader
INVARIANT_03 (I3): Single binding
Given any connection at any moment — before, during, and after any number of swaps
Then at most one device is bound to it
And immediately after each completed swap exactly one device (the newest) is bound
INVARIANT_04 (I4): Diagnosis gate
Given every path that emits a swap, including direct API calls
Then the initiation carried a device fault type and it was persisted on the task before guard evaluation
And no emitted swap exists whose task lacks such a diagnosis at emission time
INVARIANT_05 (I5): Audit completeness
Given every completed swap in the system
Then the ticket record alone yields: old device id, new device id, initiated-at, completed-at, and the governing ticket
And a reconciliation run over tickets finds every device that left or entered DEPLOYED via swap
INVARIANT_06 (I6): Connectivity-before-custody
Given every custody transition executed by a swap, under all paths including retries and races
Then a Remote-service confirmation and an Inventory-service confirmation for that swap precede it
And a failed or absent confirmation coexists with zero custody change for that attempt — no path executes custody first
INVARIANT_07 (I7): Resolution-type consistency
Given every swap initiation accepted and every swap executed
Then resolution type DEVICE_REPLACED was received on initiation and is recorded on the ticket
And no completed swap exists with a missing or different resolution type

Use & edge cases

EDGE_01 (E1): Swap on a connection with no matching binding
Given a connection whose device binding has been cleared (e.g., deactivation in progress)
When a swap is initiated for it
Then initiation passes (no G6) but custody rejects on the binding guards before the old-app gate is called
And the CSP receives the binding-specific rejection and no device or old-app state changes
EDGE_02 (E5): Chained swap custody states
Given a ticket with swap #1 completed (device A out, device B in)
When swap #2 completes (device B out, device C in)
Then A and B are both pending return to Wiom, C is serving the connection
And the audit trail orders both swaps unambiguously
EDGE_03 (E7): Non-device fault type
Given an initiation carrying a fault type outside the 3 device types
When SRS processes it
Then the diagnosis is persisted on the task (truthful information) but the swap is rejected on the fault-type guard
And no swap event is emitted
EDGE_04 (E8): Invalid replacement device
Given a replacement device that is (a) owned by a different CSP, or (b) in a non-eligible custody state (each tested)
When the swap reaches custody validation
Then it is rejected with the specific guard reason, the old-app services are never called, and no state changes
And the CSP can immediately retry with a different device on the same ticket
EDGE_05 (E9): Ticket becomes non-actionable before initiation
Given a ticket that leaves ASSIGNED/ESCALATED (platform takeover or explicit closure)
When a swap initiation lands for it
Then it is rejected on the open-ticket guard and no swap event is emitted
EDGE_06 (E10): Re-initiation with a different fault type
Given a task whose last initiation carried DEVICE_HARDWARE, followed by a new initiation carrying a non-device fault
When the new initiation is processed
Then the latest persisted diagnosis governs and the swap is rejected
And a further initiation carrying a device fault succeeds normally
EDGE_07 (E12 / R3): Duplicate initiation
Given a swap in flight (emitted, neither completion nor rejection received)
When the same task initiates again
Then the second initiation is rejected as swap-in-progress
And a duplicate delivery of the same swap event to custody produces no second transition (idempotent)
EDGE_08 (E13 / R2): Resolution during an in-flight swap
Given a ticket with a swap in flight
When a resolution submission lands for the same ticket
Then it is blocked until the swap completes or is rejected — swap ends before resolution begins
EDGE_09 (E3+E4 chain): Deny-then-reopen sequence
Given a completed swap, then resolution, then customer denial, then a reopen within the window
Then at every step the ticket lineage is single and continuous
And every post-swap interaction references the new device, never the displaced one
EDGE_10 (E2 — partially pending): Old-app confirmation failure detail
Given the nullify-on-failure outcome is verified in LOGIC_07
Then partial-failure semantics (one of the two services confirms, the other fails or times out) are [TBD with Rahul Nijhawan — define with the D4 contract before build; this block intentionally not counted as covered]

Regression

REGRESSION_01 (G-A): Non-swap resolutions unaffected
Given a RESTORE task that never initiates a swap
When the CSP submits a normal resolution
Then the flow behaves exactly as before this change — same states, same verification entry, and no diagnosis is required anywhere
REGRESSION_02 (G-B): Custody mechanics untouched around the new gate
Given a valid swap reaching custody
Then all five custody guards still evaluate first, the two-device transition remains atomic, the completion event carries both devices' state facts, and duplicate events remain idempotent — identical to pre-change behaviour with only the confirmation step inserted between validation and execution
REGRESSION_03 (G-C): No connection/quality side-effects from a swap
Given a completed swap
Then the connection's lifecycle state is unchanged
And no event reaches connection-lifecycle, compensation, or quality systems from the swap itself
REGRESSION_04 (G-D): Quality signal unchanged
Given a ticket resolved after a swap and a ticket resolved without one
Then both emit the same resolution-signal structure with the same semantics — no new fields, no new events
REGRESSION_05 (G-E): Platform reclassification still evidence-gated
Given a CSP claiming router fault to transfer ownership to the platform
Then the evidence requirement and time bound apply exactly as before
And a diagnosis supplied with a swap initiation does not substitute for that evidence
REGRESSION_06 (G-F): Installation binding flow intact
Given a normal new installation (no swap involved)
Then device binding and deployment behave exactly as before the change
And the old-app confirmation gate applies only to swaps, never to installations
REGRESSION_07 (G-G): Verification model unforked
Given a ticket entering verification after a swap
Then it follows the same model as any other ticket under the common verification service — no swap-specific verification branch, state, or event exists
REGRESSION_08 (G-H): Timeout semantics preserved
Given the swap-completion window, regardless of any recalibrated value
Then expiry still raises an ops flag, never auto-resolves, never closes the ticket, and late completions are still processed — identical semantics to pre-change behaviour
