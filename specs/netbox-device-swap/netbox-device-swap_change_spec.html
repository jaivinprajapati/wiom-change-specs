Wiom · Change Spec · v0.8 · PM deliverable

CSP Netbox Swap — Diagnosis-Driven Device Replacement

Backend specification for the netbox swap flow. A swap initiates on an open service ticket with a device-fault diagnosis; once gate checks pass, ACS owns the swap end-to-end — a provisional swap via the Remote API, verification by the common Validation Layer (new device up + old device down), then the final custody commit on confirmation (or a reversal if not), with a dedicated swap-log and swap state machine. A committed swap tells SRS to close the ticket; the ticket is locked while a swap is in progress. Scope is strictly swap-related; SRS fundamentals (ticket-creation gating, complaint lifecycle automatics) are a separate amendment and are not part of this spec. Per author directive, exact technical references (API paths, event names, field names, DB columns) are carried inline — a deliberate deviation from the template's default scope fence.

Author: Jaivin Prajapati  ·  Reviewer: Engineering  ·  Tier: Full

What is changing?
A net-new swap flow owned by ACS: after gate checks, ACS does a provisional swap via the Remote API, calls the common Validation Layer (new device up + old device down), and only on CONFIRMED commits the final custody change and tells SRS to close the ticket; an unconfirmed swap is reversed. ACS adds a swap-log table and a swap state machine; the ticket is locked while a swap is in progress; guard G6 removed.
What triggered it?
Product decision: today's swaps run outside the OS with no verifiable record; the OS-governed flow is unreachable (no diagnosis path) and, even if it ran, internet would not actually shift to the new device.
Blast radius
Swap initiation & guards (SRS), the provisional shift + reversal via the Remote API (Remote/Inventory), swap verification (common Validation Layer), the whole swap orchestration + custody commit + swap-log + state machine (ACS), ticket closure & lock (SRS).
Reversible?
Feature: Yes — disabling swap initiation stops all swaps cleanly. A committed swap: No un-swap. A pre-commit (provisional) swap: reversed via the Remote API on a non-confirmation.

A2. Why This Change WHAT

QuestionAnswer
What's wrong with the current behaviour?When a CSP/technician diagnoses a faulty netbox, there is no in-system way to swap it: the OS-governed swap flow exists in the backend but is unreachable (no path feeds it a diagnosis, so its entry guards can never pass). And even if it executed, custody records would change while actual internet delivery — driven by the old-app Remote and Inventory services — would not, leaving the customer offline with a "completed" swap.
Who experiences it?Customers with device-fault internet issues (no resolution, or a paper resolution with no internet); CSPs and technicians (no legitimate swap path); Wiom inventory & finance (swaps happen off-books and cannot be reconciled).
Cost of leaving it as-is?Every swap remains an unaudited device movement: unrecoverable devices, unreconcilable inventory, customer downtime, and a custody ledger that can drift from connectivity reality.

A3. Current Behaviour WHAT

Confirmed with author 2026-06-06 (re-scoped to swap-only in v0.2). Observable behaviour of the slice being changed. Technical references inline per author directive.
Trigger / conditionObservable behaviour today
CSP works a RESTORE task and concludes the device is faultyThere is no way to tell the system. The diagnosis fields exist on the task record (complaint_tasks.diagnosis_outcome, complaint_tasks.diagnosis_fault_type) but nothing feeds them — so the swap entry guards (G8 "diagnosis complete", G9 "device fault type") can never pass, and the swap flow is unreachable in practice.
A swap is submitted (POST /tasks/{taskId}/device-swap with old_device_id, new_device_id)SRS validates G6–G11 — including G6, a connection-state query to CL OS — and emits DEVICE_SWAP. ACS validates G1–G5 and immediately executes the atomic custody transition (old device DEPLOYED → RETRIEVAL_PENDING, new device CUSTODIED/IDLE → DEPLOYED), then emits DEVICE_SWAP_COMPLETED. No external system is consulted before execution.
The swap completesNothing informs the old-app stack (Remote service, Inventory service) — actual internet delivery does not shift to the new device. Custody says "swapped"; connectivity says otherwise. On receiving DEVICE_SWAP_COMPLETED, SRS records the swap on the complaint (complaints.device_swap_old_device_id, device_swap_new_device_id, device_swap_initiated_at, device_swap_completed_at, resolution_type = DEVICE_REPLACED) and auto-moves the complaint to PENDING_VERIFICATION — swap completion is treated as the resolution action itself.
Verification window runsVerification is SRS-internal today (telemetry check always inconclusive in v1; customer confirmation or timeout resolves; denial re-escalates). A common verification service — which will verify all service tickets in general, not just swaps — is being built in parallel and is not yet the verifier.
CSP attempts another swap on the same complaintAllowed for the time being — guards re-evaluate and a second swap proceeds if they pass. Nothing additional governs it.
Guard failure / no completionAny guard failure → rejection with reason (DEVICE_SWAP_REJECTED), complaint unchanged. No completion within 120 s (P_SWAP_COMPLETION_TIMEOUT) → ops flag, complaint stays open, late completion still processed.

A4. Desired Behaviour WHAT

Trigger / conditionDesired observable behaviour
CSP initiates a device swap on an open service ticketThe backend receives, in the initiation request: diagnosis fault type, diagnosis outcome, resolution type (DEVICE_REPLACED), replacement device. SRS persists the diagnosis on the active task before evaluating its guards. The frontend journey is the frontend's decision.
Gate checks runSRS validates its guards G7–G11 (open complaint; diagnosis present; device fault type; replacement specified; resolution type). G6 removed — no connection-state query. SRS emits DEVICE_SWAP; ACS validates its guards G1–G5 (old device DEPLOYED & bound to this connection; new device CUSTODIED/IDLE; same CSP). Any failure → CSP shown the reason; nothing changes.
All gates pass → ACS owns the swapOnce all gate checks pass (G1–G5 at ACS, G7–G11 at SRS), the swap is fully handed to ACS. ACS runs it end-to-end: provisional swap → validation → commit → close. The ticket is locked the moment the swap begins.
ACS performs a provisional swapACS calls the old-app Remote API to perform a provisional connectivity swap onto the new device. Provisional = the network is shifted but custody is not yet changed, so it can be cleanly rolled back. (Exact Remote/Inventory contract: TBD with Rahul Nijhawan.)
ACS validates the swap really happenedACS calls the Validation Layer (VL) — the common verification layer. For a swap, VL confirms via router pings: the new device pinged ≥1 in the last 10 min AND the old device is no longer pinging; on a failed check it waits 5 min and re-checks, up to 2 retries (~10 min). Outcome: CONFIRMED / DECLINED / NO_DATA. The CSP sees a synchronous "verifying…" countdown.
VL = CONFIRMED → ACS commits the final swapACS executes the atomic custody transition (old device DEPLOYED → RETRIEVAL_PENDING, new device CUSTODIED/IDLE → DEPLOYED), making the provisional swap final, emits DEVICE_SWAP_COMPLETED, and informs SRS to close the ticket. SRS updates its device mapping to the new device and closes — a confirmed swap is the resolution.
VL = DECLINED or NO_DATA → ACS reversesACS reverses the provisional swap by re-calling the Remote API to restore the pre-swap state. Custody was never committed, so nothing to undo there. The ticket is unlocked and stays open; the outcome is logged; the CSP is shown: "We couldn't verify the swap. If you've found another problem, fix it and retry; otherwise swap the devices back (old → customer, new → CSP)." If the reverse call itself fails → ops escalation.
Throughout — the ticket is lockedWhile a swap is in progress (from hand-off to ACS until it commits or reverses), the SRS ticket accepts no resolution and no other action — the CSP cannot resolve, reclassify, or otherwise act on it. The lock releases when the swap reaches a terminal state (committed → ticket closed; reversed → ticket reopened for retry).
Audit & lifecycleACS keeps a dedicated swap log recording every attempt from provisional through final or reversal/failure, and runs a dedicated swap state machine governing those transitions. Every swap is reconcilable from the swap log alone.
Reopen after a confirmed+closed swapWithin the reopen window → same lineage, no fresh SLA clock, runs against the new device. swap_reason is always FAULTY_DEVICE in v1; UPGRADE remains a placeholder.

A6. Must-Not-Change — Regression Guard GUARD

#Adjacent behaviour that must not changeWhy it's in the blast radius
G-ANon-swap resolutions on a RESTORE task behave exactly as before — same states, same flow into verification. Diagnosis is not mandatory for them.D2 adds diagnosis to the swap path only; it must not gate other resolutions.
G-BThe atomic custody transition itself (old → RETRIEVAL_PENDING, new → DEPLOYED), guards G1–G5, the DEVICE_SWAP_COMPLETED payload, and event idempotency are unchanged. ACS now does more around it (provisional, VL, log, state machine), but the commit itself is byte-identical.Wrapping the commit in orchestration could tempt a behaviour change in the transition — forbidden.
G-CA swap never changes connection state and emits no signal to CL OS, Compensation OS, or Quality OS by itself.D1 removes the only CL interaction; nothing must replace it.
G-DCOMPLAINT_RESOLUTION_SIGNAL to Quality OS keeps its schema and semantics. A swap-closed ticket emits the same signal as any other closure.D7 makes a swap auto-close the ticket; the closure signal must stay byte-identical.
G-EReclassification-to-platform (router fault, system-verifiable evidence, time-bounded) unchanged.Sibling device-fault path; the swap diagnosis must not substitute for its evidence.
G-FNormal installation binding (CUSTODIED → DEPLOYED) unchanged. The provisional swap, VL gate, reversal, swap-log, and swap state machine apply only to swaps.Shares the custody machine; the new machinery must not leak into installs.
G-GVerification is the common verification layer's responsibility. This change feeds it swap-specific inputs (the ping rules) but does not fork it into a separate swap-only verifier.D5 routes swaps through the common layer; a parallel verifier would split the verification truth.
G-HSwap-completion timeout semantics: ops flag on expiry, ticket not auto-resolved on timeout, late completion still processed.D4/D5 lengthen the path (provisional + ~10-min VL window); the timeout value changes (B3) but its semantics must survive.

A7. Rules, Invariants & Edge Cases Affected WHAT

A7.1 Rules & invariants (must always hold)

#Rule / invariantStatement
I1INV — complaint anchoringEvery swap carries a complaint_id whose complaint is in ASSIGNED or ESCALATED at initiation. A swap without an open ticket is structurally impossible.
I2INV — custody atomicityWhen ACS commits, either both devices transition (old → RETRIEVAL_PENDING and new → DEPLOYED) or neither does. No partial custody outcome is ever observable.
I3INV — single bindingA connection has at most one device bound to it at any moment, including across repeat swaps. After a committed swap, exactly the new device is bound.
I4INV — diagnosis gateNo swap proceeds unless the initiation carried a device fault type {DEVICE_HARDWARE, DEVICE_SOFTWARE, DEVICE_CONNECTIVITY}, persisted before guard evaluation. Latest diagnosis governs.
I5INV — provisional-before-finalACS performs the Remote provisional swap before it commits custody. Custody is committed only after a provisional swap exists and VL = CONFIRMED.
I6INV — verify-before-commitACS commits custody only after VL = CONFIRMED. DECLINED or NO_DATA coexists with zero custody change and a reversal of the provisional swap — custody never claims a swap the network did not perform.
I7INV — resolution-type consistencyEvery swap carries, and every committed swap records, resolution_type = DEVICE_REPLACED. No committed swap has a missing or different resolution type.
I8INV — no false closureA swap closes the ticket only on VL = CONFIRMED + custody commit. DECLINED and NO_DATA never close the ticket — they reverse and reopen it.
I9INV — ticket lockWhile a swap is in progress (between hand-off to ACS and a terminal swap state), the ticket accepts no resolution or other mutating action. The lock releases only on COMMITTED (close) or REVERSED (reopen).
I10INV — swap-log completenessEvery swap attempt has a swap-log record carrying its lifecycle from provisional to a terminal state (COMMITTED / REVERSED / REVERSAL_FAILED / ABORTED). No swap acts on the Remote API or custody without a log trail.
R1RULE — unlimited repeat swapsAny number of swaps may run against one ticket; each re-runs the full flow and is a new swap-log record. No cap in v1.
R2RULE — swap-as-closureA VL-confirmed, committed swap closes the ticket. There is no separate resolution submission for a swap-resolved ticket.
R3RULE — duplicate-submission safetyWhile a swap is in progress, a second initiation for the same task is rejected. A duplicate of an already-processed custody commit produces no second transition (idempotent).
R4RULE — no un-swap of a committed swapOnce a swap is committed and the ticket closed, custody is never reversed. Any later need is a fresh forward swap on a reopened ticket.

Exact validation check (D5)

Let T₀ = the moment ACS calls VL (immediately after the provisional swap). At an evaluation time t, over the trailing 10-minute window (t − 10 min, t]:
· new_up(t) = the new device has ≥ 1 ping in that window.
· old_down(t) = the old device has 0 pings in that window.
· CONFIRM(t) = new_up(t) AND old_down(t).

Schedule — at most 3 evaluations, each failure followed by a 5-minute wait:
· Eval 1 at t = T₀.
· If not CONFIRM → wait 5 min → Eval 2 at t = T₀ + 5 min.
· If not CONFIRM → wait 5 min → Eval 3 at t = T₀ + 10 min.

Verdict:
· CONFIRMED — the first eval where CONFIRM(t) is true (early-exit).
· DECLINED — false at all 3 evals, with usable ping data present.
· NO_DATA — no usable ping data for the device(s) across the window.

Max time to verdict = ~10 min. Both DECLINED and NO_DATA → reverse (fail-closed). Eval 1 at T₀ catches the fast path where the fault had already killed the old device (instant CONFIRMED).

F. Future Scope — Noted, Not Specced Out of scope for this version

Items intentionally parked. Recorded so the intent isn't lost, but explicitly not part of this build. Each needs its own spec (and, where flagged, its own cross-OS amendments) before it can be picked up.

F1. Closing a Pickup Ticket (PUT) by swapping a device

AspectDetail
Today's scopeThis spec enables a swap only when the customer has raised a service ticket. The swap lives inside that complaint's lifecycle.
The gap / scenarioFrustrated customers often raise a Pickup Ticket (PUT) — they want to leave Wiom and return the device. The CSP visits, diagnoses on site, and convinces the customer to stay on the condition that a new device is provided. Today a PUT can only close by the customer recharging or by the device being picked up — neither reflects a save-via-swap.
The proposalIntroduce swapping as a third PUT-closure path, alongside recharge and pickup. A PUT would close as "retained via device replacement", old device routes to return-to-Wiom, new device binds to the connection.
Why deferredMaterially larger: it changes how a PUT terminates, rippling across Exit OS (PUT lifecycle), CL OS (a connection saved from exit), Asset Custody OS (swap from a non-complaint context), and SR OS. It also breaks invariant I1 ("every swap carries an open complaint_id"). Its own initiative.
StatusNoted only. Separate change spec when prioritised.

F2. Device locking / concurrency between gate-check and commit

AspectDetail
The gapGate checks (G1–G5) run at initiation, but ACS commits custody up to ~10 min later (after the VL window). In that gap a device's state could change underneath the swap. Note: the ticket is locked (I9), but the two devices are not exclusively reserved.
Why deferredJudged too small an edge for this effort; a full fix needs reservation/lock checks across multiple OSes and services. Accepted as a known limitation for v1 — ACS re-reads device state at commit, but holds no device lock.
StatusNoted only. Revisit if it shows up in practice.

F3. Validation beyond a ping (true service check)

AspectDetail
The gapv1 treats a router ping as proof of internet. A device can ping while the customer still has no usable service (auth/plan/throughput).
Why deferredDeeper checks (session/auth/throughput) are a future VL enhancement. For v1, ping = internet, with the swap-log validation outcome available to spot patterns that justify adding layers.
StatusNoted only. Future VL enhancement.
