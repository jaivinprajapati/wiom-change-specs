Device Order Eligibility — Engine Changes

A modification to the existing CSP device-ordering eligibility engine (the "provisioning engine" in Asset Custody OS, reading from Payment, Capacity, Enforcement and Quality OS). This change corrects the At-Risk quality multiplier, simplifies and re-parameterises the security-deposit ceiling, adds two new custody gates (absolute cap, free-stock-on-hand), introduces a security-deposit top-up soft-blocker, makes the engine return a priority-ranked block reason, and reuses the same gates to answer connection eligibility. Business behaviour only — engineering owns implementation.

Author: Jaivin Prajapati (PM)  ·  Reviewer: Engineering (ACS / Payment)  ·  Tier: Full
Tier: Full — touches multiple gates, a money flow (wallet→SD top-up), new parameters, and the connection-eligibility surface.
Baseline: Business behaviour doc "Device Order — How We Decide" (Device_Order_Eligibility.html), already updated for the capacity / enforcement / new-gate framing this spec implements.

A2. Why This Change WHAT

QuestionAnswer
What's wrong with the current behaviour?(1) An At-Risk CSP is granted half their entitlement instead of zero — quality enforcement is being under-applied. (2) The SD-backed device ceiling uses a two-parameter "₹2,000 → 10 devices" step that is opaque and carries hard-coded code defaults, defeating the point of having parameters. (3) There is no absolute ceiling on how many devices one CSP can hold, no guard against CSPs ordering when they already have idle stock, no top-up path when only the deposit is short, and no priority when multiple gates fail. (4) Connection eligibility is not surfaced, even though it is decidable from gates the engine already computes.
Who experiences it?CSPs (wrong device entitlements, no recovery path when only deposit-short, no clarity on why they're blocked); Wiom ops & finance (over-exposure risk, idle stock shipped, quality not biting); the CSP app "New Work" flow.
Cost of leaving it as-is?Quality lever is half-strength; capital tied up in idle/over-allocated devices; CSPs blocked with no actionable next step; connection demand and device supply decided inconsistently.

A3. Current Behaviour WHAT

Scope: the eligibility read that runs when a CSP opens the ordering surface. The order create and approve steps are out of scope and unchanged.
Trigger / conditionObservable behaviour today
CSP requests eligibilityThe engine runs gates in this order and stops at the first failure: prior-receipt → SD floor → enforcement → quality(non-compliant only) → "smallest ceiling minus held ≤ 0". It returns a single max orderable quantity and the tier options {5,10,20}.
CSP quality is AT_RISKThe quality gate only hard-blocks NON_COMPLIANT. AT_RISK passes the gate and is then multiplied by 0.5×, so the CSP is granted roughly half their structural entitlement. The block reason, if zeroed, reads as a generic "ceiling zero", not a quality reason.
SD-backed ceilingComputed in Payment as 75 + floor((balance − ₹20,000) / ₹2,000) × 10, using two parameters (₹2,000 increment, 10 devices/step). The floor (₹20,000), the 75 allocation, and the increment pair all carry hard-coded Java defaults.
CSP holds many devices / has idle stockNo absolute ceiling on total holdings. No check on ready-to-deploy stock the CSP already has; the engine will offer more even if the CSP is sitting on idle devices.
SD covers fewer devices than the CSP wants, all else fineNo top-up path. The CSP simply sees a smaller orderable number; there is no prompt to add deposit and no recomputation.
Multiple gates failThe first gate in code order wins; the reason is not ranked by business criticality.
Can this CSP take new connections?Not answered by this engine; there is no connection-eligibility verdict on the ordering surface.

A4. Desired Behaviour WHAT

Trigger / conditionDesired observable behaviour
CSP requests eligibilityThe engine evaluates all gates, then returns: a device-order verdict (eligible quantity A + orderable quantity B, or a single highest-priority block reason), a separate connection verdict, and — when applicable — a soft-blocker payload with the exact top-up amount.
CSP quality is AT_RISK or NON_COMPLIANTBoth are treated as a quality block (multiplier 0×), and the returned reason is a Quality reason — the highest-priority one. Only COMPLIANT proceeds.
SD-backed ceilingComputed as 75 + (balance − sd_floor) / per_device_deposit using a single per-device parameter. All inputs (floor, 75, per-device) come from Parameter Store with no code defaults.
CSP at the absolute capIf current holdings ≥ 3,000, the order is blocked with an "absolute cap exhausted" reason.
CSP already has ready-to-deploy stockIf count of devices in IDLE + CUSTODIED + PENDING_CSP_RECEIPT is ≥ 5, the order is blocked with a "sufficient stock on hand" reason. The CSP is told they're eligible but don't need more yet.
SD is the only binding constraint, all else passesInstead of just a smaller number, the CSP is shown a top-up amount = (orderable quantity − devices the current SD covers) × per-device deposit. They transfer wallet→SD; the front end re-requests eligibility; the order then clears at the orderable quantity.
Multiple gates failThe CSP sees the single most critical reason: Quality → Enforcement → Capacity → SD floor → Absolute cap → Free devices → Prior receipt.
Can this CSP take new connections?The same response carries a connection verdict: eligible iff Quality COMPLIANT and capacity ceiling (Σ zone caps − held) > 0 and absolute cap not hit. A CSP may be connection-eligible while device-blocked.

A6. Must-Not-Change — Regression Guard GUARD

Adjacent behaviour that must not changeWhy it's in the blast radius
COMPLIANT quality continues to grant full (1×) entitlement.The quality multiplier switch is being edited; the compliant path must stay intact.
SD floor remains ₹20,000 and below-floor is still a hard reject.The SD formula and parameters are changing around it; the floor gate must not move.
SD ceiling output is numerically identical for existing balances (e.g. ₹30K → 125, ₹22K → 85).The formula is being "simplified"; it must produce the same numbers, not new ones.
Tier floor {5,10,20}, the 20-per-order cap, and the 1–4 dead-zone → 0 rule.The post-eligibility flooring is adjacent to the new gates and the soft-blocker.
"Currently held" continues to exclude RETURNED / LOST / DAMAGED / WRITTEN_OFF.New gates count device states; the existing held-count definition must not drift.
Existing prior-receipt (POD) gate still blocks a new order while a prior receipt is pending.It now also feeds the free-devices count; its own blocking behaviour must remain.
Order create / approve paths behave exactly as before.We are explicitly not adding enforcement there; no accidental coupling.
The wallet→security-deposit transfer API behaves exactly as today (amounts, atomicity, ledger).The soft-blocker reuses it; the transfer itself must be untouched.

A7. Rules, Invariants & Edge Cases Affected WHAT

A7.1 Rules & invariants (must always hold)

Rule / invariantStatement
RULE — quality gateA CSP whose quality state is AT_RISK or NON_COMPLIANT is granted exactly 0 devices, and the returned device-block reason is Quality.
RULE — SD ceiling continuityFor any balance ≥ ₹20,000, ceiling = 75 + ⌊(balance − ₹20,000) / ₹200⌋, with no discontinuity at the floor.
RULE — absolute capNo eligibility result may permit total holdings to be ≥ absolute_custody_cap; at held ≥ 3,000 the order is blocked.
RULE — free-stock guardIf IDLE + CUSTODIED + PENDING_CSP_RECEIPT ≥ free_device_threshold, no device order is offered.
RULE — top-up amounttop_up_amount = (orderable_qty − devices_SD_covers_free) × per_device_deposit, never negative, and never asks for more than the orderable quantity (≤ 20) requires.
RULE — reason priorityWhen ≥ 2 gates fail, the single returned reason is the highest in: Quality > Enforcement > Capacity > SD floor > Absolute cap > Free devices > Prior receipt.
INV — single device verdictA device-eligibility response is exactly one of: eligible (with A, B), soft-blocked (with top-up payload), or hard-blocked (with one reason) — never more than one.
INV — A/B orderingA (total eligible) ≥ B (orderable), and B ∈ {0,5,10,20}.
INV — connection ⊇ device gatesIf a CSP is device-eligible, they are connection-eligible (device eligibility implies the connection subset passes). The converse need not hold.
INV — no front-end calculationEvery dynamic number shown (A, B, top-up amount, devices covered) is computed by the backend; the front end performs no arithmetic.

LOGIC_03 (business logic · negative): Non-compliant earns zero
Given a NON_COMPLIANT CSP

LOGIC_04 (business logic · negative): Free-stock guard
Given a CSP with 6 devices across IDLE + CUSTODIED + PENDING_CSP_RECEIPT
When eligibility is requested
Then device verdict blocked with reason = Free devices
And the connection verdict is still evaluated independently
LOGIC_05 (business logic · happy): Connection-eligible while device-blocked
Given a COMPLIANT CSP with capacity room and held < cap, but SD below floor

COMPUTE_01 (computation · normal): SD ceiling parity
Given balance ₹30,000
Then sd_ceiling = 75 + (30,000 − 20,000)/200 = 125 (identical to the old formula)
COMPUTE_02 (computation · boundary): Exactly at floor
Given balance exactly ₹20,000
Then sd_ceiling = 75 (no discontinuity, the 75 allocation is granted)
And balance ₹19,999.99 is below floor → hard reject
COMPUTE_03 (computation · boundary): Top-up amount
Given balance ₹20,000 (covers 75), held 70, orderable B = 20
Then devices_SD_covers_free = 5 and top_up_amount = (20 − 5) × ₹200 = ₹3,000
And after a ₹3,000 transfer, re-request yields sd_ceiling 90, free 20, B = 20, no soft-blocker
COMPUTE_04 (computation · boundary): Free-device threshold off-by-one
Given free devices = 4 → not blocked; = 5 → blocked; = 6 → blocked
Then the threshold is "≥ 5"
COMPUTE_05 (computation · boundary): Absolute cap off-by-one
Given held = 2,999 → not blocked by cap; held = 3,000 → blocked "absolute cap exhausted"
Then the cap is "≥ 3,000"
COMPUTE_06 (computation · zero / config): Tier dead-zone & per-order cap unchanged
Given eligibility = 3 → B = 0; eligibility = 60 → B = 20

COMPUTE_07 (computation · config extreme): Parameter absence fails fast
Given per_device_deposit / floor / cap / threshold absent from Parameter Store
Then the service does not serve eligibility with a guessed default

INVARIANT_02 (from A7.1): A ≥ B and B ∈ {0,5,10,20}
