Device / NetBox Custody — State Machine & Scenario Gaps

v2 · 2026-06-29 csp-os-yaml @ prod Current machine = live code Target = + the 3 specs + scenario gaps

1Objective

Lay out the device custody state machine as it runs today, then diff it against the full scenario space — every real-world thing that can happen to a device — to surface the transitions the machine cannot express yet. This is about completeness of system thinking, not implementation defects.

2Approach

The current machine is read straight from the live custody service. The target machine overlays (a) the states/transitions from the three change specs and (b) the scenario gaps below. Gaps are drawn on the machine so they are visible at a glance: red dashed = missing transition, amber = needs modification, blue dotted = spec-only (future) state/edge.

What changed from v1 (owning a miss): v1 hunted for unwired/broken code — so it missed transitions the code never had but the business needs (CRP→DEPLOYED, LOST→DEPLOYED), and it parked the spec machine in a footnote. v2 is driven from scenarios per state and diffs against the shared spec machine. It also drops implementation-bug observations (per review scope) and corrects the exposure claim — see Notes.

5The scenario gaps

GAP-1 · modify DEPLOYED → CRP

Device state follows the connection (CSP ISP expiry), not the customer's plan cycle

ScenarioA paying customer is still in their plan cycle, but the CSP's own ISP/connection window lapses — and the device gets dragged toward recovery.
TodayThe DEPLOYED→recovery move is driven by the connection-lifecycle deactivation, anchored to the CSP/ISP window.
NeededCustody state should track the customer's plan cycle, so a live customer never has their device pulled because of a CSP-side expiry.
GAP-2 · missing CRP → DEPLOYED

Churned customer recharges and wants to continue — no path back to live

ScenarioCustomer in recovery (device still at their home) recharges and wants to keep using Wiom.
TodayCRP can only go to IDLE (after physical pickup) or LOST. To resume service the device must be picked up, go IDLE, then be re-installed.
NeededA direct rescue edge CRP→DEPLOYED (the spec's T_REC_6) so a recharge simply restores service in place — no pickup, no re-install, no re-pay.
GAP-3 · missing LOST → DEPLOYED

A lost device turns up and is put back into service

ScenarioA device marked LOST is later found / recovered and a customer is (or stays) live on it.
TodayLOST's only edge is WRITTEN_OFF. There is no way to bring a recovered device back to DEPLOYED.
NeededA recovery edge LOST→DEPLOYED (and/or LOST→IDLE) so a found device re-enters the active fleet instead of being forced to write-off.
GAP-4 · missing PUT layer

No way to cancel a PUT without recharging again

ScenarioCustomer raised a PUT while their plan was still active (e.g. a service issue), then wants to continue.
TodayThe only way to clear a PUT is to recharge again — there's no "cancel the PUT, I'm staying" option.
NeededLet a customer withdraw an open PUT and stay live without paying twice. Pairs with G2 — both are the "I want to continue" exit.
GAP-5 · missing any → IDLE / CUSTODIED

CSP has a device and wants to keep it free — no provision

ScenarioA CSP ends up holding a device (from any state) and wants to retain it as free stock rather than return it.
TodayThere is no clean "keep it" route; idle stock only arises via the churn→recovery path.
NeededA verified retention path into IDLE/CUSTODIED (proof/verification gated) so a CSP can legitimately keep a device free.

6Notes & corrections

Exposure (correction). v1 wrongly stated "no CSP exposure exists." A CSP exposure table does exist in the payment-settlement DB. In code, the exposure concept that's visible is csp_zone_exposures (demand-allocation — capacity/eligibility bands per CSP×zone), which is a different axis from device liability. The open question for a later pass: is custody-driven device exposure kept in step with that table.

Scope. Implementation-level defects (settlement amounts, broken handlers, double-writes) are intentionally out of this doc — it is a system-design / scenario-completeness review. Money is called out only where a scenario demands it (e.g. G2/G4: continuing must not force a re-payment).
