The blue fan into RETURNED is the warehouse "accept from any state" capability. The red fan into IDLE (Gap 4) is its CSP-claim counterpart — same shape, different trust model (below). Blue PENDING_CSP_RECEIPT / RECOVERY_HOLD / WIOM_INVENTORY are spec-only states.

Why IDLE is not the same as RETURNED — two ways out of active service, two trust models

RETURNED = Wiom physically holds the asset at the warehouse. It is self-verifying: nothing more to check, no further action.
IDLE = a CSP claims it holds the device. The claim must be verified, and moving to IDLE must also fire the cross-cutting actions the normal path would have done — close the open NBREC pickup task, deactivate the connection in CLOS, and so on. Example: a direct CRP→IDLE that skips the NBREC recovery-confirmation still has to close NBREC and deactivate the connection. That is what makes the IDLE accept-all (Gap 4) different from the RETURNED accept-all.

Already designed in your specs (blue) — not gaps

  • RETURNED from any state — warehouse accept-all (Wiom physically has the device).
  • CRP → DEPLOYED — customer recharged and continues (rescue). Connection side: recharge reactivates the connection.
  • CRP → RETRIEVAL_PENDING (CSP exits mid-recovery) and CRP → RETURNED (internal team returns it direct).
  • LOST → RECOVERY_HOLD → RETURNED — device recovered late, handed to warehouse.
  • RETURNED → WIOM_INVENTORY → PENDING_CSP_RECEIPT — re-dispatched to a new CSP.

Still open — no spec covers these

  • Gap 1 · state should follow the customer's plan cycle, not CSP ISP expiry (modify).
  • Gap 2 · LOST → DEPLOYED — customer recharged, continue on the same device.
  • Gap 3 · cancel a PUT without recharging again (PUT layer).
  • Gap 4 · move to IDLE from any active state on a verified CSP claim, firing the cross-cutting actions.

5The four open gaps

Gap 1 · modify DEPLOYED → CRP

Device state follows the connection (CSP ISP expiry), not the customer's plan cycle

ScenarioA paying customer is mid plan cycle, but the CSP's own ISP window lapses and the device is dragged toward recovery.
TodayThe move out of DEPLOYED is anchored to the connection/ISP deactivation, not to the customer.
NeededAnchor custody state to the customer's plan cycle so a live customer is never affected by a CSP-side expiry.
Gap 2 · missing LOST → DEPLOYED

Customer recharged on a device that was marked lost

ScenarioA device is marked LOST; the customer then recharges and wants to keep using it.
TodayLOST goes only to WRITTEN_OFF, or (per spec) to RETURNED via RECOVERY_HOLD — there is no way back to live.
NeededA LOST→DEPLOYED edge on a recharge, so the customer simply continues on the same device.
Gap 3 · missing PUT layer

No way to cancel a PUT without recharging again

ScenarioCustomer raised a PUT while their plan was still active (e.g. a service issue), then wants to continue.
TodayThe only way to clear a PUT is to recharge again — there is no "cancel the PUT, I'm staying" option.
NeededLet a customer withdraw an open PUT and stay live without paying twice.
Gap 4 · missing any active → IDLE

A CSP can claim it holds a device — verified, with cross-cutting actions

ScenarioA CSP says it has the device (from DEPLOYED, CRP, RETRIEVAL_PENDING, etc.) and wants it as free stock — the IDLE counterpart of the warehouse accept-all.
TodayIDLE is reachable only via the full CRP→IDLE recovery-confirmation; there is no general claim path from other states.
NeededAllow any active state (not LOST / DAMAGED / RETURNED) → IDLE on a verified claim, and fire the cross-cutting actions — close NBREC, deactivate the connection in CLOS, etc. Unlike RETURNED, the CSP claim is not self-verifying.

6Notes

Exposure. A CSP exposure table exists in the payment-settlement DB. (The exposure visible in code is csp_zone_exposures in demand-allocation — capacity/eligibility bands per CSP×zone, a different axis from device liability.) Open question: whether custody-driven device exposure is kept in step with it.

Scope. System-design / scenario-completeness review — implementation defects are out of scope. Money is raised only where a scenario demands it (e.g. Gap 3: continuing must not force a re-payment).
