0Read-this-first — the headline gaps

Five facts a reader should leave with. Each is proven below; this is the elevator version.

① A device lost in a CSP's custody is never actually charged.

Write-off computes a liability of ≥ ₹20,000 (device value + capped carry fee) CustodyStateServiceImpl.java:211 and emits ASSET_LIABILITY_SETTLED. The only consumer (Payment-Settlement) is called with depositApplied = 0L, residual = 0L hard-coded InboundEventProcessingServiceImpl.java:237-246 (PAY), so it writes a ₹0 DEPOSIT_FORFEITURE row and no liability row; the real amount is only logged DepositServiceImpl.java:197-220 (PAY). Compensation does not consume the event at all.

② A churned device can sit in recovery limbo forever.

CUSTOMER_RECOVERY_PENDING → LOST (the 30-day timeout, "T_REC_4") is a declared transition NetboxCustodyStateMachine.java:44-47 with no writer. The params recoveryMaxWindowSeconds/recoveryWindowSeconds exist AssetCustodyParameters.java:50-54 but are read by no Java code, and no batch trigger evaluates it BatchTriggerController.java:26-64. Exit is only forward (recovery confirmed → IDLE) or a manual ops loss declaration.

③ Carry fee is booked twice, two different ways, off one event.

One daily CUSTODY_CARRY_FEE_ACCRUED is consumed by both Compensation (entitlement ledger, flat −1×daily-rate, threshold-gated) CompensationEventProcessingServiceImpl.java:229-252 and Payment-Settlement (wallet ledger, amount = device count, no threshold) InboundEventProcessingServiceImpl.java:157-171 (PAY).

④ There is no CSP "exposure" accounting anywhere.

CSP_EXPOSURE_CHANGED / csp_exposure appears in zero files across all 18 services (repo-wide grep). The exposure invariants the specs assume (+1 at CUSTODIED, −1 at RETURNED/LOST) are not implemented in V1.

⑤ The "deactivate & return" CSP action is broken.

The wired endpoint CustodyStateController.java:59-67 calls deactivateAndReturn(), whose first step is DEPLOYED → IDLE CustodyStateServiceImpl.java:350 — an edge removed in v1.11. It throws InvalidTransitionException for every input.

1The 10 custody states

The custody enum has exactly 10 values CustodyStatus.java:3-14. (Note: stale internal docs/specs reference 12 — there is no PENDING_CSP_RECEIPT and no RECOVERY_HOLD in live code.) Terminal states are RETURNED, DAMAGED, WRITTEN_OFF NetboxCustodyStateMachine.java:63-67.

active / resting transient (pass-through) terminal
CUSTODIED
With CSP · never deployed
Fresh stock the CSP holds. Entry state on order-receipt and on allocation. Idle counter runs.
DEPLOYED
At a customer · live
Device installed and serving a customer. Idle counter paused/reset.
IDLE
With CSP · was deployed
Back with the CSP after a customer journey. Only reachable from CUSTOMER_RECOVERY_PENDING in V1 — DEPLOYED→IDLE was removed.
CUSTOMER_RECOVERY_PENDING
At ex-customer · pickup open
Customer deactivated (churn / disconnect); device still physically at the customer, awaiting recovery. Idle counter paused.
RETRIEVAL_PENDING
Returning to Wiom warehouse
CSP→Wiom handover in flight. The single gateway into all terminal outcomes. Idle counter paused.
REASSIGNED
Transient · changing CSP
Pass-through during CSP-to-CSP reallocation; immediately re-stamped to CUSTODIED under the new CSP in the same transaction.
RETURNED
Terminal · back at warehouse, OK
Physically handed over & functional. Triggers the only "happy" deposit credit.
DAMAGED
Terminal · back, damaged
QC classified it damaged during retrieval.
LOST
Soft-terminal · unrecovered
Declared lost or timed out of retrieval. Only onward edge is WRITTEN_OFF.
WRITTEN_OFF
Terminal · accounting close
Liability "settled" (computed; see Gap ①). Final.

Reachability fact worth noting: IDLE has exactly one inbound edge — CUSTOMER_RECOVERY_PENDING → IDLE. A device cannot become IDLE from DEPLOYED or CUSTODIED directly. So "idle stock that was once deployed" can only arise via the churn→recovery path.

So, "a device is lost in custody of a CSP — what are the repercussions?" (the worked example)

Ground sequence: customer churns → device sits in CUSTOMER_RECOVERY_PENDING → if recovered it goes IDLE (and the CSP earns a recovery payout); if not recovered it… stays there (Gap ②), because nothing times it out. The only way it advances is a CSP/ops manual loss declaration → LOST → 90-day sweep → WRITTEN_OFF.

Financial repercussion at write-off: ACS computes a liability of min(carryFeeUnits, 1000) + 20000 paise-equivalents CustodyStateServiceImpl.java:211 and announces it. But no ledger ever debits it — PAY forfeits ₹0 and books no liability row, COMP ignores the event. Net real-money impact on the CSP for losing a device today: the ₹200 return credit it doesn't get, plus any carry fee that accrued while idle. The headline ₹20,000 device liability is announced but not enforced.

5Device-order sub-machine (the on-ramp to CUSTODIED)

A separate 5-state machine governs how stock reaches a CSP DeviceOrderStateMachine.java:13-22. Its terminal FULFILLED is what mints CUSTODIED custody rows.

stateDiagram-v2
  direction LR
  [*] --> REQUESTED: CSP places order
  REQUESTED --> APPROVED: cap check passes (auto)
  REQUESTED --> REJECTED: cap exceeded
  APPROVED --> DISPATCHED: ops confirms dispatch
  DISPATCHED --> FULFILLED: CSP confirms receipt → mints CUSTODIED rows
  DISPATCHED --> REJECTED: 72h dispatch-confirm timeout
  REJECTED --> [*]
  FULFILLED --> [*]

What gates an order

Only two checks: (1) no other active order for the CSP, (2) device-count cap not exceeded DeviceOrderServiceImpl.java:43-102. There is no security-deposit / wallet-balance gate — see Gap ⑧.

What FULFILLED does

Loops quantityApproved times, minting a custody row per device with a random UUID as device_id DeviceOrderServiceImpl.java:153-175 → CUSTODIED. Real hardware identity arrives (if ever) via the separate NETBOX_ASSIGNMENT_SIGNAL path — see Gap ⑨.

6Carry-fee accrual engine

A daily batch CarryFeeAccrualServiceImpl.java:34-99 finds idle devices past the threshold, increments their accrual units, and emits one CUSTODY_CARRY_FEE_ACCRUED per CSP.

  • Eligibility: idle > idleThresholdDays = 30 AssetCustodyParameters.java:18, accrual capped at carryFeeHardCap = 1000 units AssetCustodyParameters.java:21.
  • Increment: +1 unit/device/day CarryFeeAccrualServiceImpl.java:62-63.
  • Event payload: totalAccrualUnits = the count of that CSP's devices that accrued this cycle (it sums +1 per device) CarryFeeAccrualServiceImpl.java:74 — not a per-device unit total. This is the number both consumers then (mis)use differently (Gap ③).
  • Rate param carryFeeRatePaise = 2000 (₹20/day) is declared in ACS AssetCustodyParameters.java:44-45 but the actual debit rate lives in the consumers, not here.
  • Idle counter is paused in DEPLOYED / RETRIEVAL_PENDING / CUSTOMER_RECOVERY_PENDING / terminal NetboxCustodyStateMachine.java:95-100 — so a churned-but-unrecovered device accrues nothing while it waits.

7Gaps in V1 (the point of this document)

Every gap below is a fact about the live code, not a recommendation. Severity is the author's read of blast radius. These are the seams where Jaivin's specific inputs will land next.

HIGHGAP-1

Customer-recovery devices have no automatic exit to LOST

The edge CUSTOMER_RECOVERY_PENDING → LOST ("T_REC_4: P_RECOVERY_MAX_WINDOW expired / T_REC_5: CSP reports irrecoverable") is declared valid NetboxCustodyStateMachine.java:44-47, and the windows are parameterised — recoveryWindowSeconds=604800 (7d), recoveryMaxWindowSeconds=2592000 (30d) AssetCustodyParameters.java:50-54. But both params are read by zero Java code, there is no batch trigger for recovery timeout BatchTriggerController.java:26-64, and the one LOST sweep only scans RETRIEVAL_PENDING CustodyStateServiceImpl.java:171-193. Cross-service trace confirms TAS does not drive it either.
Impact: a churned customer who never returns the device leaves it parked in CUSTOMER_RECOVERY_PENDING indefinitely — accruing no carry fee, never written off, never charged — unless an ops person manually declares loss. The "30-day auto-LOST" the design assumes does not exist.
HIGHGAP-2

Lost / written-off device liability is computed but never charged

Write-off sets totalLiability = min(carryFeeUnits, 1000) + 20000 CustodyStateServiceImpl.java:211 and emits ASSET_LIABILITY_SETTLED with it. PAY's handler is invoked with depositApplied=0L, residual=0L InboundEventProcessingServiceImpl.java:237-246 (PAY); downstream, appliedDebit = min(0, balance) = 0 → a ₹0 DEPOSIT_FORFEITURE row, and the residual-liability branch is skipped because residual is 0 DepositServiceImpl.java:200-224 (PAY). The real totalLiability is used only in a log line. COMP has no consumer for the event.
Impact: the central financial deterrent of the whole custody model — "lose Wiom's device, owe ₹20k" — is announced on the bus but lands nowhere. Same for damage/loss deposit claims via CUSTODY_CONDITION_CLASSIFIED (also passed 0L).
HIGHGAP-3

Carry fee is double-booked across two services, with different math

One CUSTODY_CARRY_FEE_ACCRUED is consumed by COMP → entitlement_ledger CARRY_FEE_DEBIT at a flat −1×daily-rate gated by a threshold CompensationEventProcessingServiceImpl.java:219-252, AND by PAY → wallet_ledger CARRY_FEE at −totalAccrualUnits with no threshold InboundEventProcessingServiceImpl.java:157-171 (PAY). Two ledgers, two amounts, two threshold semantics, one event.
Impact: the CSP's carry-fee charge is ambiguous and potentially counted twice; reconciliation between the wallet and the entitlement ledger cannot net to a single source of truth.
HIGHGAP-4

"Deactivate & return" endpoint throws on every call

deactivateAndReturn() first executes DEPLOYED → IDLE CustodyStateServiceImpl.java:350, an edge removed in v1.11 — so transition() raises InvalidTransitionException for any input state. The endpoint is live and permissioned CustodyStateController.java:59-67.
Impact: the single-call "deactivate a still-deployed device and start its return" flow is non-functional in prod. Callers must fall back to deactivation (via CL) then a separate initiate-return.
MEDGAP-5

No CSP "exposure" accounting exists at all

A repo-wide search for CSP_EXPOSURE_CHANGED / csp_exposure / cspExposure returns zero files across all 18 services. Payment-Settlement has wallet, deposit and liability ledgers but no per-device exposure counter. The exposure increments/decrements the change specs rely on are unimplemented.
Impact: there is no live count of "how many of Wiom's devices is this CSP currently on the hook for." Any spec that gates ordering or settlement on exposure is building on a primitive that doesn't yet exist.
MEDGAP-6

Three inbound triggers have no emitter — they are manual/external

NETBOX_ASSIGNMENT_SIGNAL …agent-decisions.md:107, REALLOCATION_INITIATED, and EXIT_TRIGGERED_RETRIEVAL are subscribed and handled in ACS but emitted by no service in the repo (demand-allocation emits the differently-named REASSIGNMENT_COMPLETE, not REALLOCATION_INITIATED).
Impact: the entire REASSIGNED (CSP-to-CSP) path and ad-hoc exit recalls fire only when something/someone posts the event by hand. The state machine has live edges that no automated producer drives.
MEDGAP-7

Device ordering has no financial gate

createOrder checks only "one active order per CSP" + a device cap DeviceOrderServiceImpl.java:43-102. No security-deposit minimum, no wallet check; sdAbsoluteMinimum / order-eligibility appears in zero files in Payment-Settlement. The only ₹20k SD-floor logic lives in the (not-yet-live) device-order-eligibility spec.
Impact: a CSP can order stock with no deposit on file; the financial guardrail is documented but not enforced in V1.
MEDGAP-8

Two disjoint device-creation paths, one mints synthetic IDs

Order FULFILLED mints custody rows keyed by UUID.randomUUID() DeviceOrderServiceImpl.java:153-175; NETBOX_ASSIGNMENT_SIGNAL creates rows keyed by a real external device_id InboundEventProcessingServiceImpl.java:161-195. The two paths are not reconciled in code.
Impact: custody rows created at order-receipt are not tied to physical hardware serials, so a CSP's "with me" count can diverge from real netboxes until/unless an assignment signal reconciles them.
