1Objective

Already designed in your specs (blue) — not gaps

  • RETURNED from any state — warehouse-return accept-all (10 source states).
  • CRP → DEPLOYED — T_REC_6 rescue (recharge & continue). Connection side handled by rescue-intent (PENDING_DEACTIVATION→ACTIVE).
  • CRP → RETRIEVAL_PENDING (T_REC_4) and CRP → RETURNED (T_REC_3).
  • LOST → RECOVERY_HOLD → RETURNED — late recovery.
  • RETURNED → WIOM_INVENTORY → PENDING_CSP_RECEIPT — re-dispatch (new episode).

Still open — no spec covers these

  • OG1 · state should follow customer plan cycle, not CSP ISP expiry (modify).
  • OG2 · LOST → DEPLOYED — put a found device back into service directly.
  • OG3 · cancel a PUT without recharging again (PUT layer, not a custody edge).
  • OG4 · verified path for a CSP to keep a device free (any → IDLE/CUSTODIED).

5The four open gaps

OG1 · modify DEPLOYED → CRP

Device state follows the connection (CSP ISP expiry), not the customer's plan cycle

ScenarioA paying customer is mid plan cycle, but the CSP's own ISP window lapses and the device is dragged toward recovery.
TodayThe DEPLOYED→recovery move is anchored to the connection/ISP deactivation, not the customer.
NeededAnchor custody state to the customer's plan cycle so a live customer is never affected by a CSP-side expiry. (Rescue-intent only aligns the connection on a recharge; it doesn't re-anchor custody.)
OG2 · missing LOST → DEPLOYED

A found device put straight back into service

ScenarioA device marked LOST turns up with the customer still live (or willing to continue) — no warehouse round-trip wanted.
TodayLOST goes only to WRITTEN_OFF, or (per spec) to RETURNED via RECOVERY_HOLD — both routes pull it out of the field.
NeededA recovery edge LOST→DEPLOYED (and/or LOST→IDLE) so a found device re-enters the active fleet directly.
OG3 · missing PUT layer

No way to cancel a PUT without recharging again

ScenarioCustomer raised a PUT while their plan was still active (e.g. a service issue), then wants to continue.
TodayThe only way to clear a PUT is to recharge again — there is no "cancel the PUT, I'm staying" option. (Rescue-intent's path requires paying post-facto; it does not cover cancelling without payment.)
NeededLet a customer withdraw an open PUT and stay live without paying twice.
OG4 · missing any → IDLE / CUSTODIED

CSP wants to keep a device free — no verified provision

ScenarioA CSP ends up holding a device (from any state) and wants to retain it as free stock rather than return it.
TodayNo "keep it" route; idle stock only arises via the churn→recovery path.
NeededA verification-gated retention edge into IDLE/CUSTODIED so a CSP can legitimately keep a device, after verified means.

6Notes & corrections

Exposure. A CSP exposure table exists in the payment-settlement DB. (The exposure visible in code is csp_zone_exposures in demand-allocation — capacity/eligibility bands per CSP×zone, a different axis from device liability.) Open question for later: whether custody-driven device exposure is kept in step with that table.

Scope. This is a system-design / scenario-completeness review — implementation defects are out of scope. Money is raised only where a scenario demands it (e.g. OG3: continuing must not force a re-payment).
