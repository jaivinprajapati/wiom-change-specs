Netbox-Pickup Unread-Update Surfacing — Pickup List & Detail

Netbox-pickup tasks do not participate in the unread-update experience that install and service tasks already have. This change brings pickups to parity on three points — the pickup list (reached by tapping the home pickup group card) and the pickup detail page: a clearing unread count, the latest-update text, and pink-highlighted unread update entries. The home-page pickup group card is explicitly out of scope (tracked separately).

Author: Jaivin Prajapati (PM)  ·  Reviewer: Engineering (CSP app · Gateway · ACS)  ·  Tier: Full
Tier: Full — the change spans two surfaces (list + detail), moves the drilldown-open workflow, introduces tracked unread data, and amends two backend OSes. All sections filled or N/A-with-reason.
Scope fence: business behaviour only. No API contracts, schemas, field names, storage, concurrency, or exact copy — engineering and design own those.

A2. Why This Change WHAT

What is expected: A short problem statement — observable trigger, who is affected, cost of leaving it. Two or three lines.
QuestionAnswer
What's wrong with the current behaviour?On pickup tasks the unread-update experience that install/service have does not work: the pickup list row shows an unread count that never clears after the task is opened, the row's "latest update" text is the current-state line rather than what actually changed, and the pickup detail page shows an empty update timeline with nothing highlighted.
Who experiences it?CSPs and their delegated team members handling netbox pickups — especially anyone returning to the app after updates (reassignment, photo rejection, deadline change, cancellation) happened while they were away.
Cost of leaving it as-is?CSPs miss or react late to pickup changes → slower device recovery, breached pickup SLAs, and lost/written-off netboxes. Pickup is a revenue-recovery flow, so the miss carries direct cost; it also erodes trust in the app's "what changed while I was away" signal that install/service already earn.

A3. Current Behaviour WHAT

What is expected: How the system observably behaves today for the slice being changed. Observable behaviour only.
Tip: "Given X, the system does Y." Behaviour, not code structure.
Trigger / conditionObservable behaviour today
CSP taps the home pickup group cardThe pickup list opens, listing each pickup as a task card, sorted so the most-recently-updated pickup is at the top.
A pickup has updates the CSP has not yet seenThe pickup's list row shows a pink numeric unread count. After the CSP opens that pickup and returns to the list, the count does not clear — it keeps showing, and persists across refreshes.
CSP reads a pickup's list rowThe row shows the pickup's current-state status line plus a last-update timestamp. It does not show the text of the latest discrete update (e.g. "Assigned to Ramesh", "Photo rejected").
CSP opens a pickup's detail pageThe "updates" timeline is empty ("no updates yet"). No update entries appear, so nothing is highlighted. The app never retrieves a pickup's update history.
(Contrast) CSP opens an install or service taskThe list row shows a count that clears once opened and the latest update text; the detail page lists the update history newest-first with the not-yet-seen entries highlighted pink.

A4. Desired Behaviour WHAT

What is expected: The same slice after the change, mirroring A3 so the two read side by side.
Trigger / conditionDesired observable behaviour
CSP taps the home pickup group cardThe pickup list opens, sorted most-recently-updated first. (Unchanged.)
A pickup has updates the CSP has not yet seenThe pickup's list row shows a pink numeric count of the unseen updates. After the CSP opens that pickup, the count clears to zero and stays cleared until a new update occurs.
CSP reads a pickup's list rowThe row shows the title of the pickup's newest update (the "UPDATE — Title" for its latest lifecycle event, per Netbox AFM) as the latest-update line, plus the last-update timestamp.
CSP opens a pickup's detail pageThe updates timeline lists the pickup's update entries newest-first; the entries the CSP has not seen yet are highlighted pink; opening the page marks those updates as seen.
(Parity) Install / service tasksBehave exactly as today — pickups now match them on these three points.

A5. The Delta WHAT

What is expected: One atomic change per row — what changes → before → after → why. What engineering builds against and tests are generated from.
A4 or A5? A4 is the single picture of the result; A5 is the itemised list of differences, one change per row.
What changesBeforeAfterWhy
D1 — Pickup unread count clears on open The list row's unread count never clears; opening a pickup does not mark its updates seen. Opening a pickup marks its updates seen; the list row's count clears to zero and stays until a new update occurs. A count that never clears is noise and destroys the "what's new" signal; parity with install/service.
D2 — Pickup list "latest update" text Row shows the current-state status line. Row shows the title of the pickup's newest update entry (the AFM "UPDATE — Title" for its latest event). The CSP needs to see what changed, not merely the current state.
D3 — Pickup detail update timeline is populated Timeline is always empty ("no updates yet"). Timeline lists the pickup's update entries, newest-first. The CSP must be able to see updates that happened while they were off the task/app.
D4 — Unread highlight on pickup detail Nothing is highlighted (no entries exist). Update entries the CSP has not yet seen are highlighted; the count highlighted equals the unseen count shown on the list before opening. Draw the eye to exactly the updates that are new to this CSP.
D5 — Pickup lifecycle events become visible update entries Pickups produce no CSP-facing update history. Pickup lifecycle events (assigned, self-/team-assigned, reassigned, work started, photos submitted, photo rejected, resubmitted, verified, recovery complete, cancelled — per Netbox AFM) are surfaced as titled, timestamped update entries. The timeline (D3), the list latest-text (D2) and the highlight (D4) all require a source of update entries.
D6 — Per-pickup unread marker A pickup carries no "how many updates, seen up to where" marker, so unseen cannot be computed or cleared. Each pickup carries a monotonic update marker; the unread count is "updates since the CSP last opened it"; opening advances the "seen up to" point. The count (D1), the highlight (D4) and their clearing all derive from this single marker.

A7.1 Rules & invariants (must always hold)

Rule / invariantStatement
INV-1 — count is non-negative & derivedA pickup's displayed unread count equals the number of updates that occurred since the CSP last opened it, and is never negative.
INV-2 — clear-on-openImmediately after a CSP opens a pickup, that pickup's unread count is zero for that CSP, and stays zero until a new update occurs.
INV-3 — highlight equals countThe number of update entries highlighted on the detail page at open equals the unread count that was shown on the list row just before opening.
INV-4 — newest-first & latest-text consistencyUpdate entries are ordered newest-first everywhere they appear; the list row's latest-update text is the title of the top (newest) timeline entry.
RULE-1 — parity, not divergencePickup uses the same unread/timeline semantics as install/service; no pickup-only rule for counting, clearing, ordering, or highlighting is introduced.
RULE-2 — single latest-textA list row shows exactly one latest-update title (the newest), never a concatenation of several updates.

A7.2 Edge cases

Edge / conditionIntended business outcome
E1 — Pickup with only its creation event (no later updates)No unread count and no highlight; timeline shows the single creation/assignment entry; list latest-text is that entry's title ("Pickup task assigned").
E2 — An update arrives while the CSP is viewing the pickup detail[Decision needed — define before build: does the new update live-append and highlight in the open detail, or only surface on the next open?]
E3 — A pickup is delegated: a team member and the admin CSP each open it[Decision needed — define before build: is "seen / unread" tracked per user (each clears their own) or per task (either open clears it for both)? Must match install/service semantics.]
E4 — Pickup reaches a terminal state (recovery complete / cancelled) with unseen updatesThe terminal card auto-dismisses per Netbox AFM; the unread count is not surfaced after dismissal and blocks nothing.
E5 — Pickup has a large update historyThe list shows only the newest update as latest-text; the detail timeline shows the newest page and loads older entries on demand (parity with install/service paging).
E6 — An update entry's title has no translation for the active languageThe entry renders via the existing language fallback; it never shows a blank line or a raw key.

Business logic (A5 delta · A7.1 rules)

LOGIC_01 (logic · happy) — D1/INV-2 count clears on open:
Given a pickup whose list row shows an unread count of 3 for this CSP
When the CSP opens that pickup and returns to the list
Then the pickup's unread count reads zero
And it stays zero across list refreshes until a new update occurs
LOGIC_02 (logic · negative) — D1 no false clear:
Given a pickup with unread updates that the CSP has not opened
When the list is refreshed or re-sorted
Then the unread count is still shown (only opening the pickup clears it)
LOGIC_03 (logic · happy) — D2 latest-text is the newest update title:
Given a pickup whose most recent update is "Assigned to Ramesh"
When the CSP views the pickup list
Then that row's latest-update line reads the title of that newest update, not the current-state line
LOGIC_04 (logic · happy) — D3/D5 timeline populated from lifecycle events:
Given a pickup that has been assigned, started, and had a photo rejected
When the CSP opens its detail page
Then the updates timeline lists those events as titled, timestamped entries, newest-first
LOGIC_05 (logic · happy) — D4 highlight of unseen entries:
Given a pickup with 2 updates this CSP has not seen and 4 older seen ones
When the CSP opens the detail page
Then the 2 newest entries are highlighted and the 4 older ones are not
LOGIC_06 (logic · negative) — RULE-2 single latest-text:
Given a pickup with several updates in quick succession
When the CSP views the list row
Then exactly one title (the newest) is shown, never a concatenation

Computation & calculation (with boundaries)

COMPUTE_01 (computation · normal) — unread = updates since last open:
Given a pickup the CSP last opened after update #5, now at update #8
When the list row renders
Then the unread count reads 3
COMPUTE_02 (computation · zero boundary) — no new updates:
Given a pickup the CSP last opened at its latest update
When the list row renders
Then the unread count is zero and no count badge is shown
COMPUTE_03 (computation · first-update boundary) — brand-new pickup:
Given a pickup that has just its creation/assignment event and was never opened
When the list row renders
Then the count reflects that single unseen update (1), and the latest-text is that event's title
COMPUTE_04 (computation · off-by-one) — highlight count equals list count:
Given a list row showing an unread count of N just before opening
When the CSP opens the detail page
Then exactly N entries are highlighted — not N−1 or N+1
COMPUTE_05 (computation · max / paging boundary) — large history:
Given a pickup with more updates than one page
When the CSP opens the detail page
Then the newest page is shown, older entries load on demand, and the newest-first order holds across page loads
COMPUTE_06 (computation · post-open increment) — update after clear:
Given a pickup the CSP opened (count cleared to zero)
When one new update occurs afterwards
Then the unread count becomes exactly 1

Invariants (A7.1)

INVARIANT_01 (INV-1) — non-negative & derived:
Given any pickup and any CSP at any time
Then the displayed unread count equals updates-since-last-open and is never negative
INVARIANT_02 (INV-2) — clear-on-open holds:
Given any pickup just opened by a CSP
Then its unread count for that CSP is zero
Until a new update occurs
INVARIANT_03 (INV-3) — highlight equals count:
Given any pickup opened from the list
Then the number of highlighted entries equals the count shown on the list immediately before opening
INVARIANT_04 (INV-4) — newest-first & latest-text consistency:
Given any pickup with at least one update
Then entries are ordered newest-first wherever shown
And the list latest-text equals the title of the top timeline entry
INVARIANT_05 (RULE-1) — parity, no divergent rule:
Given the same unread/timeline scenario on a pickup and on an install/service task
Then counting, clearing, ordering, and highlighting behave identically
