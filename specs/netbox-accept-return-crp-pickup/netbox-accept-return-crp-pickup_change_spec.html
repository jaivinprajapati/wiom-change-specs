NetBox "Accept Return" — CRP Device List Opening the Pickup Task Flow

The NetBox "return / take custody" entry on the CSP app should show the CSP the devices he can take custody of — the ones in Customer-Recovery-Pending (CRP) — and let him act on each through the existing netbox pickup (NBREC) flow. This change makes the "Accept Return" screen a CRP-only device list where tapping a device opens the same pickup task screen reached today from Home → pickup group card → pickup list → task, and returns him to the CRP list afterwards. Builds on FE PR #506 (which enables the card and adds search).

Author: Jaivin Prajapati (PM)  ·  Reviewer: Engineering (CSP app · Gateway · TAS · ACS)  ·  Tier: Full
Tier: Full — crosses two surfaces (NetBox home + Accept Return list) into the shared pickup drilldown/flow, changes a backend list contract, and reworks navigation. Business behaviour only; engineering owns implementation.

A2. Why This Change WHAT

What is expected: A short observable problem — trigger, who, cost.
QuestionAnswer
What's wrong with the current behaviour?The CSP has no device-first way to act on netboxes awaiting customer recovery. The single "return" entry was hidden; when shown, it lists DEPLOYED devices (not the ones actually pending recovery) and dead-ends into a walk-in "accept" path rather than the real recovery flow. So a CSP cannot simply see "which of my devices are Customer-Recovery-Pending" and act on each.
Who experiences it?CSPs responsible for recovering netbox devices from customers whose service has ended / who requested pickup.
Cost of leaving it as-is?CRP devices linger un-actioned; recovery isn't driven through the correct NBREC flow; the CSP lacks a clear "these are the devices to take custody of" surface — leading to slower recovery, higher device loss, and overstated CSP exposure.

A3. Current Behaviour WHAT

What is expected: Observable behaviour today for the slice being changed.
Tip: "Given X, the system does Y." Behaviour, not code structure.
Trigger / conditionObservable behaviour today
CSP is on the NetBox home, returns sectionWith PR #506, a single "return / customer returned it" card is shown above the batch-return card and opens the Accept Return screen. (Before PR #506 the card was hidden.)
CSP opens the Accept Return screenIt fetches and lists the CSP's DEPLOYED devices from the backend, each showing device ID + customer name. A top-bar search filters the loaded list by device ID or customer name (PR #506), with an empty-results state.
CSP selects a device and taps the CTAThe app navigates into the pickup submission wizard (walk-in entry), not the pickup task screen used from Home. A separate, unused "accept-customer-return" path (DEPLOYED → CUSTODIED) also exists but is not wired to the button.

Backend: a CRP device's linked pickup taskThe gateway device-detail endpoint already resolves a CRP device's pickup task (returns pickup_ticket_id and VIEW_PICKUP_TICKET) via a TAS lookup — but this linkage is not carried on the inventory/Accept-Return list.

A4. Desired Behaviour WHAT

What is expected: The same slice after the change, mirroring A3.
Trigger / conditionDesired observable behaviour
CSP is on the NetBox home, returns sectionThe return / "take custody" card is shown and opens the Accept Return screen. (Copy reframed to "devices to take custody of / recover" — design deliverable.)

CSP returns, cancels, or completes the pickupThe app returns the CSP to the Accept Return CRP list (refreshed), not to Home. A device that has left CRP no longer appears.

A5. The Delta WHAT

What is expected: One atomic change per row — what changes → before → after → why.
A4 or A5? A4 is the single picture; A5 is the itemised diff, one change per row.
What changesBeforeAfterWhy
D1 — Accept Return list source Lists the CSP's DEPLOYED devices. Lists only the CSP's CUSTOMER_RECOVERY_PENDING devices; no other state appears. The CSP should act only on devices genuinely awaiting customer recovery.
D2 — Per-device pickup task id on the list The list item carries no pickup task / candidate id. Each CRP device carries its assigned pickup task id (the pickup_ticket_id / candidate the gateway already resolves for CRP on device-detail). Needed to open the correct pickup task drilldown from the list.
D3 — Device-tap target Selecting a device + CTA navigates into the pickup submission wizard (walk-in entry). Tapping a device opens the pickup task drilldown (same screen as the Home pickup path) for that device's pickup task. Parity with the Home pickup experience; full resolution/assignment, not just the wizard.
D4 — Standalone drilldown launch The pickup drilldown opens only within the Home context (relies on the home feed / its back stack). The drilldown opens from the Accept Return context by pickup task id and loads its own task detail, independent of Home. Accept Return is a different surface; the drilldown must open there without the Home feed present.
D5 — Post-flow return target Walk-in flow exit pops back / routes to Home. Return, cancel, or completion of the pickup returns the CSP to the Accept Return CRP list (refreshed). Keep the CSP in the take-custody context to action the next device.
D6 — Drop the walk-in accept path A latent DEPLOYED → CUSTODIED "accept-customer-return" path exists. Removed from this entry; custody/recovery happens only through the NBREC pickup flow. One correct recovery path; no confusing dead alternate.
D7 — Search scope Search filters the loaded DEPLOYED list (PR #506). Same search UX, now over the CRP list (device ID / customer name). Search must operate on the corrected population.

A7. Rules, Invariants & Edge Cases Affected WHAT

What is expected: Rules/invariants introduced, and new edges each with an intended outcome. All verified in B5.

A7.1 Rules & invariants (must always hold)

Rule / invariantStatement
INV-1 — CRP-only listEvery device shown on the Accept Return list is in CUSTOMER_RECOVERY_PENDING for the current CSP; no device in any other state appears.
INV-2 — device ↔ task correspondenceOpening a listed device always opens the pickup task for that same device (never a different device's task).
INV-3 — post-flow locationAfter returning, cancelling, or completing the pickup launched from Accept Return, the CSP is on the Accept Return CRP list — never dropped to Home.
INV-4 — list freshness on returnA device that has left CRP (recovery completed/cancelled) is not present in the list after returning to it.
RULE-1 — flow parityThe pickup flow opened from Accept Return is behaviourally identical to the same flow opened from Home.
RULE-2 — single recovery pathTaking custody of a CRP device happens only via the NBREC pickup flow; no walk-in DEPLOYED→CUSTODIED accept remains reachable from this entry.
RULE-3 — latest task on ambiguityIf a CRP device resolves to more than one pickup task, the list uses the latest (most recent) one; a device that resolves to no pickup task is not listed at all.

A7.2 Edge cases

Edge / conditionIntended business outcome
E1 — CRP device with no resolvable pickup task (TAS absent / cancelled / error, i.e. pickup_ticket_id null)Decided: the device is not fetched into the list at all — such a device never appears on the Accept Return screen. (Only CRP devices that resolve to a pickup task are listed.)
E1b — CRP device with more than one pickup taskDecided: resolve to the latest (most recent) task and list the device once against it. (Per RULE-3.)
E2 — Device transitions out of CRP while the list is open (recovery completed elsewhere)On refresh / return, the device is gone from the list; no stale row remains actionable.
E3 — No CRP devices for the CSPThe Accept Return screen shows an empty state (nothing to take custody of).
E4 — Search yields no matchThe existing empty-results state is shown (PR #506).
E5 — CRP list larger than one fetch page (fetch is capped, not paginated today)Decided: the CRP list must be paginated so every CRP device is reachable — a silent cap that hides devices is not acceptable. Product mandates "must paginate, no silent cap"; the pagination mechanism (page size, load-more trigger, whether search is server- or client-side) is a design decision to be specified in the FE PR, not by product.
E6 — Device tapped but the pickup drilldown detail fails to loadThe failure is shown gracefully and the CSP can return to the CRP list; no crash, no wrong-task open.

Computation & calculation (with boundaries)

COMPUTE_01 (computation · normal) — list = count of CRP devices:
Given a CSP with exactly K devices in CRP
When the Accept Return list loads
Then exactly those K devices are shown
COMPUTE_02 (computation · zero boundary) — no CRP devices:
Given a CSP with zero CRP devices
When the screen loads
Then the list is empty and the empty state is shown
COMPUTE_03 (computation · off-by-one boundary) — a device leaves CRP:
Given K CRP devices, one of which is recovered
When the CSP returns to the list

COMPUTE_04 (computation · max / cap boundary) — large CRP list:
Given more CRP devices than one fetch page
When the CSP scrolls / loads more
