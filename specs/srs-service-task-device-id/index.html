SRS Service Task — Expose Device / Netbox ID in Task API

Backend spec for a front-end PR carrying three task-card changes. Only one needs backend: the SRS service task card wants to show the device / netbox ID, but the SRS (non-gateway) service-task API does not return it. This spec covers that single additive change. The other two PR items are FE-only and carry no backend work (declared in scope note below).

Author: PM  ·  Reviewer: Engineering  ·  Tier: Light

A2. Why This Change WHAT

QuestionAnswer
What's wrong with the current behaviour?The SRS service-task card cannot show which device / netbox the complaint is for — the task API never returns that ID, so the FE has nothing to render.
Who experiences it?CSPs / partners working SRS service tasks in the app.
Cost of leaving it as-is?Slower resolution and wrong-device errors — the partner must look the device up elsewhere before acting.

A3. Current Behaviour WHAT

Trigger / conditionObservable behaviour today
Partner opens an SRS service taskCard shows complaint title, connection and status — but no device / netbox ID. The response the app receives does not carry that ID.

A4. Desired Behaviour WHAT

Trigger / conditionDesired observable behaviour
Partner opens an SRS service taskThe response carries the device / netbox ID of the complaint's connection, and the card shows it upfront alongside the existing details.
Complaint's connection has no device mappedID comes back empty / null; the card still renders every other detail as before.

A5. The Delta WHAT

The one backend change engineering builds against.
What changesBeforeAfterWhy
SRS service-task API response payloadDoes not include the device / netbox ID.Includes the device / netbox ID for the complaint's connection (empty / null when none is mapped).FE needs the ID to show the device on the task card; it is not obtainable client-side today.
Additive only: one new field on the existing response. No change to which tasks are returned, their order, states, or any existing field.

A6. Must-Not-Change — Regression Guard GUARD

Adjacent behaviour that must not changeWhy it's in the blast radius
The set, ordering and filtering of SRS service tasks returned is unchanged.Same query touched to add the field — easy to alter the result set by accident.
All existing fields on the response keep their values and shape.Existing app screens and any other consumers parse this payload.
Complaint / service-task resolution behaviour is unchanged.The change is display data only; it must not affect task lifecycle.

A7. Rules, Invariants & Edge Cases Affected WHAT

A7.1 Rules & invariants

Rule / invariantStatement
INV — correct deviceThe device / netbox ID returned for a task always belongs to that complaint's own connection, never another connection's device.
RULE — optional / non-blockingThe field is optional: when no device is mapped it is empty / null and the task is still returned and renders in full.

A7.2 Edge cases

Edge / conditionIntended business outcome
Complaint's connection has no device mappedField returns null; task renders normally without a device ID.
Connection has device history (past + current custody)Return the connection's current device / netbox ID — the one in effect now, not a historical one. [Confirm with SRS/Netbox owner before build.]

B5. Acceptance Criteria — Verification Layer HOW

LOGIC_01 (business logic · happy): Device ID is returned
Given an SRS service task whose complaint's connection has a mapped device
When the app requests the service task
Then the response includes that connection's current device / netbox ID
And the card shows it upfront
LOGIC_02 (business logic · negative): No device mapped
Given an SRS service task whose connection has no device mapped
When the app requests the service task
Then the device / netbox ID comes back empty / null
And the task is still returned and every other field renders as before
INVARIANT_01 (from A7.1): Correct device
Given any SRS service task with a returned device / netbox ID
Then that ID belongs to the task's own complaint connection
And never to another connection's device
INVARIANT_02 (from A7.1 · edge A7.2): Current device on history
Given a connection with both past and current custody devices
Then the ID returned is the device currently in effect
And not a historical / released device
REGRESSION_01 (guard · from A6): Task set unchanged
Given the same partner and data as before the change
When the SRS service tasks are fetched
Then exactly the same tasks are returned, in the same order and filtering
And only the new device / netbox ID field is added
REGRESSION_02 (guard · from A6): Existing fields intact
Given an existing consumer parsing the SRS service-task response
Then every pre-existing field keeps its value and shape
And task resolution behaviour is unchanged
