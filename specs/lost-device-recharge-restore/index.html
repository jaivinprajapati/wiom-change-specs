Restore a LOST Device to DEPLOYED on Customer Recharge

A device can sit in LOST custody while its customer's connection is live and paying. When the customer recharges, the connection reactivates but the device stays LOST — so custody, exposure and inventory are wrong. This change restores such a device to DEPLOYED on recharge, while keeping every loss penalty booked. Touches multiple OS (Asset Custody, Connection Lifecycle, Payment, Compensation, TAS) and moves a device state machine — Full tier.

Author: Jaivin Prajapati (PM)  ·  Reviewer: Engineering  ·  Tier: Full

Quick Check

7-line triage.
What is changing?
A recharge that reactivates a connection whose still-mapped device is LOST, CUSTOMER_RECOVERY_PENDING, or WRITTEN_OFF restores that device to DEPLOYED; loss / write-off penalties stay booked; exposure is re-incremented +1.
What triggered it?
Bug — ~3,124 devices stuck in LOST while serving live, paying connections (lost-device-rescue-plan).
Blast radius
ACS custody state machine + exposure; CLOS activation event payload; Payment/Compensation/TAS consumers (confirmation).
Reversible?
Yes — the restore is additive; disable the new trigger to roll back. No penalty is mutated, so nothing to un-wind.
Money / PII / migration?
Money: Y (exposure re-count; penalties must stay untouched — see A5/A8) · PII: N · Migration: Y (backfill the existing stuck LOST population — engineering runbook, out of scope here)
OS impact / sign-off?
ACS (Yes — incl. state-machine change to make WRITTEN_OFF reclaimable), CLOS (Yes); Payment, Compensation, TAS (Yes — confirm); RV, Enforcement (No). All sign-off Pending.
Tier
Full
What already exists, and the gap this closes. A LOST → DEPLOYED reclaim (T_LOSS_RECLAIM_DEPLOYED, handler handleClConnectionRescued) is already live, driven by CL_CONNECTION_RESCUED; it keeps money untouched and re-emits exposure +1. But it fires only for the rescue-intent sub-case (connection in PENDING_DEACTIVATION + a CAEO_RESCUE_INTENT). It does not cover a plain recharge-activation (CL_CONNECTION_ACTIVATED) of a still-mapped LOST device — ACS does not subscribe to that event — nor a device that has since gone WRITTEN_OFF. This spec closes both gaps: any customer recharge that reactivates the connection restores a LOST, CUSTOMER_RECOVERY_PENDING, or WRITTEN_OFF device to DEPLOYED, with all penalties preserved.

A2. Why This Change WHAT

QuestionAnswer
What's wrong with the current behaviour?A device marked LOST stays LOST even after its customer recharges and the connection goes back to ACTIVE. The device is physically serving a paying customer but is recorded as lost — so custody state, CSP exposure count and inventory are all wrong, and the device is invisible to normal operations.
Who experiences it?The CSP (penalised and exposure-reduced for a device that is actually in service), Ops/inventory (false LOST count), and Wiom (~3,124 such devices identified).
Cost of leaving it as-is?Understated exposure/deposit adequacy, corrupt inventory, devices that can never be correctly retrieved/returned, and CSP disputes. The loss penalty is legitimate, but the state is not.

A3. Current Behaviour WHAT

Trigger / conditionObservable behaviour today (production)
Customer recharges; connection is PAUSED; device is LOST and still mappedRV validates → connection goes PAUSED→ACTIVE (CL_CONNECTION_ACTIVATED emitted). The device custody state is never touched — it stays LOST. Exposure stays at the reduced (−1) count. This is the bug.
Device marked LOST (any of 3 paths)Exposure decremented −1 (ACS-SD-21); carry-fee accrual stopped; loss liability booked in Compensation (COMP_DEVICE_LOSS_LIABILITY) → Payment recoverable_due; pickup task set FAILED. The customer connection is not deactivated by the LOST transition — it remains mapped.
Device write-off timer elapses on a LOST deviceDevice → WRITTEN_OFF; full device-value liability booked (DeviceWriteOffEvent / AssetLiabilitySettled). WRITTEN_OFF is a terminal custody state today — no transition out of it exists, so a later recharge can never restore it.
Rescue-intent recharge: connection in PENDING_DEACTIVATION + a CAEO rescue-intentT_RESCUE emits CL_CONNECTION_RESCUED; ACS restores LOST / CUSTOMER_RECOVERY_PENDING → DEPLOYED, re-emits exposure +1, money untouched. This is the only recharge path that restores a device today, and it does not cover a plain PAUSED→ACTIVE recharge or a WRITTEN_OFF device.

A4. Desired Behaviour WHAT

Trigger / conditionDesired observable behaviour
Customer recharges and the connection reactivates, while a LOST or WRITTEN_OFF device is still mapped to that connectionThe device is restored to DEPLOYED and re-bound to the connection. Exposure returns to its correct value (+1). Idle / carry-fee counters reset; no carry-fee back-charge for the LOST/written-off period. WRITTEN_OFF is handled exactly like LOST.
Penalties from the LOST / write-off eventRemain booked, unchanged — the Compensation loss liability, the Payment recoverable_due row, and any full device-value write-off liability are never reversed or clawed back by the restore.
Recharge of a connection whose device is not LOST/WRITTEN_OFF (DEPLOYED, or no device mapped)No change — behaves exactly as today.
Device reassigned to another CSP, or mapped to a different connectionNot restored under the old mapping (see A7.2 edges).

A5. The Delta WHAT

The atomic changes engineering builds and tests against. Rows 1–2 are the genuinely new work; row 3 extends the state machine; rows 4–5 reuse existing restore semantics on the new triggers; row 6 guards correctness.
What changesBeforeAfterWhy
ACS reacts to a plain recharge-activation ACS subscribes only to CL_CONNECTION_RESCUED. A PAUSED→ACTIVE recharge emits CL_CONNECTION_ACTIVATED, which ACS ignores. ACS also consumes the recharge-activation signal; on it, if a still-mapped device for that connection is LOST, CUSTOMER_RECOVERY_PENDING, or WRITTEN_OFF, it transitions the device to DEPLOYED. Covers the manual-LOST, written-off, and plain-recharge populations the rescue-intent path misses.
Device linkage on the activation signal CL_CONNECTION_ACTIVATED carries connection_id but device_id = null. ACS resolves the device by connection_id (current or last mapping), OR CLOS populates the device id on the event. Either makes the device findable. ACS must locate the exact device tied to the recharging connection.
Make WRITTEN_OFF reclaimable (state machine) WRITTEN_OFF is a terminal state — no outbound transition; a recharge can never restore it. Add a WRITTEN_OFF → DEPLOYED reclaim edge (soft-terminal, like LOST), fired by the same recharge restore. A written-off device whose customer recharges is physically back in service; state must reflect it, handled identically to LOST.
Exposure on restore Not re-incremented on a plain recharge (device stays LOST/WRITTEN_OFF → still −1). CSP_EXPOSURE_CHANGED(+1) re-emitted on LOST → DEPLOYED and WRITTEN_OFF → DEPLOYED (fresh COUNT(*); Payment overwrites projection). No effect for a CUSTOMER_RECOVERY_PENDING → DEPLOYED restore (already counted). LOST decremented −1 (and WRITTEN_OFF inherits that −1 from its prior LOST); restoring must give the count back. Net zero across the round-trip.
Money is untouched on restore N/A (no restore for these paths). The restore emits no Compensation or Payment money event. Loss liability, recoverable_due, and any full device-value write-off liability stay exactly as booked. The penalty for having lost / written off the device is legitimate and must persist — only the state is corrected.
Idempotency of restore N/A Repeated recharges / renewals on an already-DEPLOYED device are a custody no-op — no second transition, no double exposure +1. Recharges recur; the restore must fire once per restore, not per recharge.

A6. Must-Not-Change — Regression Guard GUARD

Adjacent behaviour that must not changeWhy it's in the blast radius
The LOST / write-off penalties — Compensation loss liability, Payment recoverable_due, and any full device-value write-off liability — are never reversed, reduced, or clawed back by the restore.The restore path touches exposure and could be mistaken for a full "un-loss"; the money must stay.
Exposure stays ACS-authoritative: fresh COUNT(*) from ACS; Payment overwrites its projection, never self-increments.The new +1 trigger reuses the same recount mechanism; a manual ± would corrupt the count.
Recharge/activation of a connection with no device, or with a DEPLOYED device, behaves exactly as today (custody untouched).ACS now listens to the activation event; it must be a no-op unless the device is LOST / CUSTOMER_RECOVERY_PENDING / WRITTEN_OFF.
All other terminal states (RETURNED, DAMAGED) stay terminal and are not reclaimable by recharge.Only WRITTEN_OFF is being un-terminalised; the other terminals must not be loosened by accident.
The RV recharge gates and the CLOS PAUSED→ACTIVE transition are unchanged.We add a downstream consumer, not a new gate — recharge validation must not regress.
No carry-fee is back-charged for the period the device spent in LOST.Carry-fee accrual was OFF during LOST; the restore resets counters and must not retroactively bill.
The existing CL_CONNECTION_RESCUED → LOST→DEPLOYED rescue-intent behaviour is preserved unchanged.We are adding a second trigger, not replacing the rescue-intent path.

A7. Rules, Invariants & Edge Cases Affected WHAT

A7.1 Rules & invariants

Rule / invariantStatement
INV — exposure conservationAcross a full LOST → DEPLOYED round-trip the net exposure change is 0: exactly one −1 at LOST and exactly one +1 at restore, never more.
INV — penalty persistenceThe device-loss liability, its recoverable_due row, and any write-off liability are unchanged by any restore; a restored device still owes the penalty.
INV — deploy requires a live mappingA device is set to DEPLOYED by this change only when a live connection is mapped to it (current or last connection id equals the recharging connection).
RULE — restore scopeRestore applies only to a device whose state is LOST, CUSTOMER_RECOVERY_PENDING, or WRITTEN_OFF and which is still mapped to the recharging connection. All other states (incl. RETURNED, DAMAGED) → no-op.
RULE — money silenceThe restore path emits no COMP_* and no payment event — ever.

A7.2 Edge cases

Edge / conditionIntended business outcome
Device already WRITTEN_OFF when the customer rechargesRestored to DEPLOYED, handled identically to LOST: exposure +1, connection re-bound, counters reset — and the full device-value write-off liability stays booked. Requires the new WRITTEN_OFF → DEPLOYED reclaim edge (A5 row 3).
Device was reassigned to a different CSP after going LOST/WRITTEN_OFFDo not restore under the old CSP; the mapping no longer holds. No-op.
Connection recharges but the device is now mapped to a different connectionRestore only if the recharging connection matches the device's current/last mapping; otherwise no-op.
Multiple recharges / renewals in quick successionFirst one restores LOST→DEPLOYED and emits +1; subsequent ones are custody no-ops (idempotent) — no double +1.
Manual declareLoss while the connection was ACTIVE/PAUSED (never deactivated), then a plain rechargeThis is the population the rescue-intent path misses; the new activation trigger restores it. This edge is the core reason for the change.
Backfill of the ~3,124 already-stuck LOST devices whose connections are already liveOne-off correction via engineering migration runbook (out of scope for this spec); same money-untouched + exposure-recount rules apply.

B5. Acceptance Criteria — Verification Layer HOW

LOGIC_01 (business logic · happy): Plain recharge restores a LOST device
Given a device in LOST still mapped to a connection, and the connection is PAUSED
When the customer recharges and the connection reactivates
Then the device is transitioned to DEPLOYED and re-bound to the connection
LOGIC_02 (business logic · happy): Recovery-pending device restored
Given a device in CUSTOMER_RECOVERY_PENDING mapped to a connection
When the customer recharges
Then the device is restored to DEPLOYED (and no exposure change, as that state was already counted)
LOGIC_03 (business logic · negative): Non-LOST recharge is a no-op
Given a recharge for a connection whose device is DEPLOYED, or which has no device mapped
When the connection reactivates
Then no custody transition occurs and no exposure event is emitted
COMPUTE_01 (computation · normal): Exposure +1 on LOST→DEPLOYED
Given a CSP whose exposure was decremented by the device's LOST transition
When the device is restored to DEPLOYED
Then a fresh recount is emitted that is exactly 1 higher than the LOST-time count
COMPUTE_02 (computation · boundary / idempotency): No double +1
Given a device just restored to DEPLOYED by a recharge
When further recharges / renewals arrive for the same connection
Then exposure is not incremented again and the device is not re-transitioned
INVARIANT_01 (from A7.1): Exposure conservation
Given any device that goes LOST then is restored to DEPLOYED
Then the net exposure change across the round-trip is 0 — exactly one −1 and one +1
INVARIANT_02 (from A7.1): Penalty persistence
Given a device restored from LOST or WRITTEN_OFF
Then the loss liability, its recoverable_due row, and any write-off liability are byte-for-byte unchanged
And no Compensation or Payment money event is emitted by the restore
LOGIC_04 (business logic · happy): Written-off device restored like LOST
Given a device in WRITTEN_OFF still mapped to a connection
When the customer recharges and the connection reactivates
Then the device is transitioned WRITTEN_OFF → DEPLOYED, re-bound, exposure +1
And the write-off liability and recoverable_due stay booked
REGRESSION_05 (guard · from A6): Other terminals stay terminal
Given a device in RETURNED or DAMAGED
When a recharge occurs on any associated connection
Then the device is not restored — those states remain terminal
EDGE_02 (edge · from A7.2): Mapping mismatch
Given a LOST device whose current/last connection differs from the recharging connection
When that connection recharges
Then the device is not restored (no-op)
REGRESSION_01 (guard · from A6): Loss penalty survives
Given a booked device-loss liability and recoverable_due
When the device is restored to DEPLOYED on recharge
Then both remain exactly as booked — no reversal, reduction or clawback
REGRESSION_02 (guard · from A6): Recharge validation unchanged
Given the RV gates and CLOS PAUSED→ACTIVE transition
When any recharge is processed
Then validation and connection-state behaviour are exactly as before the change
REGRESSION_03 (guard · from A6): No carry-fee back-charge
Given a device that spent time in LOST with carry-fee accrual OFF
When it is restored to DEPLOYED
Then no carry-fee is charged for the LOST period; counters reset from zero
REGRESSION_04 (guard · from A6): Rescue-intent path preserved
Given the existing CL_CONNECTION_RESCUED restore on main
When a rescue-intent recharge occurs from PENDING_DEACTIVATION
Then it still restores the device exactly as before
