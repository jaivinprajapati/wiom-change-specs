Device Re-Dispatch & Custody Episodes — Supply-Chain Tracking & Liability Trail

Objective: ensure 100% accurate tracking of device status across the supply chain, with no dilution in asset↔CSP liability transactions and trail.

Once ACS has accepted a return (Part 1), the warehouse re-stacks the device and re-dispatches it to any CSP — same device_id. Today the device record is one row per device and RETURNED is terminal, so a re-dispatch is impossible without overwriting the old custodian's record. This spec introduces a custody-episode model: the live row always shows current physical custody and moves with the device; every past custodian's liability facts are frozen in an immutable per-episode log. Warehouse management (Pyrops) is out of scope.

Author (PM): Jaivin Prajapati  ·  Reviewers: Dhruv · EM  ·  Tier: Full

Quick Check

7-line triage.
What is changing?
Re-dispatch a RETURNED device to any CSP via a custody-episode model — the live netbox_custody row moves with the device (re-stamped, not reversed); an immutable per-episode log preserves each CSP's liability + history.
What triggered it?
Supply-chain reality — returned devices must re-ship to any CSP, but the single-row + forward-only model can't re-dispatch (PK collision) and overwriting it dilutes the old CSP's liability/visibility trail.
Blast radius
Custody state machine (terminal / forward-only), netbox_custody row semantics, was_ever_deployed, per-CSP reads (dashboard/inventory/exposure/prior-POD/exit), money-ledger device_id, visibility surfaces.
Reversible?
Partial — fundamental data-model change (episode log + row-reset semantics).
Money / PII / migration?
Money Y (trail is code-confirmed safe — see A6) · PII N · Migration Y (episode-log backfill + device_id columns).
OS impact / sign-off?
Asset Custody (critical), Payment & Settlement, Compensation, Visibility, ESR — all Pending.
Tier
Full.

⬤ Critical OS-level calls (EM / architectural)

  1. decided Forward-only → episode-scoped. Re-dispatch is not a reversal of a terminal state — it closes the current episode and opens a new one. Forward-only (INV-ACO-02) holds within an episode. Amend ACS OS to introduce the episode concept.
  2. decided Single current row + separate immutable logs. netbox_custody = current physical custody only (one row, re-stamped on hand-over). A new custody-episode log holds each (device, CSP) tenure's liability + history. Amend ASM-ACO-03 to allow sequential custodians.
  3. decided was_ever_deployed resets per episode; device_commissioned_at stays constant. Override SD-fork Patch 2 "never resets" — was_ever_deployed is episode-scoped (carry-fee fairness for the new CSP); device_commissioned_at is device-level (physical age / depreciation), permanent.
  4. no change NBREC uniqueness stays. The device_id-only open-task check is a correct physical invariant (one device, one open recovery at a time) — not a csp mapping. No change.

Organising principle: physical status (where the device is / who holds it now) → the live row, moves on. Liability status (what each CSP owes/owed/was-credited) → the episode log, frozen. The states that are both — RETURNED, LOST, DAMAGED, WRITTEN_OFF, IDLE (carry fee), CUSTOMER_RECOVERY_PENDING — are exactly where today's single row conflates them.

A2. Why This Change WHAT

QuestionAnswer
What's wrong?After RETURNED, the device must re-ship to any CSP — but RETURNED is terminal (forward-only) and netbox_custody is one row per device (PK device_id). A re-dispatch would collide on the primary key; overwriting the row in place destroys the old custodian's liability/history record and silently moves the device out of every per-CSP view.
Who experiences it?Supply chain / warehouse (can't cleanly re-ship), the old CSP (loses lost-list / ever-held / money-trail visibility), finance (liability-attribution & audit integrity).
Cost of leaving it?Returned devices unusable, diluted asset↔CSP trail, no audit of who held the device when, broken supply-chain status tracking.

A4. Desired Behaviour — The Episode Model WHAT

A device's life is a sequence of episodes, one per custodian. device_id is the thread.

ConceptBehaviour
Current custody (live row)netbox_custody = exactly one row = where the device is & who holds it now. On re-dispatch it is re-stamped (moved to the new CSP), never duplicated, never reversed.
Episode closeOn RETURNED (or any terminal disposition), the episode's full liability + history is snapshotted into the immutable episode log before the row can move.
New episodeRe-dispatch opens a fresh episode: row reset (status→PENDING_CSP_RECEIPT, counters zeroed, was_ever_deployed→false, fresh created_at), new csp_id. device_commissioned_at preserved.
Liability stays putEvery money fact is already stamped with the episode's csp_id; it never follows the device to the next CSP. Old CSP's dues settle at its reconciliation.

Physical status vs liability status — the two axes

State / eventPhysical fact (live row)Liability fact (episode log) — frozen to the CSP
RETURNEDdevice at warehouseclosure; ₹50 recovery credit (if CRP-return); pending dues settle
LOST (any reason)may be 3PL-recovered → warehouseloss penalty (CUSTODY_LOSS residual) / ₹200 (CUSTOMER_NONRECOVERY) — stays with old CSP
DAMAGEDat warehousedamage penalty (₹150 / min(₹300,residual) / residual)
WRITTEN_OFFunrecovered / scrappeddevice value + capped carry fee (DEPOSIT_FORFEITURE + WRITE_OFF_RESIDUAL)
IDLE (carry fee)idle stock with CSPper-day carry-fee accrual (CARRY_FEE / overflow)
CUSTOMER_RECOVERY_PENDINGat customer post-churnpending liability → ₹200 if unrecovered in 30d

When the physical status moves on (re-dispatch), the liability facts above are frozen against the closing episode. The live row carries only the current physical state.

A6. Must-Not-Change — Regression Guard GUARD

Adjacent behaviour that must not changeWhy it's in the blast radius
Money attribution stays stamped at txn time — no current-custodian join is introduced for any money decision.The whole "no dilution" guarantee rests on this; the new device_id column is additive only.
Reconciliation settles a PENDING due against the stamped recoverable_due.csp_id (the original CSP).A re-dispatch must never route the old CSP's due to the new CSP.
Penalties (lost / damage / write-off / recovery) immutable — append-only, no reversal, idempotent by source_event_id.Episodes archive these; archiving must not rewrite or reverse them.
Exposure = per-CSP authoritative count; SD = per-CSP scalar pool. No double-count across CSPs.A device moving between CSPs must not draw/credit the other's pool.
Forward-only within an episode; a device that is NOT re-dispatched stays terminal exactly as today.Episodes add a boundary, they don't loosen in-episode irreversibility.
device_commissioned_at constant across episodes (device age / depreciation clock).Age-band depreciation must stay device-level.
NBREC one-open-recovery-per-device check (device_id unique).Correct physical invariant — not part of this change.

A7. Rules, Invariants & Edge Cases WHAT

A7.1 Rules & invariants

Rule / invariantStatement
INV — one live custodianThe live netbox_custody row has exactly one current custodian (or a Wiom-inventory holder between episodes).
INV — episode immutabilityThe episode log is append-only; one row per (device, CSP) tenure; never overwritten or re-attributed.
INV — freeze-before-moveAn episode's liability + disposition is frozen to the log before the live row can be re-stamped to a new CSP.
INV — forward-only within episodeWithin one episode the state machine is forward-only; re-dispatch is a new episode, not a reversal.
INV — liability never follows the deviceA booked/pending liability stays with the episode's csp_id; re-dispatch cannot move it.
RULE — episode resetNew episode: counters zeroed, was_ever_deployed=false, fresh created_at; device_commissioned_at preserved.
RULE — device_id on money rowsEvery device-driven money entry carries a first-class device_id + csp_id.

B5. Acceptance Criteria — Verification Layer HOW

LOGIC_01 (logic · happy): Re-dispatch as a new episode
Given a RETURNED device that had been held by CSP-A
When it is re-dispatched to CSP-B
Then the episode for CSP-A is closed and snapshotted to the episode log
And the live row is re-stamped to CSP-B at PENDING_CSP_RECEIPT with counters zeroed and was_ever_deployed=false
And device_commissioned_at is unchanged
INVARIANT_01 (A7.1): Liability never follows the device
Given a PENDING loss/damage/carry-fee due booked under CSP-A
When the device is re-dispatched to CSP-B and reconciliation runs
Then the due settles against CSP-A's wallet/SD, never CSP-B's
INVARIANT_02 (A7.1): Freeze-before-move
Given an episode being closed
Then its disposition + liability refs are written to the immutable episode log before the live row is re-stamped
LOGIC_02 (logic · happy): Lost survives re-dispatch
Given a device LOST under CSP-A, 3PL-recovered to warehouse, re-dispatched to CSP-B
Then CSP-A's lost-devices list still shows the device (from the episode log)
And CSP-B sees a clean device with no inherited liability
COMPUTE_01 (computation · boundary): Carry-fee exemption on new episode
Given a re-dispatched device CUSTODIED under CSP-B (was_ever_deployed=false)
When it sits idle past the carry-fee threshold without being deployed
Then no carry fee accrues for CSP-B until CSP-B first deploys it
LOGIC_03 (logic · happy): Per-(csp, device) money trail
Given wallet/deposit/entitlement entries now carry device_id
When CSP-A queries a device it once held
Then every money txn for (CSP-A, device) is retrievable
REGRESSION_01 (A6): No current-custodian join for money
Given any settlement / reconciliation / liability path
Then it uses the stamped csp_id on the ledger row, never the live netbox_custody custodian
REGRESSION_02 (A6): Non-re-dispatched device unchanged
Given a RETURNED device that is never re-dispatched
Then it stays terminal exactly as today; no episode re-opens
REGRESSION_03 (A6): No exposure / SD double-count
Given a device moving from CSP-A to CSP-B
Then CSP-A exposure −1, CSP-B exposure +1 at receipt, and neither SD pool draws the other's
