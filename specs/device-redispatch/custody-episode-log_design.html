Custody-Episode Log — Detailed Design

The immutable per-tenure history that lets netbox_custody stay a single live row while the device passes through many CSPs — preserving every custodian's liability and audit trail. Grounded in the current schema (V5–V18) and dispatch/receipt code.

Owner: Jaivin Prajapati  ·  Reviewers: Dhruv · EM  ·  Status: Draft for detailed review

1. Objective

Give every device a complete, immutable, per-custodian history — so that re-dispatching a device to a new CSP never dilutes the prior CSP's liability or audit trail, and the live custody record always reflects only current physical custody. One device = one live row + N immutable episodes.

It separates the two axes that today's single row conflates:

  • Physical status — where the device is & who holds it now → the live netbox_custody row (moves with the device).
  • Liability status — what each CSP owed / was charged / was credited for the device → the custody_episode log (frozen per tenure).

3. Core model

A device's life is a chain of episodes. An episode = one continuous tenure of the device under one custodian, from dispatch to terminal disposition.

The open episode IS the live row. At any time a device has exactly one open episode — and that open episode is the live netbox_custody row (tagged with current_episode_id). The custody_episode log holds only closed episodes (immutable). So there is one source of truth for "now" (the live row) and one immutable record per finished tenure (the log) — never two live copies.

Why a second row can't exist (the constraint that forces this)

netbox_custody.device_id is the PRIMARY KEY, reinforced by partial-unique idx_netbox_custody_active_device ON (device_id) WHERE status NOT IN ('RETURNED','DAMAGED','LOST','WRITTEN_OFF'). So a re-dispatch cannot insert a second row — it must re-stamp the existing row. Re-stamping overwrites the prior tenure → which is exactly why the tenure must be snapshotted to the log before the row is reset ("freeze-before-move").

Identity — episode_id is universal-level

episode_id is a universal, system-level identifier — globally unique across all devices and CSPs, allocated from a system-wide episode registry/sequence. It is not a device-scoped counter; device_id and csp_id are attributes of an episode, and episode_seq is only a per-device display ordinal (not identity). The universal episode_id is minted at episode open (dispatch), stored on the live row as current_episode_id, and stamped on every event, audit row, and money-ledger entry during the tenure — so the per-tenure trail is one clean filter by episode_id, robust even when the same device returns to the same CSP twice.

Two ways an episode closes (the disposition depends on who returned it)

A device reaches Wiom — and the episode ends — by exactly two paths. Both funnel the live custody state to RETURNED (physical), but the episode's liability disposition differs:
Pathreturned_by_typePhysical (live row)Episode liability_disposition
A · Returned by CSPCSPRETURNEDRETURNED — CSP fulfilled custody; clean (₹50 if CRP-recovery)
B · Returned by 3PL3PLRETURNEDLOST — the device was LOST for the CSP (CSP failed to recover from customer); 3PL recovered it. CSP's loss penalty stands.

Per Part 1, a 3PL return is only valid for a device that is LOST with lost_reason = NOT_RECOVERED_FROM_CUSTOMER. So path B's episode is stored as LOST (carrying that lost_reason), even though the device is physically back at the warehouse. The custody state machine reflects this as the P1 edge LOST → RETURNED (3PL recovered).

7. Liability correlation — episode_id on the ledgers

Money attribution is already safe (every ledger stamps csp_id at txn time; no path re-derives the current custodian). This change adds queryability, not correctness:

LedgerTodayAdd
recoverable_duecsp_id ✓ device_id ✓episode_id NEW

deposit_ledger_entriescsp_id ✓ netbox_id onlyepisode_id + device_id
wallet_ledger_entriescsp_id ✓ device only in remarks JSON (carry-fee = comma list)episode_id + first-class device_id
entitlement_ledger_entriescsp_id ✓ device in program_ref/JSONepisode_id + device_id

Per-(CSP, device, tenure) money statement = ledger rows filtered by episode_id — unambiguous even if the same device served the same CSP across two separate tenures.

Guard (must-not-change): stamping episode_id is additive. No settlement/reconciliation decision may read the live custodian — reconciliation still settles a due against its stamped recoverable_due.csp_id. The episode log references dues; it never moves or duplicates money.

8. Workflows

W1 · Episode OPEN (dispatch)
Trigger: DEVICE_ORDER_DISPATCHED (device assigned to CSP-X). Steps:
  1. Mint episode_id; compute episode_seq = (max prior seq for device)+1.
  2. Re-stamp the live row (§5.2): csp_id=X, holder_type=CSP, status=PENDING_CSP_RECEIPT, current_episode_id=new, counters reset, was_ever_deployed=false, fresh created_at/dispatched_at; preserve device_commissioned_at.
  3. No custody_episode row yet — the open episode is the live row.
For a first-ever dispatch opening_trigger=INITIAL; for a re-dispatch RE_DISPATCH (the live row already exists in WIOM_INVENTORY).
W2 · Episode ACTIVE (tenure)
Normal custody transitions on the live row (CUSTODIED→DEPLOYED→IDLE→…), each tagged current_episode_id. Every emitted event, custody_audit_log row, and money-ledger entry carries (episode_id, csp_id, device_id). was_ever_deployed set true on first CUSTODIED→DEPLOYED within this episode.
W3 · Episode CLOSE (return accepted) — the critical transaction
Trigger: the device is accepted back to Wiom (custody → RETURNED, per Part 1) by one of the two paths — A · returned by CSP or B · returned by 3PL (see §3). All steps in ONE transaction (freeze-before-move):
  1. Read returned_by_type → set closing_trigger (RETURNED_BY_CSP / RETURNED_BY_3PL) and liability_disposition (CSP→RETURNED, 3PL→LOST carrying the lost_reason). physical_outcome=RECOVERED_TO_WAREHOUSE in both.
  2. Compute the liability snapshot: pull totals + due refs for episode_id from the ledgers; set liability_open_at_close.
  3. Write the immutable custody_episode row (all §6 columns from the live row + snapshot).
  4. Detach the live row: holder_type=WIOM_INVENTORY, current_episode_id=null.
Other dispositions (DAMAGED / WRITTEN_OFF / TRANSFERRED_OUT / NEVER_RECEIVED) close the episode the same way, carrying their own liability disposition. If the device is not re-dispatched, it stays in WIOM_INVENTORY with the episode logged.
W4 · Episode RE-OPEN (re-dispatch)
Trigger: a new DEVICE_ORDER_DISPATCHED for a device currently in holder_type=WIOM_INVENTORY. → Run W1 with opening_trigger=RE_DISPATCH. The loop repeats for every onward CSP.
W5 · Visibility reads
  • Old-CSP lost list: custody_episode WHERE csp_id=A AND liability_disposition IN (LOST_CSP_CUSTODY, LOST_CUSTOMER_NONRECOVERY).
  • Ever-held / returned: custody_episode WHERE csp_id=A (+ live row if currently held).
  • Device timeline: all episodes for device_id (by episode_seq) + custody_audit_log + the live row.
  • Per-(csp, device) money trail: ledger rows by episode_id.
W6 · Reconciliation / money interaction
Unchanged. Dues stay keyed by stamped csp_id; reconciliation settles a PENDING due against the original CSP's wallet/SD regardless of where the device now sits. episode_id is drill-down only.
W7 · Path B detail — LOST → 3PL → warehouse
This is closure path B. The device was LOST for CSP-A (failed to recover from customer). 3PL recovers it to the warehouse → custody RETURNED. The episode closes with closing_trigger=RETURNED_BY_3PL, liability_disposition=LOST (penalty stays with CSP-A, carrying lost_reason) AND physical_outcome=RECOVERED_TO_WAREHOUSE. The two axes captured independently — then W4 re-dispatches the physically-recovered device to CSP-B with no inherited liability.
W8 · Wiom-inventory gap
Between W3 and W4 the device is holder_type=WIOM_INVENTORY, not counted in any CSP's exposure/free-stock/prior-POD. (Warehouse sub-states are Pyrops.)

9. Invariants

  • One open episode per device = the live row. Closed episodes live only in the log.
  • Immutability: a custody_episode row is never updated after write.
  • Freeze-before-move: the episode row is written before the live row is detached/re-stamped — atomically.
  • Forward-only within an episode; re-dispatch is a new episode, never a terminal reversal.
  • Liability never follows the device: a booked/pending due stays with the episode's csp_id.
  • Episode_id completeness: every money/audit row created during a tenure carries that tenure's episode_id.
  • device_commissioned_at constant; was_ever_deployed resets per episode.

10. Edge cases

CaseHandling
Dispatched but never received (timeout)Episode closes closing_trigger=NEVER_RECEIVED, received_at=null; no exposure was ever counted.
Same device, same CSP, second tenureA distinct episode (new episode_id, higher episode_seq) — money cleanly separable by episode_id.
Pending due unsettled at closeliability_open_at_close=true; due still settles at the original CSP's reconciliation.
CSP exit while a device is in WIOM_INVENTORYDevice isn't the exiting CSP's (holder=WIOM_INVENTORY) → correctly excluded; its prior episode under that CSP remains in the log.
Crash between snapshot and re-stampSingle transaction → either both or neither; no half-closed episode.
Legacy stuck devicesBackfill one CLOSED episode per stuck (device, csp) + stamp episode_id onto historical money rows. migration

11. Open decisions (for review)

  1. csp_id nullability on the live row. When holder_type=WIOM_INVENTORY, set csp_id=null (needs the NOT-NULL constraint relaxed) or keep last csp with holder as authoritative? Recommend: nullable + holder authoritative.
  2. Open at dispatch vs at receipt. Episode opens at dispatch (captures NEVER_RECEIVED). Confirm this vs opening only at CUSTODIED.
  3. Episode_id — DECIDED: universal-level globally-unique id, stamped on all five money ledgers + audit (not device-scoped).
  4. Closure disposition — DECIDED: driven by returned_by_type — CSP return → episode RETURNED; 3PL return → episode LOST (per §3).
  5. Snapshot totals vs pure refs. Keep denormalised totals (group D) for fast visibility, or refs-only with on-read aggregation? Recommend keep totals + refs.
  6. Transfer (CUSTODY_TRANSFERRED) as an episode boundary? A logical CSP-A→CSP-B transfer (device stays DEPLOYED, no physical move) — close + open an episode, or a separate "logical re-attribution" path? Recommend: close epN (TRANSFERRED_OUT) + open epN+1 for symmetry.

Identify every API used in front-end flows that reads device→CSP / custody state / lost / returned, and define the changes (episode-aware reads, history endpoints).
