Front-End API Impact — Re-Dispatch / Custody-Episode Model

Every device-related API the CSP app calls, traced to its backend data source, and whether the custody-episode model requires a change. Two buckets: A = reads netbox_custody for terminal/past device states → must also consult custody_episode_log; B = active-only or a different store → no change. Plus one source-of-truth fix on earnings.

FE: wiom-csp-app-apr09 @ development (c300cfa0)  ·  Backend: csp-os-yaml @ prod (eddd75d7e)  ·  Owner: Jaivin Prajapati  ·  Reviewers: Tech · EM

1. The test (what actually triggers a change)

The episode model only moves a device off the CSP's live netbox_custody row once it is terminal (RETURNED / LOST / DAMAGED / WRITTEN_OFF) and re-dispatched. So the test is not "does it read netbox_custody" — it is "does it surface a device in LOST or RETURNED (terminal) state from netbox_custody?" If yes → the device leaves the live row on re-dispatch → the API must consult the episode log → Bucket A.

Code-decidable: findActiveDevicesByCspId = WHERE csp_id = ? AND status NOT IN ('RETURNED','DAMAGED','LOST','WRITTEN_OFF') (NetboxCustodyRepository.java:25) — terminal-excluded. Endpoints on this query are active-only (Bucket B). Endpoints that read all statuses or a specific device by id can see terminal states (Bucket A).

3. Earnings — carry-fee source fix CHANGE (different)

GET assurance/earnings (AssuranceStripFacadeService.java:413) builds the earnings strip. Bonus and pickup are read from the Compensation ledger (period-filtered — lines 453–462, historical ✓). Carry fee is the exception:

Lines 464–469 (verbatim intent — code comment on :464): "Carry fee: computed from ACS devices × Comp rate (NOT from ledger)"
idleDevices = acs.devices().filter(carryFeeActive && idleDays>0) · carryFeeAbsPaise = Σ(rate × idleDays)

So the carry-fee number in earnings is recomputed live from netbox_custody active devices. A device charged carry fee, then returned, drops out of acs.devices() → its carry fee vanishes from earnings. (Pre-existing inconsistency vs bonus/pickup; the episode model makes it bite more often.)

Fix: source the earnings carry-fee from the carry-fee transaction ledger (entitlement_ledger CARRY_FEE_DEBIT), like bonus/pickup — it holds the entry regardless of the device's current status.

Refinement (to enable a break-up): the entitlement CARRY_FEE_DEBIT entry must also record the count of devices and the rate of fee applied at that moment, so the "N devices × ₹rate/day" break-up is reconstructable historically.
Why the refinement is needed (prod fact): the carry-fee entry today (CompensationEventProcessingServiceImpl.java:242-252) sets only csp_id, entry_type=CARRY_FEE_DEBIT, amount, earning_period_id, credit_sequence, program_ref — no device count, no rate field, no per-device breakdown. So a break-up cannot be drawn from the ledger as-is.
