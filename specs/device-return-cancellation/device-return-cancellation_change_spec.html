CSP Cancellation of an Initiated Device Return

The story: a CSP raised a return on a NetBox, the box went into RETRIEVAL_PENDING and Ops started preparing the pickup — then a customer walked in and the CSP wants the box back. Today there is no way back: RETRIEVAL_PENDING is a one-way door whose only exits are RETURNED or the timers that quietly mark the box LOST/WRITTEN_OFF, leaving the CSP penalised for an asset it still holds. This spec gives the CSP a "Cancel return" it can actually use — a single, tightly-gated reverse transition (T_RETURN_CANCELLED) that walks the box home to the exact state it left (IDLE or CUSTODIED), keeps every clock running across the in-between days, charges the carry fee that was genuinely due, and tells the warehouse to stand down. It refuses to undo a return the system started, and it shuts off the moment the box is marked LOST. Written from the backend's point of view, told as the journey a device takes. Fundamental state-machine change → EM review before any architectural call.

Author (PM): Jaivin Prajapati  ·  Reviewers: Dhruv · EM  ·  Tier: Full

Quick Check

7-line triage.
What is changing?
A new T_RETURN_CANCELLED transition lets a CSP cancel its own RETRIEVAL_PENDING and go back to the exact prior state (IDLE or CUSTODIED). System-initiated retrievals (no-deployment recall, exit, swap-out, deactivate-and-return) are not cancellable. Allowed only while still RETRIEVAL_PENDING (before LOST/write-off).
What triggered it?
CSPs change their mind after raising a return; today there is no way back — the device drifts to LOST and the CSP is wrongly penalised for an asset it still holds.
Blast radius
Custody state machine (new reverse edge + 2 new columns), carry-fee/idle clock continuity, no-deployment recall clock, a one-time carry-fee catch-up, a new cancellation event that aborts the Ops pickup. Consumers: Compensation, Pyrops/Ops, audit.
Reversible?
Partial — the new edge is initiator-gated and window-bounded, but it is a state-machine expansion (architectural review required).
Money / PII / migration?
Money Y (one-time carry-fee catch-up on IDLE restore; no SD movement; no liability reversal) · PII N · Migration N (forward-only; existing stuck RETRIEVAL_PENDING devices unaffected).
OS impact / sign-off?
Asset Custody, Compensation, ESR/Pyrops — all Pending. CL OS / Payment / SPR — not impacted.

A2. Why This Change WHAT

QuestionAnswer
What's wrong?Once a CSP raises a return, the device enters RETRIEVAL_PENDING and the state machine offers no way back — its only exits are RETURNED, or the timers that mark it LOST (P20) / WRITTEN_OFF. A CSP that changes its mind (keeps a customer, redeploys the box) has no in-system action; the device ages out to LOST and the CSP is charged device value + carry fees for an asset it still physically holds.
Who experiences it?CSPs (penalised for a return they wanted to undo), Ops/finance (LOST/write-off entries that don't reflect reality, manual reversals with no supported path).
Cost of leaving it?Wrong LOST/write-off liability, manual back-office correction with no audited transition, CSP trust erosion.

(3) Cancelling after the device has left RETRIEVAL_PENDING (LOST/WRITTEN_OFF).

Part B

HOW — Detailing

The detail engineering needs to build and verify the delta. Still business behaviour — diagrams describe logic, never architecture.

B1. The Journey — Cancelling a Return, Step by Step Conditional — flow changes

Picture a NetBox that has been sitting IDLE in a CSP's shop for a few days. Last Tuesday the CSP tapped Return in the app — that fired initiateReturn, pushed the box into RETRIEVAL_PENDING, stamped retrieval_start_date, quietly paused the carry-fee fields, and sent DEVICE_RETURN_REQUESTED so Ops could schedule a pickup. Today a new customer walks in and the CSP needs that box back. Here is what happens behind the glass when they tap Cancel return — the backend never changes a thing until it has asked, in order, four questions.

Step 1 · The CSP asks to cancel

The app calls POST /api/asset-custody/devices/{deviceId}/cancel-return (CSP-permissioned). ACS loads the single netbox_custody row for that device_id and takes an optimistic-lock read on its version — so if a nightly timer touches the same row mid-cancel, one of them will lose cleanly rather than corrupt the state.

Step 2 · "Did you start this return?"

The first guard reads retrieval_initiator. If it says SYSTEM — the box was pulled into RETRIEVAL_PENDING by the 45-day no-deployment recall (T_RECALL_CUSTODIED), by an exit, or by a swap-out — ACS stops here and the app would not have shown the Cancel button in the first place. Only a CSP-started return (retrieval_initiator = CSP) gets through. Ours did, so we continue.

Step 3 · "Is it too late?"

The second guard checks the box is still in RETRIEVAL_PENDING. If one of the timers had already fired overnight — the P20 window flipping it to LOST, or the write-off sweep — then in the system's eyes the box has already left the CSP's hands, and ACS answers CANCEL_TOO_LATE. The cancel window is exactly "until the box is marked LOST," and not a moment later.

Step 4 · "Where does it go home to?"

ACS reads pre_retrieval_status — the resting state the box was in when the return was raised, stamped at that moment so we never have to guess. Two roads lead out of here.

Step 5a · The box was CUSTODIED (a fresh box, never deployed)

ACS sets status = CUSTODIED and we are almost done — because the clock that matters here, the 45-day no-deployment recall, was never paused in a way that loses time. That recall hunts for devices via findNeverDeployedCustodiedBefore, which measures age from the row's immutable created_at. The days the box spent in limbo were always counted; restoring CUSTODIED simply makes the box visible to the recall sweep again. So if those limbo days pushed the box past 45 days old, the very next sweep re-recalls it immediately — the CSP cannot park a box in RETRIEVAL_PENDING to dodge the recall. No carry fee applies (CUSTODIED boxes never accrue it). Nothing else moves.

Step 5b · The box was IDLE (it had been deployed before)

ACS sets status = IDLE. The idle clock, like the recall clock, never actually lost time: initiateReturn preserves idle_start_date (it only zeroes the carry-fee counters), so the box's idle age already includes the limbo. The one thing that needs care is the money. Two sub-stories:

  • (a) Carry fee was not yet due. The box's idle age — limbo included — is still under the P19 threshold. The catch-up computes to zero; ACS just re-activates accrual and the daily job picks it up from here. The CSP pays nothing extra.
  • (b) Carry fee had become due. Counting the limbo, the box has crossed P19 and would have been accruing carry fee had it stayed IDLE. So ACS runs one off-cycle accrual — the very same mechanism the daily job uses — emitting CUSTODY_CARRY_FEE_ACCRUED for exactly the units that came due across the limbo, capped at the hard cap, which Compensation turns into the normal CARRY_FEE_DEBIT. It then sets last_accrual_date = today so the daily job continues cleanly and never double-charges. The CSP is charged precisely what it would have paid by simply leaving the box idle — no reward for the round-trip, no penalty either.

Step 6 · Tell the warehouse to stand down

Ops began preparing a pickup the moment the box hit RETRIEVAL_PENDING. So ACS emits DEVICE_RETURN_CANCELLED (device_id, csp_id, the state it was restored to, timestamp). Pyrops/Ops consume it and drop the box from the pickup queue — the retraction the original DEVICE_RETURN_REQUESTED never had.

Step 7 · The box is home

ACS writes one custody_audit_log row (RETRIEVAL_PENDING → IDLE/CUSTODIED, triggered_by = csp, reason = CSP_RETURN_CANCELLED, carrying both ids). Because RETRIEVAL_PENDING, IDLE and CUSTODIED are all inside the exposure set, the box never left the CSP's exposure — so no CSP_EXPOSURE_CHANGED is emitted. The Cancel CTA disappears, and the CSP redeploys the box to its new customer that same afternoon. If it changes its mind again next week, it can raise a fresh return — every initiate and every cancel is its own audited line.

Then the device returns to CUSTODIED, no exposure event is emitted, and a DEVICE_RETURN_CANCELLED event is published
COMPUTE_01 (computation · boundary): No-deployment clock counts the limbo
Given a CUSTODIED device with created_at 40 days ago, in RETRIEVAL_PENDING for 6 days (P_ACO_01 = 45d)
When the CSP cancels on day 46-from-creation
Then the next recall sweep immediately re-recalls it (created_at < now − 45d) — the limbo was counted, not reset
LOGIC_02 (logic · happy): Cancel restores IDLE, no fee due
Given an IDLE device whose idle age + limbo is still below P19
When the CSP cancels
Then the device returns to IDLE, the idle clock resumes inclusive of the limbo, and the carry-fee catch-up computes to zero
COMPUTE_02 (computation · boundary): IDLE restore with carry-fee catch-up
Given an IDLE (was_ever_deployed) device whose idle age + limbo crosses P19 by N accruable days
When the CSP cancels
Then exactly N carry-fee units (capped at the hard cap) are charged once via CUSTODY_CARRY_FEE_ACCRUED, last_accrual_date = today, and daily accrual resumes — no double-charge
REGRESSION_01 (A6): System recall is not cancellable
Given a device put into RETRIEVAL_PENDING by T_RECALL_CUSTODIED (retrieval_initiator = SYSTEM)
When the CSP attempts cancel
Then it is refused; the device stays RETRIEVAL_PENDING
REGRESSION_02 (A6): Cancel after LOST is refused
Given a device whose P20 LOST timer has already fired
When the CSP attempts cancel
Then it is refused with CANCEL_TOO_LATE; no reverse transition occurs
INVARIANT_01 (A7.1): Exposure-neutral
Given any successful cancel (IDLE or CUSTODIED restore)
Then no CSP_EXPOSURE_CHANGED is emitted and the CSP exposure count is unchanged
INVARIANT_02 (A7.1): SD / liability untouched
Given any successful cancel
Then no deposit_ledger entry is written, sd_balance is unchanged, and no prior liability is reversed
EDGE_01 (edge · race): Cancel vs timer
Given a cancel and the LOST timer commit near-simultaneously
Then the optimistic lock on version serialises them; if the timer wins, cancel returns CANCEL_TOO_LATE; if cancel wins, the timer skips the now-non-RETRIEVAL_PENDING device
EDGE_02 (edge): Toggle does not dodge carry fee
Given a CSP that cancels and re-initiates a return repeatedly across an idle window
Then the cumulative carry fee equals that of a device left IDLE the whole time (each cancel runs the catch-up)
REGRESSION_03 (A6): Forward exits intact
Given a RETRIEVAL_PENDING device that is never cancelled
Then handover→RETURNED, P20→LOST and the write-off window behave exactly as before
