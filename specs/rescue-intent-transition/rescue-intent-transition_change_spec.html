Rescue-Intent Transition (T_RESCUE) — resolve to ACTIVE or PAUSED by ISP window

On CAEO_RESCUE_INTENT, CLOS today always moves a PENDING_DEACTIVATION connection to PAUSED. This change makes the target state depend on the connection's live ISP window. Code-derived; no inference. Business behaviour only — engineering owns implementation.

Author: Jaivin Prajapati  ·  Reviewers: Varun, Dhruv (Engineering)  ·  Tier: Full (touches a state machine)

Quick Check

What is changing?
T_RESCUE target state: unconditional PAUSED → conditional ACTIVE (window in future) / PAUSED (else).
What triggered it?
Bug — post-deactivation recharge leaves connection PAUSED with a live future ISP window; renewal claim blocked.
Blast radius
CLOS handleCaeoRescueIntent + ConnectionStateMachine; outbound ClConnectionRescued. RV gates read but unchanged.
Reversible?
Yes — revert the handler + state-machine entry; no data migration.
Money / PII / migration?
Money: indirect (unblocks recharge commission claim) · PII: No · Migration: No.
OS impact / sign-off?
CL state-machine amendment — Pending (Varun, Dhruv). RV: No change.
Tier
Full.

A2. Why This Change WHAT

Why (from feedback): The block surfaces at RV Gate 2 (GUARD-RV-04 / guardNoActiveWindow), which rejects a recharge confirmation when a recharge_gate with expired_emitted=false AND window_end > now already exists — error RV_GATE2_DUPLICATE_WINDOW. After rescue the connection is PAUSED yet its ISP window_end is already in the future, so the only RV exit from PAUSED is blocked as a duplicate window. We do not modify or relax Gate 2. Correcting the rescue transition to ACTIVE makes CLOS emit CL_CONNECTION_ACTIVATED, which TAS's race-window fallback resolver (process(ClConnectionActivated)) consumes to resolve the recharge candidate (reason CONNECTION_REACTIVATED) and disburse commission — a path that does not go through RV at all. Gate 2 keeps its exact logic; it simply stops being the only exit.
QuestionAnswer
What's wrong?Customer requests deactivation, then pays post-facto to save the connection. CLOS fires CAEO_RESCUE_INTENT; handleCaeoRescueIntent always moves PENDING_DEACTIVATION → PAUSED. The recharge has already set latest_recharge_window_end in the future, so CL sits PAUSED while the ISP window is live — a conflicting state. RV Gate 2 then rejects the renewal as a duplicate window until window_end passes.
Who experiences it?Customers who pay to save the connection; CSPs whose recharge commission claim is stuck until the window boundary.
Cost of leaving it?Claim blocked for days (until window_end / next expiry sweep); connection state inconsistent with supply. Observed live (e.g. ca34d571-…, ec59cc21-…).

Allowed targets from PENDING_DEACTIVATIONConnectionStateMachine.VALID_TRANSITIONS = {DEACTIVATED (T8), PAUSED (T_RESCUE)}. ACTIVE is not permitted.
Renewal arrives while connection is PAUSED with future windowRV Gate 1 (guardConnectionPausedOrActive) passes. RV Gate 2 (guardNoActiveWindow) finds the existing gate (expired_emitted=false, window_end > now) and rejects → RV_GATE2_DUPLICATE_WINDOW. No RechargeConfirmed; pause never clears until window_end elapses.
TAS recharge candidate while connection is PAUSEDStuck ACTION_REQUIRED / UNCLAIMED. Its two resolvers cannot fire: the RV path (process(SupplyRechargeResolved)) needs a RechargeConfirmed that Gate 2 blocks; the CL path (process(ClConnectionActivated)) needs the connection to be ACTIVE, which rescue-to-PAUSED never produces. (Live: ec59cc21-….)

A4. Desired Behaviour WHAT

Trigger / conditionDesired observable behaviour
CAEO_RESCUE_INTENT & latest_recharge_window_end > nowConnection moves PENDING_DEACTIVATION → ACTIVE. No pause fields set. ClConnectionRescued carries new state ACTIVE. State matches the live ISP window; no duplicate-window renewal is needed.
CAEO_RESCUE_INTENT & latest_recharge_window_end ≤ now or nullConnection moves PENDING_DEACTIVATION → PAUSED (current behaviour, unchanged): pause_reason=RESCUE, P76 reset, pause_count++.
The 4 rescue gates & RV gatesUnchanged — same guards, same RV Gate 1 / Gate 2 logic.

A6. Must-Not-Change — Regression Guard GUARD

Explicit: RV Gate 2 is not relaxed. The fix corrects the rescue transition only.
Adjacent behaviour that must not changeWhy it's in the blast radius
RV Gate 2 (guardNoActiveWindow, GUARD-RV-04) logic is unchanged — still rejects a genuine duplicate recharge confirmation (active future window) → RV_GATE2_DUPLICATE_WINDOW. The fix touches no RV code; the rescue resolution routes through the CL-activation path, not RV."Do not relax the gate." Duplicate-window protection must stay; the fix must not depend on weakening it.
RV Gate 1 (guardConnectionPausedOrActive, GUARD-RV-03) still accepts PAUSED or ACTIVE.The new ACTIVE resting state must remain acceptable to Gate 1.
The 4 rescue gates a–d (guardConnectionInState, guardP77NotExpired, guardDeactivationReasonRescueEligible, guardPriorCaeoStateValid) unchanged.Same handler; easy to disturb. Eligibility must be byte-for-byte.
PENDING_DEACTIVATION → PAUSED path when window is past/null is byte-for-byte unchanged.Only the future-window case is added; the existing branch must be preserved.
PENDING_DEACTIVATION → DEACTIVATED (T8) and DEACTIVATED-as-terminal unchanged.Shares the same state-machine entry being edited.
