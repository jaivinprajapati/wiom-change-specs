CSP-Level Device-Ordering Gate — Ops manual flag on csp_exposure

A new, highest-priority gate in the device-order eligibility engine: a per-CSP manual flag, set by Ops, that decides whether device ordering is permitted for that CSP at all. There is no system logic behind the flag — it is a governance switch Ops toggles by hand. If the flag is ON, the engine runs the existing eligibility gates (Quality → Enforcement → Capacity → SD-floor → custody caps → prior-receipt) exactly as the Device Order Eligibility spec defines. If the flag is OFF, the engine short-circuits immediately: device ordering is blocked, no further gate is evaluated, and the front end does not render the device-ordering card at all (not a disabled / "blocked" card — the card is absent). The flag is stored as a new column on the existing csp_exposure table in the Payment & Settlement DB — the table already tied to the CSP's device-ordering exposure — and is read by the ACS eligibility engine as Gate 0.

Author: Jaivin Prajapati  ·  Gate owner: Asset Custody (ACS)  ·  Data owner: Payment & Settlement  ·  Tier: Light
Tier: Light — A1, A2, A5, A8, B5 + Workflow + Wired-layers. The change in one line: add a per-CSP, Ops-set device_ordering_allowed column to the existing Payment csp_exposure table and read it as Gate 0 — a short-circuit ahead of every existing eligibility gate; flag OFF ⇒ hard block + FE hides the device-ordering card; flag ON ⇒ engine behaves exactly as the parent spec.
Rows: Required — every row filled or marked N/A with a reason.
Decisions taken (PM): table = existing csp_exposure (Payment & Settlement DB); default = BLOCK (missing/false ⇒ ordering blocked); enforcement = eligibility read API only (order create/approve unchanged); scope = device ordering AND the connection verdict; Ops surface = direct DB / SQL runbook (no new endpoint).

Quick Check

7-line triage. Filled last, after the body is complete.
What is changing?
One new gate in the device-order eligibility engine. (1) New column on csp_exposure (Payment & Settlement DB): device_ordering_allowed BOOLEAN NOT NULL DEFAULT false + audit columns (ordering_block_reason, ordering_updated_by, ordering_updated_at). One value per CSP. (2) New "Gate 0" at the very top of the eligibility read: load the flag for the requesting CSP; if it is false (or no row) → return a hard block with a distinct verdict ORDERING_DISABLED and stop — no Quality / Enforcement / Capacity / SD-floor / custody-cap evaluation. If true → fall through to the existing gates unchanged. (3) The same flag gates the connection verdict the engine produces on the assurance strip — flag OFF ⇒ CSP not eligible for new connections either. (4) FE behaviour: ORDERING_DISABLED renders differently from a normal hard-block — the front end hides the device-ordering card entirely instead of showing a card with a block reason.
What triggered it?
Ops needs a manual, per-CSP kill-switch for device ordering, independent of all the computed gates — to stop ordering for a CSP under review, in a paused region, or pending a commercial decision — without writing new system logic. Today there is no per-CSP "allowed to order at all" switch; the only per-CSP ordering hook in code (DeviceOrderGuards.checkCspEligibilityForOrdering) is unused and has no source of truth behind it.
Blast radius
Payment & Settlement: new column on csp_exposure + migration. ACS: Gate-0 read at the top of the eligibility engine, new ORDERING_DISABLED verdict, connection-verdict gating. FE: the device-ordering card render path (gateway assurance strip + CSP App) gains one branch — hide on ORDERING_DISABLED. No new events. No change to order create / approve. No change to any other OS's gates (Gate 0 short-circuits before them).
Reversible?
Yes. Data-driven — set every CSP's flag to true and the engine behaves exactly as the parent spec. Code-side, Gate 0 can be feature-flagged off. The column + migration are additive.
Money / PII / migration?
No money. No PII. Yes — a data backfill is required: because the default is BLOCK, every currently-live CSP must be set device_ordering_allowed = true before Gate 0 is enabled, or device ordering halts fleet-wide. See §A5 + the runbook in §B5.
OS impact / sign-off?
Payment & Settlement OS: owns the csp_exposure table — add the column. Asset Custody OS: add Gate 0 to the provisioning-engine gate list. CSP App / Gateway: confirm the card-hide branch. Quality / Capacity / Enforcement / Demand-Allocation OS: no change (Gate 0 runs before them).

A2. Why This Change WHAT

What is expected: Observable trigger, who is affected, cost of leaving it.
QuestionAnswer
What's wrong / missing today?The eligibility engine has only computed gates — Quality, Enforcement, Capacity, SD-floor, custody caps, prior-receipt (per the parent spec). There is no manual, per-CSP "is this CSP allowed to order devices at all" switch. When Ops needs to stop a specific CSP from ordering — under commercial review, in a paused area, flagged for misuse, or not yet cleared — there is no lever short of changing one of the computed inputs (indirect, side-effects, may not even block ordering). The one per-CSP ordering hook in code, DeviceOrderGuards.checkCspEligibilityForOrdering(eligible, cspId, reason), is referenced only in tests; nothing feeds its eligible argument in production.
Who experiences it?Ops / Asset Custody team: cannot turn device ordering off for a single CSP on demand. Wiom (risk): CSPs that should not be receiving devices can still order them — no gate expresses "Ops says no". CSPs: a CSP that should be blocked still sees the ordering card and can attempt an order, getting a confusing computed-gate failure instead of a clean "ordering is not available for you".
Cost of leaving it as-is?Every per-CSP ordering stop is a manual, ad-hoc engineering or data intervention with no single source of truth and no audit trail. Device-shipment risk for flagged CSPs stays open. The intended FE experience ("don't show the card") cannot be delivered because the backend has no signal distinguishing "Ops disabled ordering for this CSP" from the ordinary computed block reasons.

A5. The Delta WHAT

What is expected: One row per atomic change: what changes → before → after → why.
What changesBeforeAfterWhy
New flag column on the existing csp_exposure table (Payment & Settlement DB), migration V29 The csp_exposure table holds the CSP's device-ordering exposure state. It has no per-CSP ordering-permission flag. Add to csp_exposure: device_ordering_allowed BOOLEAN NOT NULL DEFAULT false (default = BLOCK), plus audit-by-convention columns ordering_block_reason VARCHAR(255), ordering_updated_by VARCHAR(120), ordering_updated_at TIMESTAMPTZ. Migration V29__add_device_ordering_allowed_to_csp_exposure.sql in csp-payment-settlement-service. One value per CSP. Reuses the table already tied to device-ordering exposure (no new table, no new ownership). DEFAULT false encodes default-BLOCK so "no decision recorded" fails safe (blocked), not open.
Engine reads the flag — exposed on the ordering exposure path The eligibility engine already consults the CSP's exposure / SD-provisioning state from Payment when computing the SD ceiling. The flag travels on the same exposure read the engine already makes to Payment (e.g. surfaced in the exposure/SD response the ACS engine consumes), so Gate 0 needs no new cross-service call — it reads device_ordering_allowed from the data already fetched for the SD path. Keeps Gate 0 cheap and avoids a second round-trip; the flag rides the exposure read that already happens.
New Gate 0 at the top of the eligibility engine (ACS) The engine begins with the computed gates (parent spec: evaluate all gates, return the highest-priority reason). No manual pre-gate. Before any computed gate runs, read device_ordering_allowed for the requesting CSP (X-Csp-Id). If false or no row → return device verdict ORDERING_DISABLED + connection verdict ineligible, and short-circuit (do not evaluate Quality / Enforcement / Capacity / SD-floor / custody caps / prior-receipt). If true → fall through to the existing engine with zero behaviour change. A manual kill-switch has no data to compute and must dominate every computed gate. Short-circuiting is cheaper and semantically correct: when Ops says "no", the reason is "Ops said no", not whichever computed gate also happens to fail.
New device verdict value ORDERING_DISABLED + FE-suppression signal in the eligibility response Device verdict is one of: eligible (A, B) · soft-blocked (top-up payload) · hard-blocked (one priority reason). A hard-block is rendered by the FE as the ordering card with a reason chip. Add a distinct terminal verdict ORDERING_DISABLED (e.g. deviceOrder.verdict = ORDERING_DISABLED with deviceOrderingVisible = false). It is not a normal hard-block: it instructs the FE to omit the device-ordering card entirely. Block-reason code CSP_DEVICE_ORDERING_DISABLED for logs/analytics. The PM-required FE behaviour is "don't show the card at all", which differs from "show a blocked card". The backend must express the two distinctly so the FE can branch.
Connection verdict gated by the same flag Parent spec: connection verdict = COMPLIANT quality AND (Σ zone caps − held) > 0 AND absolute cap not hit. Gate 0 also governs the connection verdict: flag OFF ⇒ connection verdict = ineligible (reason CSP_DEVICE_ORDERING_DISABLED), short-circuited ahead of the computed connection checks. Flag ON ⇒ connection verdict computed exactly as the parent spec. PM decision: the flag is a whole-CSP supply switch — when ordering is off for a CSP, taking on new connections is off too. One switch, both verdicts.
Pre-go-live backfill of the live fleet (consequence of default-BLOCK) N/A — column does not exist yet. Because the default is BLOCK, on deploy every CSP with device_ordering_allowed = false (the column default) is blocked. Before Gate 0 is enabled, set device_ordering_allowed = true for the currently-live fleet (Ops-provided CSP list; bulk update, see §B5). Any CSP not on that list stays blocked by design (default-deny). One-time data step, gated ahead of enabling Gate 0. Without the backfill, default-BLOCK halts device ordering fleet-wide the moment Gate 0 ships. The backfill converts default-deny into "deny only those Ops hasn't cleared".
Ops control surface = direct DB / SQL runbook No surface. No new API or admin screen. Ops flips the flag with parameterised SQL on csp_exposure (templates in §B5): an allow and a block update, both setting ordering_block_reason + ordering_updated_by + ordering_updated_at = now(). Audit by convention via those columns + the table's existing audit trigger. PM decision — fastest to ship, no endpoint to build. The audit columns + trigger preserve a trail despite the manual workflow.
Order create / approve — no change (read-API-only enforcement) Parent spec: create checks tier + no-active-order; approve copies requested→approved. Gate enforcement is on the eligibility read the FE runs before ordering. Unchanged. Gate 0 is enforced only in the eligibility read. DeviceOrderController.createOrder / confirmDispatch / confirmReceipt are not modified. PM decision: read-API-only, consistent with the parent spec. Residual (accepted): a non-FE caller could still POST createOrder for a flag-OFF CSP — see the guard note below.
Table decision — why csp_exposure, not a new table. The flag is a per-CSP property of the CSP's device-ordering exposure, which is exactly what the Payment & Settlement csp_exposure table already represents and what the eligibility engine already reads when computing the SD ceiling. Putting the flag there means no new table, no new ownership boundary, and no extra cross-service call. (Considered and rejected: csp_zone_exposures in demand-allocation — wrong grain, per CSP×zone, and a computed-band state machine; a brand-new ACS table — an extra store and read for a value the exposure read already carries.)
Residual risk — read-API-only enforcement. Because enforcement is on the eligibility read only, the flag is a UI-gating control, not a server-side block at order submission. A non-FE caller (or a stale FE) could still create an order for a flag-OFF CSP. This matches the parent spec's stance ("order create/approve unchanged") and is accepted for v1. If a true server-side block is wanted later, feed this flag into the already-present DeviceOrderGuards.checkCspEligibilityForOrdering at DeviceOrderServiceImpl.createOrder — a small, isolated follow-up.
Why Gate 0 is an explicit exception to "evaluate all gates, return highest". The parent spec evaluates every computed gate and ranks the reasons so the CSP sees the most important computed constraint. Gate 0 deliberately does not participate: it has no computation, it changes the FE rendering (hide vs show-with-reason), and Ops intent should not be buried under a co-incident computed failure. So it runs first and returns on its own.

B5. Acceptance Criteria — Verification Layer HOW

Schema (migration V29, Payment & Settlement)

ALTER TABLE csp_exposure
    ADD COLUMN device_ordering_allowed BOOLEAN NOT NULL DEFAULT false,  -- default = BLOCK
    ADD COLUMN ordering_block_reason   VARCHAR(255),                    -- Ops note (audit-by-convention)

    ADD COLUMN ordering_updated_at     TIMESTAMP WITH TIME ZONE;
-- (existing audit / updated_at triggers on csp_exposure continue to apply)

Ops SQL runbook (direct-DB control surface)

-- BLOCK device ordering for a CSP
UPDATE csp_exposure
   SET device_ordering_allowed = false,
       ordering_block_reason   = :reason,
       ordering_updated_by     = :ops_user,
       ordering_updated_at     = now()
 WHERE csp_id = :csp_id;

-- ALLOW device ordering for a CSP
UPDATE csp_exposure
   SET device_ordering_allowed = true,
       ordering_block_reason   = :reason,
       ordering_updated_by     = :ops_user,
       ordering_updated_at     = now()
 WHERE csp_id = :csp_id;

-- PRE-GO-LIVE BACKFILL — set the live fleet to ALLOW before Gate 0 is enabled
-- (:live_csp_ids = the Ops-provided list of currently-live CSPs)
UPDATE csp_exposure
   SET device_ordering_allowed = true,
       ordering_block_reason   = 'go-live backfill',
       ordering_updated_by     = 'ops_migration',
       ordering_updated_at     = now()
 WHERE csp_id = ANY(:live_csp_ids::varchar[]);
Sequencing. Run the backfill before Gate 0 is enabled in production. Any CSP not in :live_csp_ids stays blocked by default-deny — that is intended.

Business logic

LOGIC-1: Flag OFF — engine short-circuits, FE hides the card
  Real-world: Ops has blocked device ordering for this CSP.

  Given csp_exposure.device_ordering_allowed = false for <csp_X>
  When  <csp_X> opens the ordering surface (eligibility read with X-Csp-Id = csp_X)
  Then  the device verdict = ORDERING_DISABLED
  And   deviceOrderingVisible = false
  And   the connection verdict = ineligible, reason = CSP_DEVICE_ORDERING_DISABLED
  And   NO computed gate is evaluated (no Quality / Enforcement / Capacity / SD-floor / cap work)
  And   the FE does NOT render the device-ordering card at all

  Verify:
    • Response — deviceOrder.verdict = 'ORDERING_DISABLED', deviceOrderingVisible = false;
        connection.eligible = false, connection.reason = 'CSP_DEVICE_ORDERING_DISABLED'
    • Short-circuit — engine logs/timers show no Quality, Capacity, SD-ceiling,
        or custody-cap computation for this request
    • FE — the device-ordering card element is absent from the rendered surface
        (NOT present-but-disabled, NOT present-with-reason)
    • Negative — response carries no computed hard-block reason (no QUALITY /
        CAPACITY / SD_FLOOR reason); the only reason is CSP_DEVICE_ORDERING_DISABLED
LOGIC-2: Flag ON — engine behaves exactly as the parent spec
  Real-world: normal, cleared CSP.

  Given csp_exposure.device_ordering_allowed = true for <csp_Y>
  When  <csp_Y> opens the ordering surface
  Then  Gate 0 passes and the engine evaluates the existing gates unchanged
  And   the device verdict is one of eligible(A,B) / soft-block / hard-block(reason)
  And   the FE renders the device-ordering card exactly as today

  Verify:
    • Response — verdict is NEVER ORDERING_DISABLED; deviceOrderingVisible = true
    • Parity — for the same CSP state, the verdict/A/B match the parent-spec engine
        output with Gate 0 absent (Gate 0 is a no-op when the flag is true)
    • Negative — no CSP_DEVICE_ORDERING_DISABLED reason anywhere in the response
LOGIC-3: No row / NULL exposure for the CSP — default-deny
  Real-world: a CSP with no csp_exposure row yet, or never backfilled.

  Given csp_exposure has NO row for <csp_Z> (or the flag column is unset)
  When  <csp_Z> opens the ordering surface
  Then  the engine treats the absent/false flag as device_ordering_allowed = false
  And   the verdict = ORDERING_DISABLED (same as LOGIC-1)

  Verify:
    • Response — identical to LOGIC-1
    • Negative — the engine does NOT fail open (never defaults to allowed when the
        row/flag is absent) and does NOT error/500 on the missing row

Use / edge cases

EDGE-1: Backfill correctness
  Given the pre-go-live backfill set the live fleet to device_ordering_allowed = true
  When  a backfilled CSP and a non-backfilled CSP each open the ordering surface
  Then  the backfilled CSP sees the card; the non-backfilled CSP does not
  Verify:
    • count(csp_exposure WHERE device_ordering_allowed = true) = size of the live-fleet list
    • a CSP intentionally omitted from the list returns ORDERING_DISABLED
EDGE-2: Ops flips the flag — next read reflects it
  Given <csp_X> is currently device_ordering_allowed = false (card hidden)
  When  Ops runs the ALLOW update (sets true, ordering_block_reason, ordering_updated_by)
  And   <csp_X> re-opens the ordering surface
  Then  the card now appears and the engine evaluates the computed gates
  Verify:
    • ordering_updated_at advanced; reason + updated_by persisted; audit row written by the trigger
    • no stale cache serves ORDERING_DISABLED after the flip (read reflects current DB state)
EDGE-3: Flag OFF dominates an otherwise-eligible CSP
  Given <csp_X> would pass every computed gate (good SD, capacity, quality)
  And   device_ordering_allowed = false
  When  <csp_X> opens the ordering surface
  Then  verdict = ORDERING_DISABLED (the manual flag overrides a clean computed pass)
  Verify:
    • response shows ORDERING_DISABLED, not eligible(A,B)
    • Negative — no A/B numbers are surfaced
EDGE-4: Read-API-only — order create is NOT blocked (documented residual)
  Given device_ordering_allowed = false for <csp_X>
  When  a caller POSTs /api/asset-custody/orders directly for <csp_X>
  Then  the order is still created (Gate 0 is enforced on the eligibility read only)
  Verify:
    • this is the accepted v1 behaviour (read-API-only scope) — documented in A5/residual,
      NOT a defect. If a server-side block is later required, wire the flag into
      DeviceOrderGuards.checkCspEligibilityForOrdering at DeviceOrderServiceImpl.createOrder.
