NetBox Inventory — Custody-State Visibility in Summary & Filters

The "All NetBox" inventory page shows a state-wise summary of a CSP's devices and a matching filter-chip row. Today, devices in three custody states are counted nowhere on this page, and written-off devices are counted under a category whose name does not mention them. This spec makes every resting custody state visible and correctly named, without changing how any existing category behaves.

Author: Jaivin Prajapati  ·  Reviewer: Engineering  ·  Tier governed by: Lead PM

Quick Check

7-line triage. Filled after the body was completed.
What is changing?
Four custody states gain their own summary category + filter chip on the All NetBox page (Pending Receipt, Recovery Pending, To Be Handed Over, Written Off — the last split out of "Damaged / Lost"); devices in previously unmapped states get readable state text.
What triggered it?
PM audit: devices in 3 of 12 custody states are invisible in the summary/filters; the "All" headline undercounts the listed devices; some device rows render an untranslated placeholder code.
Blast radius
All NetBox page (summary card, filter chips, device rows) and device-detail state text — CSP-facing only.
Reversible?
Yes — removing the four new categories and the new state texts restores today's view exactly; no data is created or destroyed.
Money / PII / migration?
No / No / No — display and categorisation only; carry-fee and write-off liability computations untouched.
OS impact / sign-off?
NetBox Asset Custody OS — Yes (inventory category contract amended 6 → 10). Sign-off: Pending. All other OSes: No.

A2. Why This Change WHAT

QuestionAnswer
What's wrong with the current behaviour?The custody lifecycle has 11 resting states, but the inventory page's summary and filters cover only 8 of them. Devices that are (a) dispatched but not yet receipt-confirmed, (b) awaiting recovery from a customer after deactivation, or (c) recovered after being declared lost are counted in no category and cannot be filtered to. Written-off devices are counted under "खराब / गुम (Damaged / Lost)" — a name that never mentions them. The "All" headline is the sum of the visible categories, so it is lower than the number of devices actually listed under "All". Two of the invisible states also render an untranslated placeholder code as the device-row state text.
Who experiences it?Every CSP viewing their NetBox inventory — most acutely CSPs with devices in transit, in customer recovery, or written off. Secondary: support/ops who field "my device count doesn't add up" and "what does this code mean" queries.
Cost of leaving it as-is?CSPs cannot account for devices they are financially responsible for (write-off liability, recovery obligations), eroding trust in the app as the single source of truth; avoidable support tickets; disputes during settlement because the CSP "never saw" the device in the app.

A3. Current Behaviour WHAT

Tip: written as "Given X, the system does Y" — observable behaviour only.
Trigger / conditionObservable behaviour today
CSP opens the All NetBox (inventory) pageA summary card shows an "All" row with a total, followed by six category rows with counts: With customers · With me · On order · Returning · Returned · Damaged / Lost. Below it, a horizontally scrollable filter-chip row mirrors the same six categories plus "All". Tapping a row or chip filters the device list to that category.
A device has been dispatched to the CSP but the CSP has not yet confirmed receipt (state: pending receipt confirmation)The device is counted in no summary category and has no filter chip. It appears only in the unfiltered "All" device list, where its state text renders as an untranslated placeholder code instead of readable text.
A customer's connection has been deactivated and the device is still with the customer, awaiting recovery (state: customer recovery pending)The device is counted in no summary category and has no filter chip. It appears in the unfiltered "All" list with readable state text ("कस्टमर से वापस लाना है"), but the CSP cannot see how many such devices exist or filter to them.
A device that was declared lost is later recovered and is awaiting handover back to Wiom (state: recovery hold)The device is counted in no summary category and has no filter chip. It appears in the unfiltered "All" list with an untranslated placeholder code as its state text. It has also left the "Damaged / Lost" count (it is no longer lost), so it is visible nowhere.
A device is written offIt is counted inside the "खराब / गुम (Damaged / Lost)" category together with damaged and lost devices. There is no way to see the written-off count on its own, despite write-off carrying a distinct financial consequence for the CSP.
CSP reads the "All" total on the summary cardThe total equals the sum of the six visible category counts. When devices exist in the three invisible states, the device list under the "All" filter contains more devices than the headline number.
CSP opens device detail for a device in one of the two unmapped statesThe state timeline shows the same untranslated placeholder code wherever those states appear.

A4. Desired Behaviour WHAT

Trigger / conditionDesired observable behaviour
CSP opens the All NetBox (inventory) pageThe summary card shows "All" plus ten category rows: With customers · With me · On order · Pending Receipt · Recovery Pending · Returning · To Be Handed Over · Returned · Damaged / Lost · Written Off. The filter-chip row mirrors all ten plus "All". Tapping any row or chip filters the device list to exactly that category, as it does today for the existing six.
A device has been dispatched but receipt is not yet confirmedIt is counted under "रसीद बाकी / Pending Receipt", filterable via its chip, and its device-row state text reads "रसीद बाकी / Pending receipt".
A connection is deactivated and the device is still with the customerIt is counted under "रिकवरी जारी / Recovery Pending" and filterable via its chip. Its device-row state text is unchanged ("कस्टमर से वापस लाना है").
A lost device is recovered and awaits handover to WiomIt is counted under "जमा करना बाकी / To Be Handed Over", filterable via its chip, and its device-row state text reads "जमा करना बाकी / To be handed over".
A device is written offIt is counted under "राइट-ऑफ़ / Written Off" with its own chip. "खराब / गुम (Damaged / Lost)" now contains only damaged and lost devices, so its name is truthful.
CSP reads the "All" totalEvery device in the CSP's custody is counted in exactly one category, so the headline reconciles with the "All" device list (the known On-order ↔ Pending-Receipt overlap window excepted — see A7.2 E1).
A device is ever in a state the app does not recognise (future-proofing)Its state text shows a graceful fallback — "स्थिति अपडेट हो रही है / Status updating" — never a raw placeholder code. (Same fallback applies on the device-detail timeline.)

A6. Must-Not-Change — Regression Guard GUARD

Reviewer note: scoped to what an engineer might realistically break while adding categories to a shared summary/filter surface. Each line has a REGRESSION block in B5.
Adjacent behaviour that must not changeWhy it's in the blast radius
G1 · "With me" remains one merged category (setup-pending + idle devices together); its membership and count basis are unchanged.An explicit product decision; splitting categories elsewhere invites "splitting" this one too.
G2 · "On order" keeps its current count basis (units on the active order) and remains count-only (no device list behind its chip), including during the dispatch→receipt window.The new Pending Receipt category overlaps it in time; the accepted-overlap decision (A7.2 E1) must not silently morph into a change to On order.
G3 · Membership and counts of With customers, Returning and Returned are byte-for-byte as today.They share the same summary/categorisation surface being edited.
G4 · Damaged and lost devices remain counted in "Damaged / Lost" (only written-off leaves it).R4 narrows this category; over-narrowing would orphan damaged/lost devices the same way this change fixes others.
G5 · Existing device-row state texts (active, idle, setup-pending, returning, returned, damaged, lost, written-off, recovery-pending) are unchanged.New text entries are being added to the same label set; existing entries must not be touched.
G6 · Existing chips' filtered lists, the search box, pagination, and tapping a device row to open its detail behave exactly as today.All live on the page being modified.
G7 · The NetBox Home (action window) — device count, carry-fee strip, prioritised device list, quick actions — is unchanged.It is fed by the same inventory data; a categorisation change must not leak into the action surface.

A7. Rules, Invariants & Edge Cases Affected WHAT

A6 or A7? Preserved behaviour → A6. New/changed rules, new invariants, new edges → here. Everything here is verified in B5.

A7.1 Rules & invariants (must always hold)

Rule / invariantStatement
INV-1 — single-category membershipAt any moment, every device in a CSP's custody is counted in exactly one summary category (On order excepted — it counts ordered units, not custody devices).
INV-2 — no raw state codesNo CSP-facing surface ever renders a raw/untranslated state code as a device's state text — every state resolves to readable Hindi/English text or the fallback.
INV-3 — count ↔ list consistencyFor every device-backed category, the number shown on its summary row equals the number of devices its filter returns.
RULE-1 — truthful Damaged / LostThe "Damaged / Lost" category contains only damaged and lost devices.
RULE-2 — category completenessEvery resting custody state maps to exactly one summary category (the in-transfer moment is excluded by design — see A7.2 E5).

A7.2 Edge cases

Edge / conditionIntended business outcome
E1 · Device in the dispatch→receipt window (order still active and device pending receipt)Accepted overlap (PM decision, 2026-06-06): the units stay in "On order" and the devices appear in "Pending Receipt"; the "All" headline includes both during this window. No change to On order.
E2 · Lost device is recoveredIt moves from "Damaged / Lost" to "To Be Handed Over": Damaged / Lost count decreases by one, To Be Handed Over increases by one, at the same refresh.
E3 · A category has zero devicesThe summary row and chip still appear, showing 0 — consistent with how existing categories behave today.
E4 · A device reports a state the app does not recogniseIt appears in the "All" list with the fallback state text; it is counted in no category. (No category is invented for unknown states.)
E5 · Device at the instant of transfer between CSPs (transient reassignment)Excluded by design: this state never rests, so no CSP can observe a device in it; it gets no category, no chip, no state text. If one were ever observed, E4's fallback applies.

B5. Acceptance Criteria — Verification Layer HOW

Why this matters: code is AI-generated; review is human. B5 is the contract the generated code is checked against. Every block is labelled with its class.

Business logic

LOGIC_01 (logic · happy · R1): Pending-receipt device is counted and filterable
Given a CSP with one device dispatched to them and receipt not yet confirmed
When they open the All NetBox page
Then the "Pending Receipt" summary row shows 1
And selecting the "Pending Receipt" chip lists exactly that device
LOGIC_02 (logic · happy · R2): Recovery-pending device is counted and filterable
Given a CSP with one device awaiting recovery from a deactivated customer
When they open the All NetBox page
Then the "Recovery Pending" summary row shows 1
And selecting its chip lists exactly that device
LOGIC_03 (logic · happy · R3): Handover-pending device is counted and filterable
Given a CSP with one device recovered after being declared lost, awaiting handover
When they open the All NetBox page
Then the "To Be Handed Over" summary row shows 1
And selecting its chip lists exactly that device
LOGIC_04 (logic · happy · R4): Written-off device sits in Written Off, not Damaged / Lost
Given a CSP with one written-off device and no damaged or lost devices
When they open the All NetBox page
Then "Written Off" shows 1 and "Damaged / Lost" shows 0
And the device appears under the "Written Off" chip only
LOGIC_05 (logic · negative · R4/RULE-1): Damaged and lost devices do not leak into Written Off
Given a CSP with one damaged device and one lost device and no written-off devices
When they open the All NetBox page
Then "Damaged / Lost" shows 2 and "Written Off" shows 0
And the "Written Off" chip lists no devices
LOGIC_06 (logic · negative · R8): New-state devices do not appear under any old category's filter
Given a CSP with devices only in the three newly-categorised states
When they select each pre-existing chip in turn (With customers, With me, Returning, Returned, Damaged / Lost)
Then every one of those filters returns an empty list
And each pre-existing summary row shows 0
LOGIC_07 (logic · happy · R5/R6): Readable state text for the two newly-texted states
Given one device pending receipt and one device awaiting handover
When the CSP views them in the device list (Hindi and English app language in turn)
Then the first reads "रसीद बाकी" / "Pending receipt" and the second "जमा करना बाकी" / "To be handed over"
And no placeholder code is visible anywhere on the row
LOGIC_08 (logic · negative · R7): Unknown state falls back gracefully
Given a device reporting a state the app has no display text for
When the CSP views it in the All list and opens its detail timeline
Then its state text reads "स्थिति अपडेट हो रही है" / "Status updating" in both places
And the device is counted in no summary category (E4)

Computation & calculation

COMPUTE_01 (computation · normal): All headline reconciles with category counts
Given a CSP with devices spread across all ten categories and no active order
When they open the All NetBox page
Then the "All" total equals the sum of the ten category counts
And equals the number of devices listed under the "All" filter
COMPUTE_02 (computation · boundary zero · E3): Zero-count categories
Given a CSP with no devices in any of the four new categories
When they open the All NetBox page
Then all four new rows and chips are present showing 0
And selecting any of their chips shows the empty-result state, not an error
COMPUTE_03 (computation · boundary max-shift · E2): Lost → recovered moves exactly one unit between categories
Given a CSP whose "Damaged / Lost" shows N (N ≥ 1) including one lost device
When that lost device is recovered and the page is refreshed
Then "Damaged / Lost" shows N−1 and "To Be Handed Over" has increased by exactly 1
And the "All" total is unchanged
COMPUTE_04 (computation · boundary overlap · E1): Dispatch→receipt window counts in both On order and Pending Receipt
Given a CSP with an active order of 3 units that has been dispatched and not yet receipt-confirmed
When they open the All NetBox page
Then "On order" shows 3 and "Pending Receipt" shows 3 simultaneously (accepted overlap)
And after the CSP confirms receipt, "On order" shows 0, "Pending Receipt" shows 0, and "With me" has increased by 3

Invariants

INVARIANT_01 (from A7.1 INV-1): Single-category membership
Given any device in a CSP's custody, in any resting state, at any moment including immediately after a state change
Then it is counted in exactly one summary category
And never in two categories at once, and never in zero (unknown states per E4 excepted)
INVARIANT_02 (from A7.1 INV-2): No raw state codes anywhere
Given every CSP-facing surface that shows a device state (summary, chips, list rows, detail, timeline), across every custody state and both languages
Then the rendered state text is always readable Hindi/English or the declared fallback
And never a raw code or placeholder key
INVARIANT_03 (from A7.1 INV-3): Count ↔ list consistency
Given any device-backed category (all except On order) with count N on its summary row
Then its filter returns exactly N devices
And this holds for every one of the nine device-backed categories

Use & edge cases

EDGE_01 (edge · E5): In-transfer devices are never visible
Given a device at the instant of being transferred between CSPs
When either CSP views their inventory at any observable moment
Then the device appears either under the old CSP (pre-transfer state) or the new CSP ("With me") — never in a "transfer" category, which must not exist
EDGE_02 (edge · B1 branch): Every resting state reaches a category — none left behind
Given a CSP holding one device in each of the eleven resting custody states
When they open the All NetBox page
Then each of the nine device-backed categories shows its expected count and the eleven devices are all accounted for
And the unfiltered All list contains exactly eleven devices, each with readable state text
EDGE_03 (edge · E4 negative): Unknown state does not invent a category
Given a device reporting an unrecognised state
When the CSP opens the All NetBox page
Then no new summary row or chip appears for it
And the page renders without error, with the device visible only in the All list (per LOGIC_08)

Regression (one block per A6 guard)

REGRESSION_01 (guard G1): With me stays merged
Given a CSP with two setup-pending devices and three idle devices
When they open the All NetBox page
Then "With me" shows 5, exactly as before the change
And no separate setup-pending or idle category exists
REGRESSION_02 (guard G2): On order is untouched

And its chip still returns no device list (count-only), exactly as today
REGRESSION_03 (guard G3): Unchanged categories count as before
Given a CSP with devices with customers, being returned, and returned

REGRESSION_04 (guard G4): Damaged and lost devices stay put
Given a CSP with one damaged and one lost device

Then both devices remain counted and listed under "Damaged / Lost"
And their device-row state texts ("खराब", "गुम") are unchanged
REGRESSION_05 (guard G5): Existing state texts unchanged

REGRESSION_06 (guard G6): Page interactions unchanged
