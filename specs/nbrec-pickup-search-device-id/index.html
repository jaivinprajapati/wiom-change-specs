NetBox Pickup List — Device ID on the Feed Card for Search

Backend spec for FE PR #464 — a NetBox-ID search on the home-screen NetBox pickup batch list. The search is client-side: it filters the loaded pickup tasks by each card's device_id. The backend already sends the netbox id on those cards, but under netbox_id, not device_id — so the filter never matches. This change adds device_id to the pickup task card, mirroring the value already carried by netbox_id.

Author: Jaivin Prajapati (PM)  ·  Reviewer: Engineering  ·  Tier: Light

Tier
Light
This is a field-name alignment, not new data. The netbox id is already on the NETBOX_PICKUP card as netbox_id (gateway HomeFeedService.toTaskCard, value = TAS objectId, e.g. WBOX-a0a0i9-001). PR #464 reads device_id, so task.deviceId stays null and search-by-device returns nothing. Backend fix (this spec): emit device_id alongside netbox_id (same value). FE-only alternative (no backend): the app reads the existing netbox_id — cheaper, but changes the merged PR. This spec takes the backend route so the FE PR ships unchanged. The home feed is one-shot (not paginated), so a client-side search over the full pickup list is sound.

A2. Why This Change WHAT

QuestionAnswer
What's wrong with the current behaviour?The new NetBox-ID search on the pickup batch list filters cards by device_id, but the feed emits the netbox id under netbox_id. The FE field is always null, so searching by device id matches nothing.
Who experiences it?CSPs with many netbox pickup tasks who want to find one device quickly instead of scrolling.
Cost of leaving it as-is?The shipped search feature is dead for device-id queries — it only ever matches ticket id, connection id, or locality.

A3. Current Behaviour WHAT

Trigger / conditionObservable behaviour today
App loads the NetBox pickup batch list/home/feed returns all tasks in one response (not paginated). Each NETBOX_PICKUP card carries the netbox id as netbox_id (value = TAS objectId, "WBOX-…"). There is no device_id key on the card.
CSP types a netbox id into the search boxThe FE filters the loaded list by device_id (plus ticket id, connection id, locality). device_id is null on every card, so no card matches the device-id query.
NETBOX_RETURN cardsCarry no netbox/device id (NETBOX_RETURN is not an emitted NBREC family today; the list is filtered to NETBOX_PICKUP).

A4. Desired Behaviour WHAT

Trigger / conditionDesired observable behaviour
App loads the NetBox pickup batch listEach NETBOX_PICKUP card carries device_id holding the same netbox id as netbox_id.
CSP searches by netbox idThe client-side filter matches on device_id (case-insensitive substring) and the matching pickup cards are shown.
A card with no netbox iddevice_id is null/omitted; the card still renders and simply doesn't match a device-id query.

A5. The Delta WHAT

The one backend change engineering builds against.
What changesBeforeAfterWhy
Device id key on the NETBOX_PICKUP feed card Netbox id emitted only as netbox_id; no device_id key. Card also emits device_id with the identical value; netbox_id retained for existing consumers. The FE search reads device_id; supplying it makes device-id search work without changing the merged PR.
Additive only: one new key mirroring an existing value, on the NETBOX_PICKUP card. No change to which tasks are returned, their order, or any other field. No new data source — the value already flows from TAS objectId.

A6. Must-Not-Change — Regression Guard GUARD

Adjacent behaviour that must not changeWhy it's in the blast radius
netbox_id keeps its value and continues to be emitted for NETBOX_PICKUP cards.Other consumers read netbox_id; adding device_id must not drop or alter it.
The set, ordering and filtering of tasks in /home/feed is unchanged.Same card builder touched to add the field; easy to perturb the result set.
All other feed-card fields (connection_id, locality, task id, timers, CTA…) keep their values and shape.The home screen and other tasks parse the same payload.
Non-pickup task families are unaffected (device_id absent/null).The field must be scoped to pickup cards, not leak onto unrelated families.
The feed stays one-shot (all tasks in one response, no pagination).Client-side search depends on the full list being loaded; introducing paging would silently break it.

A7. Rules, Invariants & Edge Cases Affected WHAT

A7.1 Rules & invariants

Rule / invariantStatement
INV — same valueOn any NETBOX_PICKUP card, device_id equals netbox_id (both are the TAS objectId); they never disagree.
RULE — pickup-scoped & optionaldevice_id is populated only for NETBOX_PICKUP cards and is null/omitted otherwise; its absence never blocks a card from rendering.
RULE — backend supplies, FE matchesThe backend only supplies the value; matching (case-insensitive substring) is client-side. No server-side search param is added.

A7.2 Edge cases

Edge / conditionIntended business outcome
Pickup card whose upstream objectId is missingdevice_id (and netbox_id) null; card renders; no device-id match.
NETBOX_RETURN familyNo device_id (not an emitted family; out of scope). If NETBOX_RETURN is later emitted with a device id, the same rule applies.
Very large pickup listStill fully searchable — the feed is one-shot, so the whole list is in memory (unlike the paginated all-devices inventory search).
