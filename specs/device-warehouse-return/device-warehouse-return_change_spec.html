Warehouse Device Return (CSP / 3PL) — Acceptance & Closure

Objective: safeguard the custody of every returned asset all the way to the Wiom warehouse — with a complete audit trail — and ensure the customer's internet has not silently stopped working.

What happens when a Wiom NetBox shows up at the warehouse — returned by a CSP or by a 3PL/recovery agent. Pyrops already accepts the physical device in any state, but ACS rejects the return event unless the device is in RETRIEVAL_PENDING. This spec makes ACS accept every return from any custody state, attribute who returned it, move it to RETURNED, and run a per-state closure across every affected entity (custody state, PUT, connection, exposure, security deposit, liability ledger, customer internet). Damage QC is deferred — every return takes the functional happy path. Fundamental state-machine + governance change → EM review before any architectural call.

Author (PM): Jaivin Prajapati  ·  Reviewers: Dhruv · EM  ·  Tier: Full

Quick Check

7-line triage.
What is changing?
ACS accepts device returns from any custody state (today: rejects all but RETRIEVAL_PENDING/RECOVERY_HOLD); Pyrops adds CSP/3PL source + identity; per-state closure of every affected entity; all anomalies persisted as DB flags.
What triggered it?
Operational reality — devices change hands near CSPs and arrive at the warehouse in states ACS won't accept; Wiom learns only at the warehouse; returns stay stuck under the CSP.
Blast radius
Custody state machine, exposure, carry-fee/idle, NBREC closure + ₹50, DEPLOYED→connection deactivation, dispatch receipt, audit/flag persistence. Consumers: Payment, Compensation, TAS, CL OS, Pyrops.
Reversible?
Partial — new transitions are flag-gated, but this is a fundamental state-machine expansion (architectural review required).
Money / PII / migration?
Money Y (no movement on return; liability stands) · PII N · Migration Y (backfill stuck-returned devices + add audit ids — engineering runbook).
OS impact / sign-off?
Asset Custody, Compensation, Payment & Settlement, Connection Lifecycle, TAS, ESR — all Pending.
Tier
Full.

A2. Why This Change WHAT

QuestionAnswer
What's wrong?Pyrops physically accepts any returned device, but when it sends the return to ACS, ACS rejects it (DEVICE_NOT_IN_EXPECTED_STATE) unless the device is in RETRIEVAL_PENDING. There is no CSP-vs-3PL source, no check on who returned it, and anomalies are thrown as exceptions but never recorded.
Who experiences it?Inventory/finance ops (devices unaccounted, exposure/liability wrong), CSPs (returns don't close, missed ₹50), customers (a wrongful pickup is never detected).
Cost of leaving it?₹-value assets unreconciled, silent drift between Pyrops and ACS, no closure of the CSP↔device relationship, no alertable trail of anomalies.

CLOS: the connection ends in the terminal DEACTIVATED state (enum: ACTIVE→PAUSED→PENDING_DEACTIVATION→DEACTIVATED) — a return must finalise deactivation, never leave it at PENDING_DEACTIVATION. A7. Rules, Invariants & Edge Cases WHAT

A7.1 Rules & invariants

Rule / invariantStatement
INV — single custody stateA device is in exactly one custody state at any moment.
INV — accept-all, no silent rejectACS accepts every return Pyrops forwards; it never silently rejects a physically-received device.
INV — exposure setExposure counts exactly {CUSTODIED, DEPLOYED, IDLE, CUSTOMER_RECOVERY_PENDING, RETRIEVAL_PENDING, RECOVERY_HOLD}. RETURNED is never counted; every exit emits one CSP_EXPOSURE_CHANGED(−1).
INV — no liability reversalReturning a device never reverses a booked LOST/DAMAGE/write-off liability.
INV — SD untouched on returnNo return, from any state, moves the security deposit.
INV — audit idsEvery entity entry (custody state, exposure, SD, liability, connection, flag) carries device_id AND csp_id explicitly.
INV — anomaly persistedEvery anomaly is written to a DB flag (not only thrown), so an alert can be built on it.
RULE — source attribution mandatoryEvery return carries returned_by_type + returned_by_id.
RULE — 3PL scope3PL returns are accepted; flagged. Expected = LOST + NOT_RECOVERED_FROM_CUSTOMER; anything else = anomaly flag.
RULE — partial receipt isolationExcluding one PENDING_CSP_RECEIPT device does not block confirmation of the rest.
RULE — functional defaultWhile damage is out of scope, every return is treated as FUNCTIONAL; no DAMAGED diversion.

B5. Acceptance Criteria — Verification Layer HOW

LOGIC_01 (logic · happy): Accept from IDLE
Given a device in IDLE returned by its mapped CSP
When the return is processed
Then the device moves to RETURNED (functional), exposure −1, carry-fee/idle stop that day
And prior liability ledger entries are unchanged
LOGIC_02 (logic · happy): Accept-all, no silent reject
Given a return for a device in CUSTODIED / DEPLOYED / LOST / WRITTEN_OFF
When Pyrops forwards it to ACS
Then ACS accepts it and moves the device to RETURNED — it is never rejected with DEVICE_NOT_IN_EXPECTED_STATE
LOGIC_03 (logic · happy): CRP return closes NBREC with ₹50
Given a CUSTOMER_RECOVERY_PENDING device returned by the mapped CSP within 30 days
Then the NBREC task closes as success ("returned-to-warehouse") and ₹50 is credited
LOGIC_04 (logic · negative): DEPLOYED return, non-blocking flag
Given a DEPLOYED device returned
Then it moves to RETURNED, exposure −1, connection deactivation is triggered, a wrongful-pickup flag is persisted and an ops customer-confirm task is created
And the return is not blocked
COMPUTE_01 (computation · boundary): ₹50 at SLA edge
Given a CRP return with method CSP_PICKUP
When confirmed at exactly entered_recovery + 30 days vs one second later
Then at the boundary ₹50 is paid; one second later no payout, exposure still closes
INVARIANT_01 (A7.1): No liability reversal on return
Given a device already booked LOST/DAMAGED/WRITTEN_OFF
When it is returned to the warehouse
Then the booked liability is never reversed or credited back, and no SD moves
INVARIANT_02 (A7.1): Anomaly persisted, not just thrown
Given any flaggable return (cross-CSP, 3PL-scope, wrongful-pickup)
Then an anomaly_flag row is written to the DB carrying device_id and csp_id
And an alert can query it
INVARIANT_03 (A7.1): Audit ids on every entry
Given any entity entry written during a return (custody, exposure, liability, flag)
Then it carries both device_id and csp_id explicitly
EDGE_01 (edge): 3PL accept + flag
Given a 3PL return for a LOST/NOT_RECOVERED_FROM_CUSTOMER device, and separately for a DEPLOYED device
Then both are accepted; the first flagged "3PL recovery", the second flagged "3PL anomaly" — neither rejected
EDGE_02 (edge): Cross-CSP return
Given a device mapped to CSP-A returned by CSP-B
Then the return is accepted and a cross-CSP flag is persisted
EDGE_03 (edge · transition): Partial dispatch receipt
Given a 10-device order in PENDING_CSP_RECEIPT, one returned
When the CSP confirms receipt
Then the 9 remaining move to CUSTODIED, the returned one is excluded, and its exposure is unchanged
REGRESSION_01 (A6): Existing handover flow intact
Given a RETRIEVAL_PENDING device confirmed by ops
Then it moves to RETURNED with exposure −1 exactly as before
REGRESSION_02 (A6): SD untouched on return
Given a return from any state
Then no deposit_ledger_entry is written and sd_balance is unchanged
REGRESSION_03 (A6): Exposure still starts at receipt
Given an order dispatched to PENDING_CSP_RECEIPT
Then no exposure is counted until the device reaches CUSTODIED
