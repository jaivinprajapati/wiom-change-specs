Customer Migration to Existing CSPs — Backend Seeding Approach

Re-assigning old-world customers (whose CSPs were not migrated) as new active connections under an existing new-world CSP, entirely backend, from an Ops-supplied data file.
Draft v1.1 — for review Prod codebase: csp-os-yaml @ prod Scope: approach only (no UI/UX) All steps code-verified + cited

This document defines the exact backend sequence — SQL inserts, event POSTs, and API calls — to take a migrating customer and land them as an ACTIVE connection under a chosen existing CSP, with the CSP paid the ₹300 recharge payout. Every step is verified against the production source; citations are file:line. Nothing here is inferred.

Verdict on the proposed approach
Sound, and backend-only is achievable. One assumption broke under review: the install flow cannot be "walked" backend-only (OTP hard-depends on the external i2e1 service — see below), so we seed-and-fire instead. Everything else holds — including the install:xyz recharge trigger, which production data confirms is real (the ₹300 install payout lands via a direct-to-compensation recharge whose reference is INSTALL:<id>). We replicate that exact mechanism with a Customer migration:<id> reference.
Production validation (live data, 2026-06-27)
Sampled the 12 most-recent install-completed connections across 5 prod datastores (via analytics replica, DB 113). Every one shows: connection.current_state = ACTIVE, a compensation BASE_PAYOUT_CREDIT of 30000 paise with credit_type=CONNECTION_ENTITLEMENT and recharge_event_ref = INSTALL:<execution_candidate_id>, and a matching wallet BASE_PAYOUT of 30000 keyed on the same reference. The connection is ACTIVE (never PAUSED) when paid → the payout reached compensation directly, not through RV's PAUSED-gated path. This is precisely the Phase 3 + Phase 5 sequence below — our approach mirrors the live install-payout path, only with raw-seeded connection rows instead of a walked install.

Architecture decision: skip TAS, seed-and-fire

Why we do not use the install flow at all

Two facts force this. (1) Install completion is gated on external i2e1 OTP — not drivable backend-only. (2) Event fan-out is autonomous and per-recipient uncontrollable: once CONNECTION_REQUEST is posted, CL emits CL_CONNECTION_REQUESTED → DAS routes → ALLOCATION_ACCEPTED is delivered by the routing registry to every subscriber (including TAS, which then creates an install candidate). You cannot emit "to CL but not TAS".

So to create zero install candidates (the chosen option — cleanest data, no orphan stuck-install tasks), connection creation must not enter the event chain. We raw-INSERT the connection (and reconciliation allocation) rows directly, then fire only the activation/recharge events, which reach CAEO/ACS/Quality/Compensation but never TAS.

Trade-off: event/API POST vs direct SQL insert

Several steps can be done either as an event POST to a service's /events/* endpoint or as a direct SQL insert. The choice is not cosmetic — it changes idempotency, side-effects, and how much state-machine validation you get. The table picks a side per step; the governing rule: use SQL where an event would create an unwanted side-effect (a TAS candidate) or where the event path can't carry a field we need; use the event where it correctly drives a state transition we want plus its downstream auto-creates.

StepChosenWhy this sideTrade-off of the other side

Residual risks & cautions

#RiskMitigation
1CSP-id format — resolved: it's the 6-char short code in every store (prod-verified). Residual risk only if a target DB column is still UUID-typed.Use the CSP short code throughout. Verify each column's deployed type once on the target DB before the bulk run.
2CAEO async ordering — recharge-confirmed no-ops if the CAEO row (created by CL activation over the outbox) hasn't landed yet.Poll for the CAEO row before Phase 4, or raw-insert the customer_access_states row directly (also fixes the customer_id quirk).
3Raw inserts bypass state-machine guards entirely — the script is the only correctness check.Validate every field (state strings, enum FKs, UUIDs, jsonb) pre-insert; run in a transaction per customer; dry-run on staging first.
4Idempotency / re-runs — partial failure mid-sequence could double-insert.Dedupe by customer_id (Phase 0a); unique connection_id guards CL/DAS; unique rechargeReferenceId guards the payout; make the whole per-customer run idempotent.
5Audit gap — no TAS install record, step history, or incentive-eval row for migrated customers.Accepted trade-off of skip-TAS. ₹300 is paid via the direct recharge route instead of the install incentive signal. Tag seeded rows (e.g. correlation_id) for traceability.
6Out-of-coverage lat-lng — no zone polygon → cannot resolve zone_id.Hard fail in Phase 0b; route these customers to a manual zone-polygon exercise before migration.
7Device CSP ownership not validated by the install signal handler.Phase 1 must set netbox_custody.csp_id = chosen CSP exactly; it determines custody ownership.
