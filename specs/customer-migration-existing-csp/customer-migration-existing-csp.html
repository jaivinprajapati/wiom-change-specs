Customer Migration to Existing CSPs

Re-assigning old-world customers (whose CSP wasn't migrated) as new active connections under an existing new-world CSP — entirely backend.
Draft v2.1 · for go-ahead review Approach only — no UI/UX Code-cited @ prod + prod-data verified
What we're asking you to approve

A backend-only script that takes an Ops data file and lands each migrating customer as an ACTIVE connection under a chosen existing CSP — with the CSP paid the usual ₹300. No app screens, no on-ground action, no install task. We seed the end-state directly and fire the same events a real installation fires.

This doc = the approach + the exact entities we write. Looking for a go / no-go before we build the script.

How we're thinking about it

01

A migration = an install that already happened

On-ground, these customers are already connected. We're only recording that fact in the new system — not re-doing the work.

02

Don't walk the install flow — seed its result

The real install flow can't complete backend-only (its final OTP step needs the external i2e1 service). So we skip it and write the finished state directly.

03

Fire the same events a real install fires

Activation, device-deploy, plan-window and the ₹300 payout all ride on existing events. We send those exact events — so downstream stays consistent.

04

Force-assign to the one chosen CSP

No scoring, no routing. Ops names the CSP + device; we bind the customer to it directly (caps don't apply on this path).

Why this is safe — it mirrors what production already does
We checked live prod data: every recent real installation ends as an ACTIVE connection paid ₹300 via a recharge sent straight to compensation (reference INSTALL:<id>), not through the normal recharge gate. Our sequence reproduces that exact end-state — we just write the connection rows instead of having a technician walk the app. We tag our version Customer migration:<id>.

The sequence — step by step

0
Pre-flight
validate & seed conditions · halt on hard fails
CHECKNo existing ACTIVE connectionCL
Dedupe by customer_id. A second ACTIVE row corrupts every read for that customer → skip if one exists.
CHECKResolve zone from lat-lngCCS · /capacity/zones/resolve
Point-in-polygon, no fallback → outside all polygons = OUT_OF_COVERAGE. Hard fail (needs a zone polygon first). Yields zone_id.
CHECKCSP authorized in zone — seed if missingCCS · /eligibility/seed
If the chosen CSP isn't authorized for the zone, seed it (AUTHORIZED + exposure row). Needed for correctness & future re-routing.
1·2
Seed device + connection (SQL — emits no events)
raw insert = no install task created
SQLDevice → CUSTODIED (no connection yet)ACS · netbox_custody
INSERT INTO netbox_custody (device_id, csp_id, status) VALUES (:device_id, :csp_short_code, 'CUSTODIED'); -- everything else takes its DB default; leave NULL: -- current_connection_id, connection_id, customer_id ← set later (bind + deploy)
Only 3 columns are mandatory (device_id, csp_id, status); the rest default. A CUSTODIED device has no connection/customer — verified against live rows — so we leave current_connection_id, connection_id, customer_id NULL; they're filled by the bind event + the deploy signal. Seed only after the service has booted once (status is an FK to a startup-seeded ref table). csp_id fixes device ownership — the install signal does not re-check it.
SQLConnection → PENDING_INSTALLCL · connections
INSERT INTO connections (connection_id, customer_id, csp_id, zone_id, service_address, plan_id, current_state, state_timestamp, installation_complete_at) VALUES (:connection_id, :customer_id, :csp_short_code, :zone_id, :addr_jsonb, :plan_id, 'PENDING_INSTALL', now(), now()); -- leave NULL: activated_at ← set by the activation event (step 3)
Mandatory: connection_id, customer_id, zone_id, service_address (jsonb), plan_id; the 9 housekeeping columns (pause_count, retry_count, version, …) default. Direct insert is the only emission-free way (any HTTP create path emits an event → TAS install task). state_timestamp=now() anchors the 72h activation window. installation_complete_at=now() is optional but makes the row match an organic ACTIVE connection (which always has it set).
SQLAllocation → ACTIVE (reconciliation)DAS · connection_allocations
INSERT INTO connection_allocations (connection_id, zone_id, csp_id, allocation_state, allocation_event_type, assigned_at, acceptance_timestamp) VALUES (:connection_id, :zone_id, :csp_short_code, 'ACTIVE', 'NEW_DEMAND', now(), now()); -- id, version, retry_count, parallel_install_warning, the 2 JSONB cols: default
Mandatory: connection_id, zone_id, allocation_state, allocation_event_type (last two are FK-checked / fixed strings). assigned_at + acceptance_timestamp are optional but every live ACTIVE row has them set. Keeps the connection visible to DAS sweeps so a future CSP-exit can auto-reallocate it. connection_id is UNIQUE — the idempotency guard.
3
Bind → activate → deploy (events → ACS / CL, never TAS)
order matters — bind before activate
EVENTBind device to connectionACS · /events/asset-custody/device-bound
{ eventId, deviceId, cspId, connectionId, boundAt: now() }
Sets current_connection_id on the device (status stays CUSTODIED). Must run before activation — the next step's binding guard reads exactly this. Valid only while the device is CUSTODIED/IDLE.
EVENTConnection → ACTIVECL · /events/customer-installation-confirmed
{ eventId, connectionId, sourceSurface:"CUSTOMER_APP", confirmedAt: now() }
Flips to ACTIVE and stamps activated_at (guards: state, source, 72h window, device bound ← prior step). Auto-creates the CAEO row and notifies DAS + Quality — none reach TAS.
EVENTDevice → DEPLOYEDACS · /events/asset-custody/customer-installation
{ eventId, deviceId, cspId, customerId, connectionId, installedAt: now() }
Transitions the device to DEPLOYED and stamps connection_id + customer_id (clears idle_start_date). End-state matches a real deployed device: current_connection_id = connection_id.
4·5
Plan window + ₹300 payout (events)
same path prod uses for real installs
EVENTPlan window → ENABLEDCAEO · /events/customer-recharge-confirmed
{ connectionId, customerId, planId, entitlementEnd: :plan_expiry, paymentReferenceId: "Customer migration:"+:connection_id, … }
Stores entitlement_end = plan expiry verbatim and enables access. (Recommended: raw-insert this row instead — avoids an async race + a customer_id quirk.)
EVENTPay CSP ₹300Compensation · /events/recharge-confirmed
{ cspId, connectionId, eventType:"RECHARGE_CONFIRMED", rechargeReferenceId: "Customer migration:"+:connection_id, … }
Credits a flat 30000 paise to the CSP wallet — posted direct to compensation, bypassing the recharge gate (which needs a PAUSED connection). Auto-provisions the CSP's compensation posture if absent. Exactly the prod install-payout path.

What we deliberately bypass

Install state machine — seed the result instead (avoids the i2e1-OTP wall + no orphan task) OTP / Aadhaar / security fee — never entered DAS routing & scoring — force-assign the chosen CSP RV recharge gate — pay direct to compensation (same as prod installs) Remote internet provisioning — already done on-ground; never blocks activation

Risks to be aware of

RiskMitigation
Raw inserts skip all state-machine guards — the script is the only safety net.Validate every field; one transaction per customer; dry-run on staging.
Re-runs / partial failure could double-write.Dedupe by customer_id; unique connection_id + reference make it idempotent.
Out-of-coverage lat-lng can't resolve a zone.Hard-fail in pre-flight; route to a manual zone exercise.
No TAS install record / step history for migrated customers.Accepted trade-off; tag seeded rows for traceability.
