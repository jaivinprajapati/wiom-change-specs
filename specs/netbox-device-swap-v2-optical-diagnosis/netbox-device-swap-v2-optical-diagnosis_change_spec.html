CSP Netbox Swap V2 — Optical Diagnosis Gate (Swap-or-Not Pre-Check)

A pre-swap diagnosis gate that decides whether a device swap will actually fix the customer's problem — or whether the fault is on the optical / network side, where a swap would waste a device and still leave the customer offline. Before the CSP is allowed to swap, the system reads the old device's optical telemetry and hard-blocks the swap when the signal indicates a fibre/line problem (too weak, too strong, or unstable). This mirrors the manual check the ops team ran while they owned swapping. It is a hard block, exactly like the existing gate checks (G1–G11) — if it blocks, the swap cannot proceed and the CSP is directed to fix the line / contact Wiom support. Fail-open: if there is no reliable optical data, the gate is skipped and the swap proceeds — we don't have enough evidence to blame the network. The production gate runs against a proper telemetry API (not Metabase/Snowflake); the exact data contract is the companion API-requirement doc.

Author: Jaivin Prajapati  ·  Reviewer: Engineering  ·  Tier: Focused (single gate)

Quick Check

7-line triage.
What is changing?
A new Optical Diagnosis Gate (call it G12) is added to the existing pre-swap gate-check phase. It reads the old device's optical readings and hard-blocks the swap when the optical signal points to a network/line fault rather than a device fault: avg < −25 dBm, avg > −8 dBm, or (max − min) > 3 dBm across valid readings. No valid data → skip & allow.
What triggered it?
Swapping (v1) proceeds on any device-fault diagnosis. Ops, who ran swapping manually before, always eyeballed optical health first — a swap can't fix a weak/unstable fibre, so those cases were stopped. We are encoding that check into the flow.
Blast radius
The pre-swap gate-check phase only (SRS/ACS gate stage). A new synchronous dependency on a telemetry optical-history API (telemetry/remote team). One new FE block screen. No change to the swap execution, custody, validation-layer, or ticket-resolution machinery of v1.
Reversible?
Yes — the gate is parameter-driven; thresholds tunable and the whole gate can be disabled (treated as always-allow) via config.
Money / PII / migration?
N / N / N.
OS impact / sign-off?
SR OS (add G12 to the gate-check, surface the block) · ACS (may host the gate computation; consumes the check pre-commit) · Telemetry/Remote API (new optical-history endpoint — Rahul Nijhawan) · Design (block screen copy — Vikash PD). All Pending.

A2. Why This Change WHAT

QuestionAnswer
What's wrong with the current behaviour?The v1 swap flow starts as soon as a CSP records a device-fault diagnosis and the custody/state gates (G1–G11) pass. Nothing checks whether the problem is actually the device. If the real fault is on the optical line (weak/strong/unstable fibre), a swap replaces a perfectly good device, consumes inventory, and the customer is still offline — the new device sees the same bad line.
Who experiences it?Customers (a swap that doesn't restore internet); CSPs/technicians (a wasted site visit + a device that must be returned); Wiom inventory (devices cycled needlessly). Ops previously caught these by manually inspecting optical readings before allowing a swap.
Cost of leaving it as-is?Avoidable device swaps on line faults: churned inventory, repeat tickets, and customer downtime that a swap can never resolve. The information to prevent it (optical telemetry) already exists.
Why a gate, and why hard?Ops treated a bad optical reading as a stop, not a suggestion — a swap on a line fault is simply the wrong action. So the gate is a hard block in the same family as G1–G11: the CSP cannot proceed. The one relief valve is data quality — if the signal can't be read reliably, we don't block (fail-open, A4/A5).

B2. The Diagnosis Logic (exact) HOW

Reproduced verbatim from the ops logic. Strict — no additions.

B2.1 Keep only valid optical readings

For the old device, over the lookback window (P_OPTICAL_LOOKBACK = 1 hour), take each hourly record and exclude it if any of:

  • OPTICAL_AVG is NULL
  • OPTICAL_AVG = 0  (sentinel for "no optical reading")
  • TOTAL_PINGS_RECEIVED = 0

Each surviving record is a valid reading contributing its OPTICAL_AVG value.

B2.2 Block conditions

Over the valid readings compute avg_optical, max_optical, min_optical (of OPTICAL_AVG). Block the swap if ANY:

ConditionMeaning
avg_optical < −25 dBmSignal too weak → fibre / optical / network side, not the device
avg_optical > −8 dBmSignal too strong / out of range → optical side, not the device
(max_optical − min_optical) > 3 dBmUnstable / flapping optical signal → network side

If none are true → allow.

B2.3 No valid data

If B2.1 leaves zero valid readings (or the API returns none / errors) → skip & allow, recording that the gate was bypassed because Wiom could not reliably confirm.

On "readings": each valid hour contributes its OPTICAL_AVG, so the range check uses max/min of the hourly OPTICAL_AVG series. The source also carries per-hour OPTICAL_MIN/OPTICAL_MAX (intra-hour extremes) — available for a tighter instability check in future, but not part of the strict logic.

B3.2 Production API contract (telemetry / remote)

Preferred shape: the API returns raw hourly rows and Wiom's gate applies the exclusions + thresholds — keeping the gate logic Wiom-owned and tunable (D7). Full contract + alternative "pre-computed verdict" shape: companion doc.

Request (old device + window):

GET /device/optical-history?device_id=<old_device_id>&lookback_hours=1

Response (raw rows; Wiom computes the verdict):

{
  "device_id": "GX44909",
  "lookback_hours": 1,
  "records": [
    { "hour_start_ist": "2026-05-02T02:00:00+05:30", "total_pings_received": 1, "optical_avg": -27, "optical_min": -27, "optical_max": -27 }
  ]
}

Required per record: hour_start_ist, total_pings_received, optical_avg. Optional: optical_min, optical_max. Confirm with telemetry: optical_avg is always signed dBm, and 0 is always a missing-data sentinel (never a legitimate 0 dBm).

F. Future Scope — Noted, Not Specced Out of scope for this version

Parked deliberately — recorded so the intent isn't lost, but not part of this build.

F1. Minimum-sample rule for the range check

AspectDetail
The gapWith very few valid readings the instability (max − min) check is weak. A minimum-sample threshold (e.g. require ≥ N valid readings before trusting the range check) would harden it.
Why deferredOps gave no minimum-sample rule; strict logic only for v2. Revisit if false blocks/passes surface.

F2. No-data disambiguation (dead device vs line down)

AspectDetail
The gapFail-open treats "no optical data" as allow, but no-data can mean a dead device (swap correct) or an upstream line/fibre outage (swap won't help). A pre-failure-window look-back could separate the two.
Why deferredAligned decision: allow on no data for v2. Disambiguation is a later enhancement.

F3. Intra-hour instability & deeper optical signals

AspectDetail
The gapThe strict logic uses hourly OPTICAL_AVG. Per-hour OPTICAL_MIN/MAX (and finer telemetry) could catch faster flaps and richer optical faults.
Why deferredKeep v2 verbatim to the ops logic; richer checks are a future gate revision.
